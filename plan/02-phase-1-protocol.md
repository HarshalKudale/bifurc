# 02 — Phase 1: Protocol design and freeze

**Goal:** define and freeze the engine↔client contract as a versioned, schema-first package
(`@bifurc/protocol`) that every later phase depends on.

**Effort:** 2–3 weeks. **Depends on:** P0 (spike 4). **Blocks:** P2, P3, P4, P5 — everything.

> This is the highest-leverage phase in the programme. Every subsequent phase consumes this contract.
> A change here after P4 costs a multiple of a change here today. **Freeze it properly.**

---

- Spike 4 complete: schemas and codegen approach chosen, renderer-unchanged thesis confirmed.
- D9 (versioning) answered — lockstep or independent.

## Work item 1 — Enumerate and classify every handler

`grep -rn "ipcMain.handle" src --include=*.ts` currently returns **112** calls. Plus the CRUD handlers
generated by `src/ipc/handlers/entityCrudFactory.ts`.

Classify every one into exactly four buckets. **Do not skip this and do not guess** — the bucket
determines whether a channel crosses the wire, and mis-classifying inflates the protocol surface and the
test matrix permanently.

| Class | Meaning | Goes on the wire? |
|---|---|---|
| **ENGINE** | Pure engine logic. Becomes an RPC command. | Yes |
| **CLIENT** | Only meaningful on the user's machine (dialogs, tray, zoom, trust store). | **No** |
| **SPLIT** | Both halves exist and must be coordinated. | Partly |
| **DROP** | Dead code. Delete. | No |

## Work item 2 — Collapse the CRUD surface

`entityCrudFactory.ts` already generates add/update/delete for ~11 entity kinds from one parameterized
function. Do **not** port 36 commands.

```
// Instead of:  mock:add, mock:update, mock:delete, rule:add, rule:update, ...
entity.create { kind, entity }   → { id, entity }
entity.update { kind, entity }   → { ok }
entity.delete { kind, id }       → { ok }
entity.load   { kind, wsId, id } → { entity }
entity.list   { kind, wsId }     → { entities }
entity.setEnabled { kind, wsId, id, enabled }
```

The `kind` discriminator maps to the existing `CrudFactoryOpts` fields (`configKey`, `folderConfigKey`,
`isFlat`, `hasEnabledState`). The factory already encodes all of this — the protocol just exposes it
generically.

**Caveat:** a handful of CRUD operations have special behaviour baked into the factory that must survive
the generalisation — `rule`/`mock` use `unshift` instead of `push`, and `mapping` delete cascades into
`proxyRules` (`entityCrudFactory.ts:155`). Encode these as documented per-kind behaviour, not as special
commands.

## Work item 3 — Command naming convention

Keep the existing `namespace:verb` shape. It already ships (`mock:add`, `config:get`) and the companion
extension consumes it.

```
entity.create          server.start          tls.generate
entity.update          server.stop           tls.status
entity.delete          proxy.status          tls.importCert
config.get             graphql.introspect    export.create
config.save            grpc.execute          import.preflight
sync.push              soap.execute          import.commit
git.diff               runner.exportReport   blob.put
```

Rules:
- Namespace is the **domain noun**, verb is the **action**. Never `getConfig` / `configGet`.
- Verbs are the same everywhere: `get`, `list`, `create`, `update`, `delete`, `execute`, `status`.
- Engine commands never contain a filesystem path (see `File_Ops_Protocol.md` §8).
- Event names use the same namespace: `event.log.entry`, `event.sync.status`, `event.server.error`.

## Work item 4 — Schema format and codegen

Pick **one**, now, and use it everywhere. Recommendation: **Zod**, because
- it validates at runtime on the engine (untrusted input from a network client — this matters),
- it infers TypeScript types (`z.infer`) so there is one source of truth,
- `zod-to-json-schema` gives you JSON Schema for docs and for non-TS clients.

```ts
// packages/protocol/src/commands/entity.ts
export const EntityCreate = z.object({
  kind: z.enum(ENTITY_KINDS),
  entity: z.record(z.unknown()),          // refined per-kind
  workspaceId: z.string().optional(),
});
export type EntityCreate = z.infer<typeof EntityCreate>;
```

**Validation is not optional.** The engine executes scripts and spawns processes. Every command payload
must be validated before it reaches a handler.

### Codegen output

```
packages/protocol/
  src/commands/*.ts      # schemas + inferred types
  src/events/*.ts        # event payload schemas
  src/errors.ts          # error taxonomy
  src/version.ts         # PROTOCOL_VERSION
  dist/                  # build output
```

The client's method signatures are **derived** from these, which is what makes the P5
`window.api`-compatibility type-check possible.

## Work item 5 — Error taxonomy

Today handlers return ad-hoc `{ ok: false, error: "some string" }` or throw. That does not survive a
network boundary or a client that needs to react differently per failure.

```ts
export const ErrorCode = {
  BAD_REQUEST:      "BAD_REQUEST",       // schema validation failed
  NOT_FOUND:        "NOT_FOUND",
  CONFLICT:         "CONFLICT",
  UNAUTHORIZED:     "UNAUTHORIZED",      // missing/invalid token
  FORBIDDEN:        "FORBIDDEN",         // authenticated but not permitted
  UPSTREAM_FAILED:  "UPSTREAM_FAILED",   // the proxied service failed
  TIMEOUT:          "TIMEOUT",
  UNSUPPORTED:      "UNSUPPORTED",       // capability not negotiated
  ENGINE_ERROR:     "ENGINE_ERROR",      // unhandled internal
} as const;
```

Wire shape:

```ts
{ id, ok: false, error: { code: ErrorCode, message: string, details?: unknown, retryable: boolean } }
```

Keep the **existing** `{id, ok, data, error}` envelope from `companionServer.ts` — it works and it
ships. Only enrich the `error` field from a string to an object.

**`retryable` matters.** `graphql:introspect` against a dead endpoint is retryable; a schema validation
failure is not. The client's retry logic needs to know.

## Work item 6 — Event model

Seven events exist today: `sync:status`, `sync:entityStatus`, `log:entry`, `log:chunk`, `server:error`,
`companion:refresh`, `webhook:payload`. Over a remote transport they need two properties they currently
get for free from being in-process.

### Sequence numbers

```ts
{ event: "event.log.entry", seq: 48213, payload: {...} }
```

Every event carries a monotonic `seq`. On reconnect the client sends its last-seen `seq` and the engine
**replays from there or tells the client to resync**. Without this, a brief network blip silently loses
log entries and leaves the UI showing stale state forever. This is the single most likely source of
"it works locally but is broken remotely" bugs.

### Backpressure and coalescing

`log:entry` fires per proxied request. `log:chunk` streams process output. Over a remote link these will
saturate a slow connection.

- `log:entry`: **coalesce into batches** (e.g. up to 100 entries or 250 ms, whichever first).
- `log:chunk`: keep streaming, but add a flow-control window so the engine can pause a chatty child
  process.
- Add a documented drop policy: under sustained overload, drop `log:entry` before `server:error`.

### Subscription model

```ts
// client → engine
subscribe   { events: ["event.log.entry", "event.sync.status"] }
unsubscribe { events: [...] }
```

Explicit subscriptions (rather than firehose) let a CLI subscribe to only what it needs, and let the
engine skip serialisation for uninterested clients.

## Work item 7 — Version handshake and capabilities

```
hello  { protocolVersion: "1.0", clientName: "electron-shell", clientVersion: "0.4.0" }
   ←   { protocolVersion: "1.0", engineVersion: "0.4.0",
         capabilities: ["blob", "stdio", "events.replay", "tls.install"], sessionId, token? }
```

Rules:
- **Major mismatch → refuse to connect** with a clear message. Do not attempt best-effort.
- **Minor mismatch → connect, degrade.** A client must tolerate an engine that lacks a capability and
  disable the corresponding UI.
- Capabilities are how the client knows whether the blob layer exists, whether event replay is
  supported, and whether it may ask the engine to do something OS-privileged.

Under D9 = lockstep, `protocolVersion` and `engineVersion` move together — but **keep them as separate
fields anyway.** You will want to decouple them later and retrofitting a version field is painful.

### The extension exception — design for it here

The companion extension moved to its own repository on 2026-09-14. It is now an **external client you
cannot update atomically with the engine**, which breaks the D9 lockstep assumption for one client.

Three consequences that must be designed into the protocol now, not retrofitted later:

1. **`clientVersion` must be recorded per session** so the engine can log and diagnose which extension
   build is connected. You will need this the first time a user reports a bug.
2. **The extension's four commands are a frozen public API** across at least one minor version:
   `mock:add`, `request:add`, `folder:add`, `config:get` (`src/companion/allowedActions.ts`).
   Do not rename or reshape them during the P1 command-naming pass. Keep them as aliases if the internal
   namespace changes — the mapping belongs in the same hand-written shim file as the P5 compatibility
   shims.
3. **A minor mismatch must never refuse a connection.** An older extension connecting to a newer engine
   is the *expected* state for weeks after every release. Refusing it would break users' browsers
   silently. Refuse on **major** only.

Record the extension's version support window in `protocol-changes.md` when you freeze.

## Work item 8 — Package setup

```
packages/
  protocol/     # no runtime deps beyond zod — must be importable from Node, Bun and a browser
```

- `protocol` must be **environment-agnostic**: no `fs`, no `path`, no Node built-ins. It is consumed by
  the engine, the Electron shell, the CLI, and a browser bundle.
- Build with `tsup` to ESM + CJS with type declarations.
- Add a `PROTOCOL_VERSION` constant exported from the package so shell and engine cannot drift.

## How to start — the first three things

1. **Run the classification.** `grep -rn "ipcMain.handle" src --include=*.ts > /tmp/handlers.txt`, then
   work through it into `plan/handler-classification.md`. Do this before writing any schema. You cannot
   design a contract without knowing what it must carry.
2. **Collapse the CRUD surface** (item 2) — it removes ~36 channels from the classification before you
   start designing, which makes everything after it smaller.
3. **Write `errors.ts` and `version.ts` first.** They are tiny, they are referenced by everything, and
   writing them forces the two decisions that are hardest to change later.

## Acceptance criteria

- [ ] `plan/handler-classification.md` covers all 112 + generated channels with a class each.
- [ ] CRUD collapsed from ~36 channels to 6 generic commands.
- [ ] `@bifurc/protocol` builds to ESM + CJS + `.d.ts` with no Node built-ins in its dependency graph.
- [ ] Every command has a Zod schema; a smoke test validates a valid and an invalid payload per command.
- [ ] Error taxonomy implemented; every existing ad-hoc error string mapped to a code.
- [ ] Event envelope includes `seq`; `subscribe`/`unsubscribe` specified.
- [ ] `hello` handshake specified with version refusal and capability degradation rules.
- [ ] `PROTOCOL_VERSION` exported and referenced by a smoke-test server and client.
- [ ] **The protocol is frozen.** A change after this point requires a written note in
      `plan/protocol-changes.md` explaining why it could not wait.

## Rollback

The protocol package is additive — it does not modify existing code until P2. If it proves wrong,
delete the package and start again. **Cost of rollback rises sharply after P4**, which is the argument
for spending the full 2–3 weeks here.

---

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Classification is rushed and mis-buckets channels | **High** | The classification *is* the deliverable. Budget a full week for it alone. |
| Protocol churns after P4, forcing client rework | High | Freeze gate + `protocol-changes.md` requiring written justification |
| Schemas fight `any`-typed payloads (`runner:saveReport`, `capture:shareJson` take `unknown[]`) | Medium | Type them properly now; do not carry `z.unknown()` forward as a habit |
| Zod adds measurable runtime cost in the proxy hot path | Low | Validate at the RPC boundary only, never per proxied request |
| `protocol` accidentally imports a Node built-in and breaks the browser build | Medium | Add an ESLint rule banning `node:*` imports in `packages/protocol` |
