## The test migration — the subtle part

`tests/ipc/handlers.test.ts` mocks **only** the seam's *reload* half:

```ts
vi.mock("@bifurc/engine/runtime/instances", async (importOriginal) => ({
  ...(await importOriginal<typeof import("@bifurc/engine/runtime/instances")>()),
  notifyConfigChanged: vi.fn(),
}));
```

`rebindRuntimePorts` is **left real** so the port assertions (`restartEdge`/`startServer`/`startWebhookServer`)
still observe real calls against the listener mocks. Stubbing both halves would have made those assertions
vacuous — they'd watch a stub call nothing. The `reloadConfig` assertions (`workspace.setActive`, `env.setActive`)
move to `notifyConfigChanged`. `importOriginal` spread is required: a whole-module replacement makes
`rebindRuntimePorts` `undefined` → `TypeError` inside the command.

`tests/integration/facadeBinding.integration.test.ts` **keeps** importing `reloadConfig` directly — it tests
the proxy's *own* surface, not the fan-out. `tests/integration/entityConflictScope.integration.test.ts` mocks
`proxy/server`'s `reloadConfig` as a bare `vi.fn()` and never asserts on it; the new chain still lands on that
mock, so no change needed.

## ⚠ THE BIG FINDING — the codemod has a SIXTH blind spot, and it was a real failure

The applied-phase acceptance test is "re-running must report 0". It did report 0 rewrites / 0 files. But the
integration suite **failed**: `Cannot find package '@bifurc/engine/store/configCommands'` at
`tests/integration/workspaceHost.integration.test.ts:622`.

Cause: that file has a **`Record<string, string>` table of module paths** passed to
`await import(/* @vite-ignore */ specifier)` — a **variable**, not a literal. No codemod can resolve it, and
`@vite-ignore` stops Vite resolving it at build time too. Five rows were stale
(`Config`, `Audit`, `Core`, `Folder`, `EntityCrud`).

**Why it surfaced and why that matters:** the test asserts
`expect(mod, "the shell calls register${fn}Commands() but no such export was importable").toBeTypeOf("function")`
— i.e. the guard is *designed* to catch exactly this, and it did. `Config` and `Audit` are rows for call sites
the shell does not currently make, so they were never loaded — but `Core`/`Folder`/`EntityCrud` are real, so the
test blew up on the first one. **The lesson is that a `toBeTypeOf` guard on a dynamic import converts a silent
stale-string into a loud failure** — worth keeping that shape wherever a path table is unavoidable.

Fixed by hand (5 specifiers + the docblock example + a new ⚠ paragraph naming the blind spot, so phase 4–7 does
not rediscover it). Verified: `npx vitest run --project integration tests/integration/workspaceHost… -t registerAll`
→ **1 passed**.

### ⚠ NEW TRAP (blind spot 7): Windows case-only renames are a SILENT no-op

`fs.renameSync(from, to)` where the **filename is identical** and only a *directory* component differs in
case does nothing on NTFS: `mkdirSync(dirname(to))` matches the existing dir case-insensitively, so source
and destination resolve byte-identically and `MoveFileEx` treats it as a self-move — **and it does not
throw.** The codemod printed `moved importExport/commands -> importexport/commands` for all 40 paths and
moved none. Worse: the import specifiers *were* rewritten, so the tree said `./importexport/commands` while
the directory was `importExport/` — **correct on Windows, broken on any case-sensitive filesystem.** My
first standalone test misled me: renaming `MyFile.ts` → `myfile.ts` *works*, because the *filename* changed.
**The discriminator is whether the filename changes, not whether the case changes.**

Fix, in order: rename the **directory** two-step (via a temp name) — but the shim **blocks renaming a
directory that contains subdirectories**, so `importExport/` (3 nested dirs) had to be rebuilt: create the
target, move all 39 files in, `rmdir` the emptied old tree inner-first, rename into place. Then force the
git index: `git update-index --force-remove <old paths>` + `git add <new paths>` — **`git add -A` cannot see
a case-only change when `core.ignorecase=true`** (verified: index unchanged after `git add -A`).

## Follow-up: `kernel/eventBus.ts` fixed — §5.1's central claim is now TRUE

The one item phase 8 recorded as needing a design decision, now done.

**The move: `emitEntityStatus()` → `runtime/entityStatus.ts`**, the engine's **second seam module** (first:
`runtime/instances.ts`, §4.1). `kernel/eventBus.ts` went from two `gitops/` **value** imports to **one
engine-internal import that is a type** (`WebhookPayload`). §5.1's *"`kernel/` imports nothing from the
engine"* — the property §5.2 calls what makes the rule "mechanically checkable rather than aspirational" —
**is now true.**

### ⚠ The decision rule, which is the reusable part

**It could NOT simply move to `gitops/`.** `emitEntityStatus` has **four callers in three files** —
`gitops/syncCommands.ts`, `workspace/entities/coreCommands.ts`, `workspace/entities/entityCrudCommands.ts`,
`workspace/healthbarCommands.ts`. **Three of the four files are `workspace/`-side**, and §6 lets `workspace/`
import only `kernel/` + `utils/`. So "move it next to its dependency" would have turned **2 `kernel → gitops`
edges into 3 `workspace → gitops` ones** — same violation count, different shape, no progress.

**The generalisable rule: before choosing a destination for a misplaced function, count which MODULES its
callers live in.** That, not the function's own dependencies, decides whether "move it next to what it reads"
is even legal. If the callers span a module that may not import the dependency, the answer is a **seam in the
composition layer**, not a move.

### The ratchet shrank, which is the point

Allowlist **24 → 22**, the two `kernel/eventBus → gitops` entries deleted in the same commit. The staleness
assertion is what forced that — it fails if an entry no longer describes a violation, so the list can only
shrink. **That assertion earned its place here.**

`SEAM` became `SEAM_MODULES` (a named set of `runtime/instances` + `runtime/entityStatus`), so a third seam
module is a deliberate act rather than a side effect.
