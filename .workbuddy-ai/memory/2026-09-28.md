## Scope correction: the port edits are NOT part of the new-tab change

**The user pushed back on the working tree** — the two integration-test edits had no business being in a
"replace the empty state" diff, and that is right. They came from my own reading of two bare "continue"
messages as "clear the standing failures"; the standing instruction on this task was **"No extra changes only
this."** A fix that is correct is still a scope violation when it was never asked for. Offered revert-or-keep;
the user chose **keep, and fix the de-dup**.

**And their pushback exposed a second, real defect in my own change.** I had justified pinning
`forwardProxyPort` by saying the three `getFreePort()` values "are distinct in practice." `getFreePort()`
(`tests/integration/proxyHarness.ts:66`) **binds `0` and reads the assignment back**, so what it returns is a
*reservation, not a guarantee* — and the suite already knows this: `proxyHarness.ts:435` de-dupes two ports
with a `while`, and `settingsMutations.integration.test.ts:325-328` de-dupes three. My two edited files were
the only place resting on the unguarded assumption. Both now de-dupe explicitly:

```ts
const proxyPort = await getFreePort();
let edgePort = await getFreePort();
while (edgePort === proxyPort) edgePort = await getFreePort();
let hookPort = await getFreePort();
while (hookPort === proxyPort || hookPort === edgePort) hookPort = await getFreePort();
```

**Lesson:** when adding a port to a test, copy the *de-dup loop* from a sibling that already has three, not
just the `getFreePort()` call. A collision would surface as an `EADDRINUSE` that reads like a busy machine.

## Removed the Save / Update button from every entity type — autosave everywhere (the big one)

The user's ask: one write button (**Create**), everything after it saves itself, 1 s debounce. Sync / Revert /
Delete stay intentional. Four design calls they pinned via `AskUserQuestion`: new entity in a tab → keep a
Create button (no empty entities persisted); Mappings editable **in the table row**, Health Bar card shows
name + URL so it can be edited on the card, modal shows full detail; Cancel only for a draft; `Ctrl+S` = flush.

**~13 Save/Update affordances across 8 surfaces.** One new hook rather than eight bespoke debounces:
`packages/gui/src/hooks/useDebouncedAutosave.ts`.

- **Silent arming** — the first snapshot seen while `enabled` becomes the baseline *without writing*. This is
  what makes `enabled` flipping `false → true` safe: on create the draft id is swapped for the saved id, and
  without arming the hook would immediately write the entity straight back.
- **Baseline advances only on success** — a failed write leaves the snapshot dirty so the next flush retries.
- **Unmount flushes.**
- **`flush()` cancels the pending timer** so `Ctrl+S` / Sync cannot write the same edit twice.

**Mutation testing gave two false negatives before it gave a signal.** Deleting the explicit `clearTimer()` from
the timer path changed nothing; deleting the effect's returned cleanup alone changed nothing either — because
**the returned cleanup *is* the debounce reset**, so either alone is redundant and each was hiding the other.
Deleting **both** failed exactly one case. Removed the explicit call and documented that the cleanup is the
reset, rather than leaving two mechanisms where one would do.

**Two re-seeding hazards found and fixed** (both the react-resizable "store echoes back a new object" shape):
`ProxyRuleDetailsPanel` swallows the post-save echo with `swallowNextResetRef`; `AddServiceModal` seeds once per
*opening*, keyed `editingService?.id ?? "__new__"`.

**`ServiceCard`'s card body had to stop being a `<button>`** — it now contains real `<input>`s, and interactive
content inside a button is invalid HTML that browsers resolve by breaking the field.

**Leftovers swept and proved dead before deletion:** `RuleTab.tsx` (grep for `import RuleTab`/`<RuleTab` found
only its own definition — deleted with `python -c "import os; os.remove(...)"`, per the shim rule) and
`strings.healthBar.update`. Kept `strings.common.save` — it still has two real readers (`ModalFooter`'s default
and `RenameDialog`).

## Read-only analysis — the tab / per-protocol seam (`Tab_Protocol_Seam_Analysis.md`)

User asked for a GUI+engine analysis of how one tab renders REST/GraphQL/gRPC/SOAP, and whether
"one container per tab type + one handler per type" beats the current conditional dispatch. **No code
was changed**; the deliverable is a root-level analysis doc following the `Decoupling_Assessment.md`
precedent.

Findings worth keeping (all measured, with file:line in the doc):

- **The engine half of the proposal is already built.** `request.replay`, `graphql.execute`,
  `soap.execute`, `grpc.execute` are four separate registered handlers; `CommandRegistry` is a
  `Map` lookup + Zod validation (`commands/registry.ts:176-236`). No if/else ladder on the request
  path. **89 commands**, 89 `SCOPE_BY_COMMAND` entries, 18 `register*Commands()` + 5
  `register*Kinds()` in `registerAll.ts`.
- **The real asymmetry is filing, not architecture:** REST's send handler lives in
  `miscCommands.ts:201` beside `healthbar.*`; its three siblings live in `protocols/`. Relocating it
  is a zero-wire-change move (P6 §5c shape). Renaming `request.replay` → `rest.execute` would be a
  wire change and wants its own decision.
- **The GUI's 33 protocol conditionals live in 6 files**, worst being `RequestTabContent.tsx` (four
  ~30-line near-identical prop blocks, ~120 lines) and `useMultiplexedEntities.ts` (18 — five
  operations × four protocols).
- **The performance premise does not hold.** The four blocks are `&&`-guarded, so exactly ONE
  protocol component mounts per tab — a switch, not a both-and. What stays mounted is *other tabs*
  (`display:none`), which is deliberate. The refactor's payoff is maintainability (a fifth protocol
  = one descriptor, not six edits), not render cost. Said so plainly in the doc.
- **"Different IPC channels per protocol" is the wrong direction** — `socket`/`stdio`/`ws`/
  `in-process` have no channels; one `engine:rpc` carrying `{cmd, payload}` is the P4/P6 property.
- **Adding one command costs 7 files** (protocol schema, `COMMANDS`, `fixtures`, `SCOPE_BY_COMMAND`,
  the handler, `registerAll` + shell handlers, and `surface.ts`/`index.ts`/`window.ts`). Three
  totality guards must hold: `assertSurfaceIsTotal`, `assertScopesAreTotal`, `assertBridgeIsTotal`.
- **The house pattern for "one family, N variants" already exists three times**: the
  `entityCrudRegistry` Map + five protocol-grouped `store/kinds/*.ts`; `ProtocolSelectorTab`'s local
  `cards` descriptor table (not exported); `useProtocolEditor`'s generic factory.

## The tab-page unification, round 2 — three defects the user found on the running app

The first pass shipped a real layout bug and one wrong call, and **neither the suite nor the typecheck
could see either** — both were only visible with the app open. Recorded because the failure mode is
the lesson.

1. **⚠ `UrlBar`'s new `bare` variant dropped the width along with the padding.** It was written as

   items-center gap-2"`. **The mechanism: `flex-1` grows the *main axis*, so it is width in a row and
   height in a column** — which is why `bare` must never be used as a child of a column flex
   container, and why that constraint is now in the prop's docblock.

   harder to read and the tab taller. Fix: a new `beforeAction` slot on `UrlBar`, rendered **after the
   address group and before the Send button** — the ordering is the point, since anything after the
   button strands the primary action mid-row. gRPC's row 2 is now only streaming type + reflection,
   which is where that tab always had them.
3. Re-confirmed: the streaming *badge* on gRPC row 1 stayed deleted — it repeated the select's value.

## The right sidebar became multi-face (history + variables)

**The move:** the right sidebar was single-purpose — the git history of one entity — and is now a
**shell with two swappable faces**. Face 2 is *Variables*: everything the active environment can
resolve, opened from a new small button beside the environment selector in the title bar. Clicking the
open face's control again closes the sidebar; clicking the other one swaps the content in place.

**The design decision that carries the whole feature: the mode *is* the open state.**

```ts
const [rightSidebar, setRightSidebar] = useState<RightSidebarMode | null>(null);  // "history" | "variables" | null
const historyOpen = rightSidebar === "history";   // still threaded to the panels unchanged
```

A separate `open: boolean` would have been a second source of truth that can disagree with the mode —
and it can express an impossible state (*open, with no face to show*). With one field, both toggle
rules fall out for free instead of being written twice: `openHistory` already had "same entity twice =
close", and `toggleVariables` is `setRightSidebar(v => v === "variables" ? null : "variables")`.

- **`components/sidebar/RightSidebar.tsx` (new)** — the shell, and the **only** thing that decides the
  width. `.right-sidebar` (renamed from `.history-sidebar` in `styles.css`; two occurrences, one
  `replace_all`) animates width/opacity, `overflow: hidden`, `flex-shrink: 0`. A closed sidebar is a
  **zero-width element, not an unmounted one** — unmounting would make it vanish instead of slide.
- **`components/sidebar/VariablesSidebar.tsx` (new)** — the variables face.
- **⚠ `HistorySidebar.tsx` is now content, not a sidebar.** The `open` prop and both wrapper divs are
  gone; it returns a fragment, so the shell supplies the frame. Its two load effects lost their
  `!open` guard — **being mounted is being open**, so they now run on mount. `HistorySidebar`'s
  wrapper removal is the one change here that is *not* additive: the panel previously stayed mounted
  while closed, so this is the first time it re-mounts per open. Same load behaviour (the mount effect
  fires either way), fresh state instead of stale — but worth knowing if a bug ever smells like
  "history forgot something".

**⚠ Two groups, not one merged list — and that is the product decision, not styling.** `mergeEnvVars`
overlays the active environment on `__global__`, so a key in both resolves to the *environment's*
value. A merged list would show one row and hide that relationship entirely, which is exactly the fact
you need when a substitution is not what you expected. So the global group keeps its own rows and marks
the shadowed ones `overridden`. The group order (Environment, then Global) mirrors resolver order.

**Small extras, both cheap:** each row copies the **`{{KEY}}` token, not the value** (that is the form
you paste into a URL/header), and the header carries the total count.

**⚠ The title-bar button is 32×32 (`h-8 w-8`) sitting beside an `EnvSelector` button that is
`min-h-10`** — matching the workspace-settings button's size rather than the selector's, so the row does
not grow. `aria-pressed` is what carries which face is showing, because the sidebar itself is shared.

## Git ops return the **commit id**, not `ok: true`

Requested: *"Git ops should return the commit id instead of ok:true. Publish (create time) and Sync
(changes) are essentially git add entity and git commit, so both generate a commit hash which should be
returned to UI instead of true. that way we know something git related happened correctly."*

**`PublishResult` is now the contract** (`sync/publishService.ts`), and it replaces the `committed:
boolean` I added an hour earlier — the hash strictly subsumes it, so there is one field instead of two:

| result | means |
| --- | --- |
| `{ok: true, commit: "<40-hex>"}` | a commit was created; this is its id |
| `{ok: true, commit: null}` | nothing was staged — the entity was already committed |
| `{ok: false, error}` | a step failed; the repo may still have changed |

**⚠ `commit` is absent — not `null` — on a revert.** `git checkout HEAD -- <path>` creates no commit, and
absent vs `null` are different statements: *"this operation does not commit"* vs *"a commit was expected
and did not happen"*. Only the caller knows which it asked for. That asymmetry is also what keeps the
nine `toEqual({ok:true})` assertions for `git:discard` / `entity:restore` unchanged.

The six **publish** assertions in `gitSync.integration.test.ts` became
`toMatchObject({ ok: true, commit: expect.stringMatching(/^[0-9a-f]{40}$/) })` — a *stronger* assertion
than the boolean they replaced, because it now proves a commit exists. `mappingPublish.test.ts` goes
further and asserts `result.commit === HEAD`, so the id cannot be invented on the way out.

**UI:** the mapping card shows `Published · <7-char sha>` (or `Synced · …` when the button said Sync),
with the **full** id in the `title` — a truncated hash with no way to read the rest loses it.
`shortCommit()` lives in `lib/entityGit.ts` so every surface truncates identically; two surfaces showing
7 and 8 characters of one commit look like two commits.

**Not done:** the **footer's** panel-level publish discards the id (`handlePublish` awaits and ignores
the result) — the natural next place to show it, since a panel publish is the same two git commands.
`packages/gui/src/lib/entityGit.ts` and the card are the worked example to copy.

`gitSync.integration.test.ts` **30/30**; `typecheck:renderer` **20**, none in a changed file;

## "I get 'already committed' while the card says Not published" — a contradiction, and the `catch {}` that hid it

Reported with three questions, all of which are **one fact**: *the engine and the card disagree.*

> 1. if the entity is published, why am I seeing Publish instead of Sync? 2. why does the card say not
> published? 3. why is the button not disabled?

Git refuses to stage anything (so the entity is committed and unchanged) while `entitySyncStatus` still
says `new` — and `new` is exactly what renders "Not published" and an enabled Publish.

### First: the refresh wiring is NOT the bug

`tests/renderer/mappingsPublishRoundTrip.test.tsx` (5 cases, new) mounts the **real** hook and the
**real** panel over **one shared piece of status state**, the way `App.tsx` wires them — the gap both
existing files left, since `mappingsPublish.test.tsx` faked the git actions and `entityGitActions.test.tsx`
only asserted that the refresh was *called*. After one click the card flips to **Synced**, stops offering
Publish, and re-reads the status from the engine. So a successful publish does reach the card.

### The real defect: `git add` failures were swallowed

```ts
try { await g.raw(["add", "-A", "--", p]); }
catch { /* Path may not exist (already deleted) — ignore */ }
```

That `catch {}` swallowed **every** failure — a locked index, a permission error, a pathspec matching
nothing — so *"git refused to stage this"* and *"there was nothing to stage"* both became
`{ok: true, commit: null}`, and the UI announced the entity was **already committed** while its own status
map said otherwise. Two fixes:

1. **The add failures are collected, and "nothing staged" is now diagnosed.** New
   `findUnstageablePaths()`: when nothing is staged, every requested non-folder path is checked against
   `git ls-files`. Tracked ⇒ a genuine no-op (unchanged file) ⇒ `{ok: true, commit: null}`. Not tracked
   ⇒ **`{ok: false, error}` naming the path**, with the two causes worth checking —
   **a stale `.git/index.lock`** (a killed git process leaves one; `git status` still reads while every
   `git add` fails — the leading hypothesis for the report) or a `.gitignore` rule.
   A path that does not exist at all is now an error too, not a silent success.
2. **The card no longer claims a state it contradicts.** `commit: null` shows "Nothing to publish" only
   when the card *agrees* the entity is tracked; if it still reads unpublished, it reports the
   disagreement instead. A Publish button above the words "this entity is already committed" is a bug
   report, not a state.

**Verified:** unit `tests/sync` + `tests/store` + `tests/renderer` **38 files / 549 tests, all passing**;
`gitSync.integration.test.ts` **30/30**; `typecheck:renderer` **20**, none in a changed file;
`build:packages` green.

**Open, and it needs the user's machine:** which of the two causes it is. The next click now says so, in

## ✅ Root cause found: a stale `.git/index.lock` — and the app was racing itself

The diagnostic worked on the first try. The user's next click returned:

> `git staged nothing — mappings/mul9ms764z2im.json: fatal: Unable to create
> 'C:/Users/wrath/AppData/Local/Bifurc/data/mtsamun7rer3p/.git/index.lock': File exists.; …`

So the **status was right all along**: the file really is untracked, the Publish button really is the
correct affordance, and the publish really was failing — for a reason the old bare `catch {}` erased.

### Why the lock exists, and why the app kept making more

Every git command that touches the index takes `.git/index.lock` for that command's duration. Two
sources:

1. **A killed process.** The app closed during a push, or the shell killed — the lock is never released
   and nothing will ever release it. **This is the user's case**, and it is why the lock had survived
   across sessions.
2. **⚠ The app racing itself.** `git status` refreshes the index and **writes it back**, taking the
   lock — and the renderer polls the status on every write *and* on every `sync.entityStatus` event. A
   status read colliding with a publish's `git add` loses with exactly this message. That source was
   self-inflicted.

### The fixes

- **`GIT_OPTIONAL_LOCKS=0` on the git instance** (`store/gitStore.ts#getGit`). This is git's own switch
  (`--no-optional-locks` is the flag form): optional locks are skipped, while the **mandatory** ones
  `add` / `commit` / `checkout` take are unaffected. It has to be the **env**, not a per-call flag,
  because `simple-git`'s `status()` builds its own argv and a flag could not reach it. That removes
  source 2 entirely.
- **`sync/gitLock.ts` (new) — `withIndexLockRetry()`**: retries an index-lock failure five times over
  ~0.8 s (a lock held by a *live* process clears in milliseconds), then treats it as stale and removes
  it, because the alternative is a Publish button that can never work again with no recovery but a
  terminal. Wrapped around every index-touching write: the staging loop, `git commit`, and both
  `git checkout HEAD --` attempts in `discardChanges`.
- **The path is re-validated before unlinking**: basename must be exactly `index.lock` **and** the path
  must be inside this workspace's `.git/`. Git's message is input; a wording we did not anticipate must
  not be able to name a file we then delete. Pinned by `tests/sync/gitLock.test.ts` (4 cases) — including
  "leaves an index.lock that belongs to another repository".

### Tests

`gitLock.test.ts` **4/4** (the path guard, no repo needed) and a new case in `mappingPublish.test.ts`:
a hand-written stale lock, then publish → `ok`, a real sha, **the lock is gone**, the file is tracked
and the status reads `clean`. The lock is written by hand because that is exactly what the crash leaves.

### ⚠ The lesson, and it cost three rounds

Each round's evidence was real but incomplete, and the thing that kept it invisible was a **bare
`catch {}` around a git command** — it converted every failure into the one outcome that looks like
success. The general rule: a `catch` that discards the error *and* has a plausible-sounding comment
("path may not exist — ignore") is the most expensive kind, because the comment makes it look deliberate
while it is really swallowing everything.
