# 2026-09-21 — Bifurc

## The P6 reduction's first handler group, and a live regression found on the way in

Started the reduction (`registerIpcHandlers()`) with `tlsHandlers.ts` — §5b-decies' table lists it as 6 dead /
0 live, so it looked like the easiest place to start. It was the one group that could not be deleted as it
stood.

**The finding.** Asking of each of the six channels *what does this body do that the client twin does not*
gave three answers of "appends a path":

- `tls:generate` appended `certPath: caCertPath()` + `keyPath: caKeyPath()`
- `tls:importCert` appended `path: caCertPath()`
- `tls:importKey` appended `path: caKeyPath()`

The engine deliberately reports no path (`File_Ops_Protocol.md` §8), so those appends were the only source.
The client twins — `tlsGenerate` / `tlsImportCert` / `tlsImportKey` — were routed as plain 1:1 `call(...)`
passthroughs by `8d0b81a` (P6 step 3b-1) and dropped them. `TlsSettingsSection.tsx:36,48,67` guards on
`result.ok && result.path` / `result.certPath && result.keyPath`, so **the Settings panel's Generate and
Import buttons have been silent no-ops since step 3b-1**: the CA lands on disk, `handleGlobalChange` never
runs, `config.tlsCaCertPath` stays null, and the panel keeps saying "not configured". A live regression on a
primary flow, invisible because the *dead* channel was the last correct implementation while the *live* one
was wrong.

**Fixed.** The three keys are `shim`, not `transport`, in `surface.ts` — a 1:1 filing *is* the claim that
nothing happens beyond the call, and that filing licensed the regression. The bodies now read the paths from
the `tlsCertStatus` local hook, so no new channel and no new `ClientLocal` member, and `window.api` is
unchanged in shape. The casts that had silenced the compiler (`as ReturnType<BifurcApi[...]>` on the *built*
object, not just on `call()`'s `unknown`) are gone. Four new assertions on the returned **shape** in
`packages/client/tests/client.test.ts` — nothing in the suite had ever asserted a result shape, which is why
a green suite sat over a broken flow. `transport` 70 → 67, `shim` 3 → 6; the 144 total and the 73 routed
entries are unchanged. Commit `1556309`.

**Then the group was deleted.** `src/ipc/handlers/tlsHandlers.ts` is gone — 6 of the 68 passthroughs —
along with its import and call in `src/ipc/handlers.ts`. Three comments that named the file as a live
implementation were corrected (`certLifecycle.ts`, `clientHandlers.ts`, `fileOps.integration.test.ts`), and
`tests/spike/protocolPoc.test.ts` re-points `tls:generate` into the retired-channel fixture (now 5 of 10) —
the fixture's only body that is *not* a bare `invoke()` adapter.

**Criterion corrected:** §5b-decies' risk test was "owns a shell-side `dialog.*`", which is one channel
short. It is now **"owns a step the engine does not perform"**, of which a dialog is only the loud instance.
Recorded as `plan/07` §5b-undecies (the finding + fix) and §5b-duodecies (the deletion), with `plan/13`'s
step-3 progress updated.

**Gate.** `npm run typecheck` ✓, `npm run spike:typecheck` ✓, suite **101 files / 2,500 tests — 2,459 passed,
40 skipped, 1 failed** (`soap.execute`, environmental). Delta 0 for the deletion: a *re-point*, not a
generated-list shrink, because `handlers.test.ts`'s `expectedChannels` never listed these six.

## `git rm` destroyed the working tree, twice

`git rm src/ipc/handlers/tlsHandlers.ts` reported success and deleted **all 22 tracked files under `src/`**.
Reproduced twice; the safe-delete-guard hypothesis was wrong (it happened with `env -u` too). Isolated with
one experiment — restore, then plain `rm` the same file: tree intact (23 → 22). Workaround: **never `git rm`
here; use `rm` + `git add`.** Full entry in `TRAPS.md`. Nothing was lost — `git checkout HEAD -- src/`
restored it both times.

## The reduction's second group — `syncHandlers.ts`, 19 channels, and the first group that cost tests

The largest single file, and the group §5b-decies lists as 19 dead / 0 live. Unlike the `tls` group it needed
no fix first — the widened criterion (*owns a step the engine does not perform*) found no such step in 18 of
the 19. The 19th, `audit:list`, is why the criterion is right rather than a restatement of "owns a dialog":
it was the file's **only** body that was not a `commandRegistry.invoke()` adapter (it called `queryLog`
directly, because §5a kept it un-re-pointed over an ordering dependency). **Deleting the channel dissolves
that concern instead of answering it** — the `audit.list` command is now the only implementation, and the
client's `listAudit` was already its only caller. `audit:export`'s dialog-first shape lives in the client's
`exportAudit` and is asserted there *by order*.

**Delta −5, mechanism named.** `handlers.test.ts`'s `expectedChannels` listed exactly five of the nineteen
(`audit:list`, `audit:diff`, `audit:export`, `history:list`, `history:diff`) and the file generates **one `it`
per entry** → the **generated-list** signature, the opposite of the `tls` group's *re-point* signature
(delta 0) for the same nominal operation. The other fourteen generated nothing (hand-written literals).

**The "failures up" signal fired first, and that is the lesson.** Before the re-point, the five affected
suites read **6 failed / 219 passed**: five *real* failures, because `handlers.test.ts` has
`describe("history:list handler")` (3) and `describe("history:diff handler")` (2) that call
`getHandler("history:list")` / `("history:diff")` **by name** — and a deleted channel is exactly what
`getHandler` looks up. §5b-ter's rule is *re-point, don't delete*, and the idiom already existed in that file:
stage 3b's `entity.*` helpers drive collapsed commands directly. Added `historyList()` / `historyDiff()`
alongside them; the five cases now pin behaviour that lives **only** in the command (`workspaceId` falling
back to the active workspace, `limit`/`offset` defaulting 100/0) — the channel had forwarded its argument
object whole. Had they been deleted instead, the delta would have been −10.

**62 call sites in two integration suites → a harness, not 62 rewrites.** `gitRemote.integration.test.ts`
and `gitSync.integration.test.ts` drove 16 of these channels by name across **62** call sites, and their
subject is real git behaviour. New `tests/integration/deletedChannelHarness.ts` holds the positional →
payload mapping the deleted bodies performed (`channel.replace(":", ".")` is exact for all 16 — checked
against the bodies, not assumed); both suites now read `const invoke = invokeDeletedChannel`. It is
explicitly **not a second contract** — the production mapping is the client's and is asserted in
`client.test.ts`.

**Correction to a rule I had stated too broadly:** §5b-duodecies' "the fixture grows with each slice" is
only true when the spike *drives* the channel. This spike drives ten channels and none is a
`sync.*`/`git.*`/`audit.*`/`history.*` one, so the retired-channel fixture **stays at 5 of 10** — an
`audit:list` entry would be a row nothing ever looks up. The rule is "grows with each *driven* channel".
