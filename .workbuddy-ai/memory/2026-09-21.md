# 2026-09-21 — Bifurc

## The P6 reduction's first handler group, and a live regression found on the way in

Started the reduction (`registerIpcHandlers()`) with `tlsHandlers.ts` — §5b-decies' table lists it as 6 dead /
0 live, so it looked like the easiest place to start. It was the one group that could not be deleted as it
stood.

**The finding.** Asking of each of the six channels *what does this body do that the client twin does not*
gave three answers of "appends a path":

- `tls:generate` appended `certPath: caCertPath()` + `keyPath: caKeyPath()`
- `tls:importCert` appended `path: caCertPath()`
- `tls:importKey` appended `path: caKeyPath()`

The engine deliberately reports no path (`File_Ops_Protocol.md` §8), so those appends were the only source.
The client twins — `tlsGenerate` / `tlsImportCert` / `tlsImportKey` — were routed as plain 1:1 `call(...)`
passthroughs by `8d0b81a` (P6 step 3b-1) and dropped them. `TlsSettingsSection.tsx:36,48,67` guards on
`result.ok && result.path` / `result.certPath && result.keyPath`, so **the Settings panel's Generate and
Import buttons have been silent no-ops since step 3b-1**: the CA lands on disk, `handleGlobalChange` never
runs, `config.tlsCaCertPath` stays null, and the panel keeps saying "not configured". A live regression on a
primary flow, invisible because the *dead* channel was the last correct implementation while the *live* one
was wrong.

**Fixed.** The three keys are `shim`, not `transport`, in `surface.ts` — a 1:1 filing *is* the claim that
nothing happens beyond the call, and that filing licensed the regression. The bodies now read the paths from
the `tlsCertStatus` local hook, so no new channel and no new `ClientLocal` member, and `window.api` is
unchanged in shape. The casts that had silenced the compiler (`as ReturnType<BifurcApi[...]>` on the *built*
object, not just on `call()`'s `unknown`) are gone. Four new assertions on the returned **shape** in
`packages/client/tests/client.test.ts` — nothing in the suite had ever asserted a result shape, which is why
a green suite sat over a broken flow. `transport` 70 → 67, `shim` 3 → 6; the 144 total and the 73 routed
entries are unchanged. Commit `1556309`.

**Then the group was deleted.** `src/ipc/handlers/tlsHandlers.ts` is gone — 6 of the 68 passthroughs —
along with its import and call in `src/ipc/handlers.ts`. Three comments that named the file as a live
implementation were corrected (`certLifecycle.ts`, `clientHandlers.ts`, `fileOps.integration.test.ts`), and
`tests/spike/protocolPoc.test.ts` re-points `tls:generate` into the retired-channel fixture (now 5 of 10) —
the fixture's only body that is *not* a bare `invoke()` adapter.

**Criterion corrected:** §5b-decies' risk test was "owns a shell-side `dialog.*`", which is one channel
short. It is now **"owns a step the engine does not perform"**, of which a dialog is only the loud instance.
Recorded as `plan/07` §5b-undecies (the finding + fix) and §5b-duodecies (the deletion), with `plan/13`'s
step-3 progress updated.

**Gate.** `npm run typecheck` ✓, `npm run spike:typecheck` ✓, suite **101 files / 2,500 tests — 2,459 passed,
40 skipped, 1 failed** (`soap.execute`, environmental). Delta 0 for the deletion: a *re-point*, not a
generated-list shrink, because `handlers.test.ts`'s `expectedChannels` never listed these six.

no fix first — the widened criterion (*owns a step the engine does not perform*) found no such step in 18 of
the 19. The 19th, `audit:list`, is why the criterion is right rather than a restatement of "owns a dialog":
it was the file's **only** body that was not a `commandRegistry.invoke()` adapter (it called `queryLog`
directly, because §5a kept it un-re-pointed over an ordering dependency). **Deleting the channel dissolves
that concern instead of answering it** — the `audit.list` command is now the only implementation, and the
client's `listAudit` was already its only caller. `audit:export`'s dialog-first shape lives in the client's
`exportAudit` and is asserted there *by order*.

**Delta −5, mechanism named.** `handlers.test.ts`'s `expectedChannels` listed exactly five of the nineteen
(`audit:list`, `audit:diff`, `audit:export`, `history:list`, `history:diff`) and the file generates **one `it`
per entry** → the **generated-list** signature, the opposite of the `tls` group's *re-point* signature
(delta 0) for the same nominal operation. The other fourteen generated nothing (hand-written literals).

**The "failures up" signal fired first, and that is the lesson.** Before the re-point, the five affected
suites read **6 failed / 219 passed**: five *real* failures, because `handlers.test.ts` has
`describe("history:list handler")` (3) and `describe("history:diff handler")` (2) that call

back to the active workspace, `limit`/`offset` defaulting 100/0) — the channel had forwarded its argument

**62 call sites in two integration suites → a harness, not 62 rewrites.** `gitRemote.integration.test.ts`
and `gitSync.integration.test.ts` drove 16 of these channels by name across **62** call sites, and their

payload mapping the deleted bodies performed (`channel.replace(":", ".")` is exact for all 16 — checked
against the bodies, not assumed); both suites now read `const invoke = invokeDeletedChannel`. It is
explicitly **not a second contract** — the production mapping is the client's and is asserted in

**Correction to a rule I had stated too broadly:** §5b-duodecies' "the fixture grows with each slice" is
only true when the spike *drives* the channel. This spike drives ten channels and none is a

`audit:list` entry would be a row nothing ever looks up. The rule is "grows with each *driven* channel".

## The reduction's third group — `folderHandlers.ts`, and the §5c guard failed *because the reduction worked*

Four channels, all dead, all one-line delegates — the smallest all-dead file, and the first group the widened
criterion cleared without needing a fix first. `folder.add` / `rename` / `move` / `delete`.

**The apparent regression that is not.** The channel's `folder:add` body was `{ kind, ...folder }` — a
**spread** — while the client's `addFolder` picks `name` and `parentId`. A spread carrying a field the twin
drops is the `tlsGenerate` shape, so it was checked: inert because the *contract* excludes the field
(`renderer/types/window.ts:63` types the argument `Omit<Folder, "id" | "createdAt" | "workspaceId">`), and
`FolderAddParams` is not `.strict()`. **But the equivalence is contract-specific** — the integration suite's
`addFolder()` helper *does* pass `workspaceId: TEST_WS`, so its translation keeps the spread. Getting it wrong
would not have failed loudly: the folder would land in the active workspace, which is `TEST_WS` there anyway,
so the suite would have kept passing while testing something else.

**Delta −3, with a mixed signature.** `expectedChannels` listed three of the four (`folder:move` never was) →
−3; the file's **fourteen** `getHandler("folder:…")` call sites were re-pointed at the commands (a re-point →
0). So a group can be a generated-list shrink *and* a re-point at once — the signature has to be read per
file, not per group. Suite **101 / 2,492 / 2,451 / 40 / 1** (baseline 2,495 / 2,454 / 40 / 1).

**The §5c static guard broke, and the reason is the lesson.** `tests/ipc/handlers.test.ts`'s anti-vacuity
floor was `Object.keys(shell).length > 20` — true while `src/` had 22 `.ts` files. `syncHandlers.ts` took it
to 21; `folderHandlers.ts` to **20**, and the assertion is `> 20`. Six more handler files are still to go
(14 would remain), so it would have failed six more times. **A guard whose floor is a file count fails as the
tree shrinks — and the tree shrinking is the work.** Re-expressed as **presence** (`src/preload.ts`,
`src/ipc/handlers.ts`, `src/ipc/rpcBridge.ts`), normalised for Vite's platform-dependent glob keys. The
engine's floor stays: that tree is not eroding, and the positive control below it independently proves
content loaded.

**The spike fixture grew this time — 5 → 7 of 10.** `protocolPoc` drives `folder:add` and `folder:move`
through the client, so both were re-attached. That is the counterpart to the second group's non-growth and
confirms the corrected rule ("grows with each **driven** channel") in both directions. The spike also had
`registerFolderHandlers()` in its `beforeAll`; removed with the file.

**Also fixed:** `legacyCompanion.ts`'s verification note named `entityCrudFactory.ts` and `folderHandlers.ts`
as its sources — both now deleted — so it points at `store/entityCrudCommands.ts` / `store/folderCommands.ts`.

**Inventory now: 64 literal channels in 7 files = 18 live + 46 dead**, so **46 dead across 6 files** remain:
`coreHandlers.ts` (17), `applicationHandlers.ts` (10), `runnerHandlers.ts` (6), `crudHandlers.ts` (5),
`systemHandlers.ts` (4 dead + `app:checkUpdate`), `importExportHandlers.ts` (4).

**A trap worth recording: `V1_COMPANION_ACTIONS` is not a channel list.** The companion's allowlist and
`packages/protocol`'s `EXTENSION_FROZEN_COMMANDS` both use `kind:verb` strings — `config:get`, `folder:add`,
`mock:add`, `request:add` — that look exactly like IPC channels, so grepping a channel name finds them and
suggests the channel is live. It is a **separate surface with its own dispatch**: `legacyCompanion.ts`'s
`handleAction` switch calls hand-written bodies (`handleFolderAdd` writes config + disk directly), and
`packages/*/src` contains no `ipcMain`/`ipcRenderer` at all. Deleting the folder channels cannot affect it.



## The reduction's fourth group — `crudHandlers.ts` → `crudKinds.ts`, and the first group that cost nothing

Five channels, all dead: `webhook:registerActive`, `webhook:unregisterActive`,
`webhookServer:start|stop|status`. **The first group whose bodies are not `commandRegistry.invoke()`
delegates** — each calls its engine function directly (`registerActiveWebhook`, `startWebhookServer`, …),
which is the shape §5a left them in, so the widened criterion had to be *re-applied* rather than inherited
from the file's neighbours. It cleared all five: the engine half is exact, and `webhookServer.start` is
strictly more capable (it honours an optional `port` the shell body ignored).

**Delta 0 — the third distinct signature in four groups, and not the `tls` one.** The five were never in
`expectedChannels` (no generated `it` to lose) *and* no suite drives them by name (nothing to re-point).
Their behaviour is already asserted at the **command** level (`handlers.test.ts`'s "slice 3": the port chain
`port` → `cfg.webhookPort` → `9101`, and the three-field status shape). So **delta 0 has two causes** —
cases re-pointed (`tls`) or no cases at all (`crud`) — and the number alone cannot separate them.

**The rename is the other half.** §5b-octies had deliberately *kept* the `*Handlers` name on the grounds
that the file registered six kinds **and** five live `webhook*` channels; deleting the five expires the
premise, so it is `crudKinds.ts` / `registerCrudKinds()` now, matching `soapKinds` / `graphqlKinds` /
`grpcKinds`. Blast radius: five call sites. **Four of them also carried a comment saying the call "wires the
*channels* and the per-kind options"** — false in its first half now, and a stale comment on a *renamed*
function is worse than on a deleted one, because it reads as current. Fixed in the same commit.

**Suite: 101 / 2,492 / 2,451 / 40 / 1 — unchanged, as predicted** (the one failure is the standing
`soap.execute` environmental one). `npm run build:packages`, `npm run typecheck` and `npm run spike:typecheck`
all clean. Commit `557d949`. `git ls-files src/` stays at **20** — a rename, not a delete, and git paired the
two (`R` status), so nothing was lost. (Note the contrast with groups 2–3, where the count *drops* by one and
that drop is the integrity check; for a rename the check is the `R` status instead.)

**The spike's fixture did not grow**, the same non-growth as the second group: `protocolPoc` drives ten
channels and none is a webhook one (the file contains no occurrence of "webhook"). The rule is "grows with
each **driven** channel", and it has now been observed in both directions twice.

**Inventory now: 59 literal channels in 6 files = 18 live + 41 dead**, so **41 dead across 5 files** remain:
`coreHandlers.ts` (17), `applicationHandlers.ts` (10), `runnerHandlers.ts` (6), `systemHandlers.ts` (4 dead +
`app:checkUpdate`), `importExportHandlers.ts` (4).

**Next group's first question, and it is the shape this group established.** `systemHandlers.ts` holds four
dead channels of two different kinds: its three `server:*` bodies (`start` / `stop` / `restart`) are
**self-contained** the way these five were — they call `startServer` / `stopServer` directly — so they need

§5b-decies' remaining six, so it is not cleared until the client's dialog-first ordering is confirmed the way
`audit:export`'s was.

**A tooling trap this group produced, now in TRAPS.md: the bulk-edit script was not idempotent.** Its skip
guard was `found_old == 0 and found_new == n`, which never fires for an **append-shaped** edit
(`new = old + extra`) because `old` survives *inside* `new`. Re-running it silently appended a second copy of
§5b-quindecies and of `plan/13`'s progress paragraph — both of which it reported as `ok`. Fixed by testing
`new` only. The lesson generalises: **re-run an "idempotent" script as a check, and grep a marker's
*count*, not its presence.**

## The reduction's fifth group — `systemHandlers.ts` shrinks to one channel, and the "trap" is dissolved

**Four channels gone, the file is not.** `server:start` / `server:stop` / `server:restart` and
`capture:shareJson` left `src/ipc/handlers/systemHandlers.ts`, which now registers exactly **one** channel —
`app:checkUpdate`. That one is **client-local, not legacy** (`packages/protocol` no longer declares
`app.checkUpdate`; `src/preload.ts:87` is its only caller), so the file was never a reduction target and now
**leaves the reduction's scope**. It is the reduction's first *reduction* rather than a whole-file deletion.

**The group held the two shapes the fourth group had named as its first question, and both cleared.** The
three `server:*` bodies were **self-contained** (`loadConfig()` → `stopServer()` / `startServer(cfg.port)`),
not `invoke()` delegates, so §5b-ter's question was asked per channel against `proxy/serverCommands.ts` and
found exact equivalents — the commands take no payload, so the translation is argument-free.
`capture:shareJson` owned the dialog, and its twin is the **opposite case from `audit:export`**:
`shareCaptureJson` is artifact-first *deliberately* (the artifact is a `JSON.stringify` of entries the renderer
already holds; asking first would discard the engine's `suggestedName` as the dialog default). That difference
is now **pinned by a test** rather than asserted in prose — a new case in `packages/client/tests/client.test.ts`
asserts the call order `["capture.shareJson", "writeArtifact:captured-requests.json"]`. The `exportAudit`
lesson applied pre-emptively: a docblock and a call site that disagree is how that bug survived.

**The trap in `serverCommands.ts` is dissolved, not answered.** Its "do NOT re-point the legacy channels at
this module yet" warning was right (a delegating body would acquire a hidden ordering dependency on
`registerIpcHandlers()`, and two suites register handler *groups* without it). Deleting the channels removes
the duplication it protected against, so it retires **with no new coupling at all** — the two suites kept
their registration shape and re-pointed the calls inside their own `invoke`. **"Duplication kept deliberately
to avoid a hidden coupling" is a temporary answer a deletion can retire, and the deletion is cheaper than the
coupling it declines.**

**Delta −8 = −9 deleted + 1 added, and the arithmetic was predicted wrong.** The prediction carried forward
from the fourth group said "three behaviour cases"; the three `describe`s each held **two** `it`s (a `has()`
case and a behaviour case), so it counted *channels*, not *cases*. The mechanism was right, the count was
half. **Suite: 101 / 2,484 / 2,443 / 40 / 1** — the 1 is the standing environmental `soap.execute`, and the
pass count moves by exactly −8.

**The six server cases were deleted, not re-pointed — the first group where §5b-septies' rule cut in the
delete direction.** Each duplicated `expectedChannels`, the registry-coverage block, or the "21 moved
commands" block. The one assertion the latter lacked — `server.restart` starting on `currentConfig.port` —
was **folded into it**. That fold is the difference between deleting a duplicate and deleting coverage, and
it is the check for every remaining group: *move* the residue rather than discarding it with the case.

**Two traps, both recorded in TRAPS.md.** (1) The capture table's first draft reproduced the deleted body's
`(_e, …)` signature — but its branch *replaces* the `fn({}, …args)` call that injected the event, so every
argument shifted by one and `entries` arrived as the suggested filename (`BAD_REQUEST: expected array,
received string`). The convention in both existing tables is caller-positional args, **no event**. (2) The
**dialog-owner risk subset had been 6 in three sections and is actually 3** — a count carried forward without
being re-derived. The sequence is **8 → 5 → 4 → 4 → 4 → 3**: §5b-undecies widened 7 → 8 by adding
`tls:generate`, group 1 took it to 5, group 2 to 4, and this group to 3 (`capture:shareJson`). The error
entered through an *omission* — group 1 never restated the subset, so group 2 computed from two sections back
— and "7 → 6" was arithmetically impossible when written (one deletion from eight cannot leave six). Settled
by `grep -n "dialog\." <the four remaining files>`: exactly three sites in three files.

**Inventory: 55 literal channels in 6 files = 18 live + 37 dead**, so **37 dead in 4 files** remain —
`coreHandlers.ts` (17), `applicationHandlers.ts` (10), `runnerHandlers.ts` (6), `importExportHandlers.ts` (4)
— and **all four are all-dead**, so every remaining group is a whole-file deletion. `clientHandlers.ts` is
still 17 live / 0 dead. The spike's fixture **did not grow** (third non-growth; it drives neither prefix),
