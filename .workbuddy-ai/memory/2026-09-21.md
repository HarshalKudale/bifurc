# 2026-09-21 — Bifurc

## The P6 reduction's first handler group, and a live regression found on the way in

Started the reduction (`registerIpcHandlers()`) with `tlsHandlers.ts` — §5b-decies' table lists it as 6 dead /
0 live, so it looked like the easiest place to start. It was the one group that could not be deleted as it
stood.

**The finding.** Asking of each of the six channels *what does this body do that the client twin does not*
gave three answers of "appends a path":

- `tls:generate` appended `certPath: caCertPath()` + `keyPath: caKeyPath()`
- `tls:importCert` appended `path: caCertPath()`
- `tls:importKey` appended `path: caKeyPath()`

The engine deliberately reports no path (`File_Ops_Protocol.md` §8), so those appends were the only source.
The client twins — `tlsGenerate` / `tlsImportCert` / `tlsImportKey` — were routed as plain 1:1 `call(...)`
passthroughs by `8d0b81a` (P6 step 3b-1) and dropped them. `TlsSettingsSection.tsx:36,48,67` guards on
`result.ok && result.path` / `result.certPath && result.keyPath`, so **the Settings panel's Generate and
Import buttons have been silent no-ops since step 3b-1**: the CA lands on disk, `handleGlobalChange` never
runs, `config.tlsCaCertPath` stays null, and the panel keeps saying "not configured". A live regression on a
primary flow, invisible because the *dead* channel was the last correct implementation while the *live* one
was wrong.

**Fixed.** The three keys are `shim`, not `transport`, in `surface.ts` — a 1:1 filing *is* the claim that
nothing happens beyond the call, and that filing licensed the regression. The bodies now read the paths from
the `tlsCertStatus` local hook, so no new channel and no new `ClientLocal` member, and `window.api` is
unchanged in shape. The casts that had silenced the compiler (`as ReturnType<BifurcApi[...]>` on the *built*
object, not just on `call()`'s `unknown`) are gone. Four new assertions on the returned **shape** in
`packages/client/tests/client.test.ts` — nothing in the suite had ever asserted a result shape, which is why
a green suite sat over a broken flow. `transport` 70 → 67, `shim` 3 → 6; the 144 total and the 73 routed
entries are unchanged. Commit `1556309`.

**Then the group was deleted.** `src/ipc/handlers/tlsHandlers.ts` is gone — 6 of the 68 passthroughs —
along with its import and call in `src/ipc/handlers.ts`. Three comments that named the file as a live
implementation were corrected (`certLifecycle.ts`, `clientHandlers.ts`, `fileOps.integration.test.ts`), and
`tests/spike/protocolPoc.test.ts` re-points `tls:generate` into the retired-channel fixture (now 5 of 10) —
the fixture's only body that is *not* a bare `invoke()` adapter.

**Criterion corrected:** §5b-decies' risk test was "owns a shell-side `dialog.*`", which is one channel
short. It is now **"owns a step the engine does not perform"**, of which a dialog is only the loud instance.
Recorded as `plan/07` §5b-undecies (the finding + fix) and §5b-duodecies (the deletion), with `plan/13`'s
step-3 progress updated.

**Gate.** `npm run typecheck` ✓, `npm run spike:typecheck` ✓, suite **101 files / 2,500 tests — 2,459 passed,
40 skipped, 1 failed** (`soap.execute`, environmental). Delta 0 for the deletion: a *re-point*, not a

## Sixth group — `coreHandlers.ts` → `coreKinds.ts`, 17 channels (commit `0e179bb`)

**The largest group, and the one that found a live bug.** Fixed first (`174a01d`), then deleted.

### The gate is where the group's real work was

The deletion itself was mechanical; **the verification gate is what the group should be remembered for**, and
it ran in three stages because the first two produced failures.

**Stage 1 — the full suite after the deletion: 53 failures, not 0.** Every one was in a suite I had edited
(`foldersAndWorkspaces`, `protocolExecution`, `settingsMutations`, `protocolPoc`) and none in an untouched
suite. That shape is the diagnosis: **an incomplete migration, never a behavioural regression.** The rule that
now belongs in the procedure: *failures confined to the files you touched means the edit set is short, not
that the change is wrong.*

**The substantive finding, which the deletion did not reveal.** Four suites had been getting their command
registrations as a **side effect of the handler files' module scope**. Deleting the channels took the
registrations with them, and the failures were **routed-surface** errors — `No handler registered for command
"request.replay"` / `"workspace.add"` — i.e. the envelope reached the registry and the registry had nothing
to dispatch to. Repairs: `registerServerCommands()` in the spike (`server:status` had been registered by
`systemHandlers.ts`'s module scope, transitive, and the fifth group's deletion of `server:restart/stop/start`
left it intact while the sixth took it), `registerMiscCommands()` + `registerConfigCommands()` in
`protocolExecution`, `registerConfigCommands()` in `foldersAndWorkspaces` and `settingsMutations`.

**The rule:** a command whose only registration came from a handler file the reduction deleted must be wired
explicitly by every suite that drives it. **Compare each suite's `register*Commands()` set against
`src/ipc/handlers.ts` — never against the suite's own history.** The failure message is what makes this a
trap: `No handler registered for "config:save"` names a channel that has been dead since §5c and points the
reader at a file that no longer contains it.

**Two of the failures were mine, not the deletion's, and both misdirect.** `theme:*` / `zoom:*` are **live**
channels in `clientHandlers.ts` (17 live / 0 dead → untouchable, per §5b-decies) that I invented commands for
(`theme.get`, `zoom.set`) — they are shell-local behaviour touching `webContents` and the title-bar overlay,
so the reduction has no claim on them. And `workspace:add` takes **one** argument, the name, with the id
generated by the command; my table mapped `(id, name)`, reproducing the *fifth* group's argument-shift trap
in a new place. Both surfaced as `Invalid payload for command "…": expected string, received undefined` **on a
named field**, which is the fast signal. **Read the call sites to get a positional signature — do not infer
it from the command's parameter list.**

### The delta arithmetic was wrong three ways, and the correction is the durable part

Predicted −41; measured **−25**. All three legs were wrong, and each is a different mistake:

1. **The baseline had moved before the deletion started.** 2,484 was measured at `35ba2ff`, but this group
   opened with a fix-first commit (`174a01d`) that added **two `it()`s to `packages/client/tests/client.test.ts`**
   (`+2 -0`, verified from that commit's own diff). **True baseline 2,486. A group that opens with a fix-first
   commit has a baseline that moves before the deletion begins — re-measure it, never reuse the previous
   group's number.**
2. **`expectedChannels` does not generate one `it` per entry.** It generates them *inside a single `for …
   of` loop*, so the array's length is not a test count. Its contribution was **−5** (7 entries → 2), not
   −14. §5b-septies' "one `it` per entry" describes the loop's shape, not a licence to read file size as
   coverage.
3. **Counting `it(` lines in a diff is not a count either.** 18 removed / 4 added suggests −14; the file's
   real movement was **135 → 110**. Reformatting hides lines and generated cases have no line at all.

**Reconciliation, per-file from vitest output:** `handlers.test.ts` 135 → 110; `foldersAndWorkspaces` 25,
`protocolExecution` 44, `settingsMutations` 30, `protocolPoc` 12 — all unchanged, net 0. **−25**, and
2,486 − 25 = 2,461 exactly. **Gate: 101 files / 2,461 tests / 2,420 passed / 40 skipped / 1 failed** (the
standing environmental `soap.execute`).

**The generalisable rule, now earned three times: when the measured delta and the decomposition disagree, the
decomposition is wrong.** The only trustworthy number is the one a run reports. Note the sign this time — the
error was **+2**, i.e. the measurement was *ahead* of the arithmetic, which is why "reconcile the delta" has to
mean "explain the number the run gave you", not "confirm the number you predicted".

### Folding, and the strongest case of it so far

Five assertions moved into the "21 moved commands" block rather than being discarded with their cases:
`settings.changed` after a save; a **non-empty** `discoverServices` list (the block asserted `toEqual([])`
against a mock returning `[]`, which cannot tell pass-through from replaced-with-empty); `request.replay`'s
returned value (the block asserted only the call slots); and `entity.load`'s acceptance of the protocol kind
names. `workspace.rename`'s not-found case was **strengthened** rather than merely kept: the original asserted
`not.toThrow()`, which an `async` handler satisfies vacuously — it now asserts the config is unchanged.

**`entity.load`'s two re-pointed cases are deliberately weaker than the ones they replace.** The deleted cases

### Repository incident — a real hazard, recorded

While trying to measure the pre-change baseline I ran `git stash push -- tests/` as a probe. **It cost about
an hour and could have cost the group's work.** The repo root resolves to `I:/workspace/Bifurc-Worskspace`
(an empty, commit-less repository created 2026-09-05), **not** to `Bifurc/`, which holds the real repo on
branch `standalone-engine`. The stash command was therefore malformed for its target and interrupted git
mid-operation, leaving `.git/refs` **deleted** and a stale `multi-pack-index` referencing packs that do not
exist. With `refs` gone, git's validity check declares `Bifurc/.git` "not a repository" and discovery climbs
to the empty parent, so every subsequent command silently operated on the wrong repo.

Recovery: recreated `.git/refs/{heads,tags}`; wrote `174a01d` into `.git/refs/heads/standalone-engine` and
`20d2aed` into `master` from `packed-refs`; deleted the stale `multi-pack-index` (the single pack verified
`ok` with `git verify-pack`); removed the index (which referenced a never-written object) and rebuilt it with
`git reset`. `git fsck` is now clean. **The reflog was never damaged** — `.git/logs/refs/heads/standalone-engine`
ended at `174a01d` and confirmed the branch tip. Nothing was lost; all 18 changes were present throughout.

**Lessons, both in TRAPS.md:** (1) **never `git stash` in this repo** — it is the operation that destroyed
`refs`, twice, and there is no reason to use it when `git show HEAD:<path> > /tmp/...` reads an old version
safely. (2) **`git status` reporting a parent directory as the root is the tell** — if `git rev-parse
--show-toplevel` does not return `Bifurc/`, stop and diagnose before running anything that writes.

**P14 WI 7 — THE COMMAND-LAYER HALF, DONE. A workspace-scoped command now reaches the workspace it names.**

**The gap, and why it was the half that mattered.** `createWorkspaceHost()` returns its runtimes as a
`ReadonlyMap` on the handle it hands back, so they were reachable by whoever *called* it and nobody else —
while the commands serve **two** consumers (the host's RPC endpoint and the desktop's IPC) through a
module-level registry neither owns. So `registerServerCommands()` / `registerWebhookCommands()` called the
**module facade**, whose lazy default instance is `workspaceId: null` = the active workspace. WI 1's
protocol half made the ten commands *accept* `workspaceId`; this makes them **read** it. Recorded as
`TRAPS.md`'s "An optional param that is *accepted and ignored* reads as implemented", now with a
**RESOLVED** note.

**Two new modules.** `runtime/runtimeRegistry.ts` — the lookup, plus `resolveRuntimeScope()`. Its
**third branch is the load-bearing one**: a registered runtime for the named workspace → that runtime; no
runtime but the target *is* the active workspace → the **facade** (which genuinely *is* the desktop's
server, so the desktop is unchanged and WI 7's "zero user-visible change" holds); anything else →
**`absent`**, reported as such. Letting the third case fall through to the facade would re-create the
original bug — acting on the active workspace while the caller named another — **with a success code**.
`runtime/runtimeServerOps.ts` — how a resolved runtime's servers are driven.

**A command never allocates a port, and the reason is a measurement.** `proxy/server.ts` seeds
`currentPort = 0`; `webhookServer.ts` seeds it with **`DEFAULT_WEBHOOK_PORT` (9101)**. So a "has it ever
started?" guard written for the proxy **does not transfer** — a never-started webhook reports a *plausible*
port, and re-binding it could take **another workspace's**. The rule that does transfer is
sentinel-independent: `restart` re-binds only a port it has **observed** running; `start` binds only a port
the **caller named**; otherwise report rather than guess.

**Verified — and mutation-checked twice, which is the part worth keeping.** New
`tests/integration/workspaceCommandScope.integration.test.ts` (**8 cases**), `activeWorkspaceId` set to A
with **every discriminating assertion addressing B**, so a command that ignores the parameter fails.
Mutation 1 — disable the runtime branch → **7 of 8 fail**. Mutation 2 — make `absent` fall through to the
facade → **exactly the 2 that should die**, which is the branch whose absence *looks* like it works. A suite
that only mutation-tested the first branch would have shown 7 reds and looked thorough.

**A real catch by an existing test, and the code was wrong rather than the test.** `server.status` gained an
unconditional `workspaceId` echo → `tests/ipc/handlers.test.ts:764` failed, because it pins the payload with
`toEqual` *deliberately* ("two views of the same `isRunning()`, with deliberately different payloads").
**"Additive" and "no user-visible change" are different claims, and only the second was the requirement** —
the field's own doc says it is "echoed so a *multiplexed* client can match response to request", and a
multiplexed client is exactly one that sends an id. So the echo became **conditional**; the desktop's
payload is byte-identical. New `TRAPS.md` section.

**Two more consolidations found while wiring it.** `protocol/commands/webhook.ts` carried its **own** copy of
`WorkspaceScope` instead of importing `./scope` — the drift `./scope`'s header already names as the hazard
that module exists to prevent. Identical, so a consolidation rather than a bug fix; identical-and-separate is
the state that precedes identical-no-longer. And `echoWorkspace` lives in the registry module rather than in
each command file, for the same reason.

**⚠ A REAL regression signal in the full run, identified rather than assumed — and it was not mine.**
`tests/runtime/portAllocator.test.ts` failed on the base-skip regression case (**not** the load pair, so it
had to be checked). Isolated: **21/21 passed.** Mechanism: that suite's `freePort()` helper is
**bind-then-close — the exact TOCTOU shape D16 forbids the allocator from using** — so under a full parallel
run the base can be taken before `tryBind` reaches it, and the allocator *correctly* scans, failing an
assertion about a regression that did not occur. **What exposed it was an unrelated change**: WI 7 added a
suite binding two more ports. **"It was green yesterday" is not evidence about a fixture that races.**
Fixed with a **conditional** retry: the two causes are distinguishable (**the regression leaves the base
free; a race leaves it held**), so the retry runs only while a missed base is genuinely occupied, and a
free-but-skipped base still fails. Proved both directions — re-introducing `reserved.add(proxyBase)` →
**3 tests fail** including both modified ones, so the guard is intact. New `TRAPS.md` section.
