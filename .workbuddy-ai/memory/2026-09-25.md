## The port model is being re-standardized: **every port becomes engine/host level**

Owner directive, 2026-09-25 (a *second* revision, superseding the same day's first). The model to build to:

| Port | Level | Default | Notes |
|---|---|---|---|
| Reverse proxy (edge) | host | **80** | active workspace's mappings + the global web-GUI mapping |
| Forward proxy | **host** (was per workspace) | **8080**, scan +1 | active workspace's **proxy rules + mocks** |
| Webhook | **host** (was per workspace) | 9101 (base kept) | active workspace's webhook endpoints |
| GUI static server | host (image only) | "not easily used by other apps", scan +1 | the edge's default mapping target |
| Companion (RPC WS) | host | **GUI + 1**, non-standard | Electron has no GUI port — companion only |

**Answers from the round of questions, which close two of the four gaps:**

- **Item 5 ("websocket feature port") is OUT OF SCOPE** — the owner said to ignore it. There is no WS
  *listener* in the tree at all (`wsConnections` is an outbound client), so nothing was built for it.
- **The Electron base page keeps the mapping directory** — *no change*. The "Hello world / app is working"
  page was **not** wanted; `buildHomePage` stays as the base domain's answer.
- The GUI static port must be **uncommon and must scan upward** when taken.

**The audit's load-bearing findings** (what this costs — it is a refactor, not a rename):

- **The companion port must be *bound, not scanned*.** A client — the WebGUI, the extension — has to know
  where to connect, so a port that moves cannot be found. This is `plan/15` §3.1's own rule
  (*a port belongs to the thing that has to be addressed once*), and it is why the edge is bound. So the
  GUI may scan but the companion must fail loudly instead, which is also what the owner's *"companion
  changes need a restart"* implies.
- **"Everything else changes without a restart" is new plumbing, not a config rename.** `configCommands.ts`
  today states the opposite in a comment: changing `settings.port` **does not** move the edge, because the
  port the proxy reads belongs to the edge. A live-changeable edge / forward proxy / webhook needs explicit
  stop-and-re-listen paths plus a UI trigger.
- **`portAllocator.ts` loses its subject.** Its whole design is *per workspace*: `preferredProxyPort`,
  `preferredWebhookPort`, and the remembered-port pair in the host-local `runtime.json`. With one allocation
  per host those four fields die, and **D16's stickiness** (*"a workspace that landed on 81 keeps 81"*) has
  to be re-pointed at the host's forward-proxy port or dropped — the browser-proxy argument for it is now
  *stronger*, since one port serves every workspace.
- **A host-level forward proxy must resolve the ACTIVE workspace per request** — the edge's `resolveConfig`
  is the precedent, and it is why `workspace.setActive` needs no invalidation. The forward proxy instead
  caches via `dispatchConfig()`/`reloadConfig()`, so this is the D16 fresh-versus-cached distinction again.
- **⚠ Product consequence, stated rather than implied:** with one host-level webhook and one host-level
  forward proxy, **switching the active workspace changes where a webhook lands and what the proxy
  returns**. There is no longer a per-workspace webhook URL, and mocks/rules follow the active workspace.
- **Electron does not start a companion endpoint at all today** — the extension has nothing to connect to.
- **The image** still needs the GUI bundled, a static server, the default `--gui-target`, and its
  `CMD`/`EXPOSE`/healthcheck moved off `9271`.
- **The gRPC mock port (`grpcMockServerPort`, 9102) is not in the owner's list** — flagged, not changed.
- **Blast radius:** `AppSettings` + `AppConfig` + the 144-key client surface + `packages/gui/src/types/config.ts`
  + `ServerSettingsSection.tsx` (which already carries `port` and `webhookPort` inputs), `runtime.json`, the
  facade `index.ts`, `src/main.ts`, the Dockerfile/compose, and every suite that asserts a port number —
  including the *"the scan lands on `base + N`"* family `TRAPS.md` warns about.

**Status: audited, NOT implemented.** The owner asked for the gap analysis; no code changed for this model.

## The five answers, and the structural discovery that changes the plan

**The owner answered all five, and the answers are now `plan/17`'s model of record:**

1. **The companion/GUI pair scans and never fails.** A base port, walking upward **in pairs** (`n` and `n + 1`
   must both be free). The **extension scans from the same base**, so the base is a **published protocol
   fact**, not an implementation detail.
2. **Electron checks `n` only** — no GUI there, so requiring `n + 1` would refuse a port for a neighbour it
   never uses.
3. **Mocks become REST-only: the gRPC mock AND the SOAP mock both go.** But **Requests keep all four** (REST,
   GraphQL, SOAP, gRPC) — the **gRPC client stays**, because it lives in Requests, not Mocks. Worth stating
   explicitly, because "remove the gRPC mock" is one keystroke from "remove gRPC".
4. **The forward proxy does NOT scan: default 8080, fail if occupied**, naming the port, so the user enters a
   working one. Whatever is in force **stays saved** — the user must always know what their browser is
   pointed at.
5. **The webhook does NOT scan either, and is OFF by default.** The user starts it and owns the port; the
   default is deliberately **random** so it does not collide with a fixed number someone else already wanted.

**⚠ The structural discovery — `WorkspaceRuntime` loses every listener it owns.** It composes exactly two
things, the forward proxy and the webhook receiver, and **both move to the host**. The edge was already
host-level. So **nothing per workspace listens any more**, and `plan/14` D10/D11's *"`WorkspaceRuntime` is the
unit"* has no subject left. What remains per workspace is **config**. That makes the refactor much larger than
"move two servers": it reaches `host.ts`'s loop/registry/status, the **runtime-scope routing** in
`runtimeServerOps`/`serverCommands`/`proxyCommands`/`webhookCommands`, the facade `index.ts`, `src/main.ts`,
`runtime.json`, the Services panel, and every port assertion in the tree. **It also raises a decision that is
not a port question:** delete `WorkspaceRuntime` (the host holds the listeners, the workspace is config) or
hollow it (it survives as a config-scope handle with no `start()`/`stop()`).

**Written down as `plan/17-host-level-ports.md`** — the model, the rules per port, what it replaces, the
structural consequence, the nine ordered work items, three open items, and the verification blocker. `plan/15`
stays the authority on the **edge** and the mapping model; on a *port*, `plan/17` wins.

**The refactor is deliberately NOT started.** It is a large, structural change and **the suite cannot run**, so
it would be unverifiable — which is the one thing this repo's discipline forbids. **`npm ci` is the
unblocking step and it is the owner's call.**

**Final runner evidence, which is what settles the diagnosis:** the probe fails identically **under a minimal
config** (no plugins, no `setupFiles`, no projects, no coverage) — so it is **vitest's installation**, not the
project's config. And `npm ls` fails for **any** package with an npm-internal
`Cannot read properties of null (reading 'edgesOut')`, which points at `node_modules`/lockfile integrity.
Both probe artifacts were deleted; the tree carries no trace.

## `plan/17` work item 7 — runtime rebinding for the edge, forward proxy and webhook (same day, later)

**The note above lists WI 7 as open; this supersedes that line.** WI 7 landed the same evening, and it is the
one item whose *subject* is a behaviour rather than a structure: `plan/17` §1 says only the **companion** needs
a restart, and the other three ports re-bind at runtime. Only the forward proxy did, and it did so on a port
that was no longer its own.

### The mechanism, and why it is an extension rather than a new one

All three `start()` implementations already begin `if (server) stop()` — so **`start(newPort)` *is* the
rebind**, and the fix is entirely about *reachability*:

- **forward proxy** and **webhook** already had module-level facades (`startServer` / `startWebhookServer`),
  so `config.save` could reach them. It read `getPort() || incoming.port` — D16's remembered resolved port,
  which `plan/17` §2 makes dead. It now reads `incoming.forwardProxyPort` outright.
- **the edge had no facade at all.** `proxy/edge.ts` gained `bindEdgeInstance(instance | null)` /
  `restartEdge(port)` / `isEdgeRunning()` — **bound-only, with no lazy default**, because an edge needs a
  `resolveConfig` and there is no honest default for one; a lazily created edge would answer **503 for every
  request**, which is worse than doing nothing because it looks like a bug rather than an unbound handle.

`config.save` is now **three parallel branches**, one per port, each a single call (the explicit
`stopServer(); startServer()` pair was redundant — `start()` stops internally — and removing it is what makes
the three read the same).

### ⚠ The gap that mattered: a composition that does not use the entry point

`bindEdgeInstance` was added to `index.ts` (`createEngine`) and `runtime/host.ts` — and **that was not
enough.** `src/main.ts` is the *desktop's* composition and **never calls `createEngine()`**: it builds the
proxy, the webhook and the edge itself, which is exactly why it already called `bindProxyInstance()` and
`bindWebhookInstance()`. Without the third call there, `restartEdge()` would have been a silent no-op **on the
desktop** — the platform the feature exists for. Found by grepping for the **factory** (`createEdgeRouter`),
not for the entry point; recorded as a trap.

Also: `src/main.ts`'s `before-quit` unbinds, and the binding is made **before** `start()` in all three
compositions, so a save arriving in the boot window finds the instance rather than skipping the re-bind.

### Two cases inverted, and both proved by narrow mutation

`settingsMutations.integration.test.ts`'s block had asserted the *opposite* rule since `plan/15` work item 3
(*"a save does not move the edge"*, with the cost stated in its own comment). Under `plan/17` §1 that
assertion is the bug, so:

- *"keeps the proxy on its resolved port when the port is changed"* → **"moves the EDGE to the new port, and
  leaves the forward proxy where it was"** — now asserting `fetchHello(portB)` **200** *and*
  `waitForPort(portA, false)` (the vacated port is dark, which is the half the old rule could not assert);
- *"still answers on the edge's port after the change, because the edge never moved"* → **"moves the forward
  proxy when `forwardProxyPort` changes, and leaves the edge alone"**.

Both are **discriminating, measured by exit code** — the discipline the project requires:

| Mutation | Result |
|---|---|
| `restartEdge(incoming.port)` commented out | **EXIT=1**, exactly 2 failures: the edge case and `server:restart picks up a port changed while the server was down` (both timing out on `waitForPort(portB, true)`) |
| `incoming.forwardProxyPort !== prev.forwardProxyPort` → `false` | **EXIT=1**, exactly 1 failure: the forward-proxy case |

Each mutation is caught by the case that owns its rule and by no other. **The failing case names matching the
rule is a stronger signal than the count**, and it is why the mutations were run separately.

`tests/ipc/handlers.test.ts`'s `config.save` case was inverted the same way (`restartEdge(9876)` called,
`startServer` / `stopServer` **not**), with the other two ports asserted in the same save's shape, and
`@bifurc/engine/proxy/edge` mocked **with `importOriginal` spread in** — the whole-module-`vi.mock` shape that
cost 10 failures in §4.
