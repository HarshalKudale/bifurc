### Two traps this exposed, both worth reusing

- **Widening a schema invalidates its `invalid` fixtures.** `COMMAND_FIXTURES["runner.saveConfig"]
  .invalid` was `config: {}` — a near-miss only because the old schema required `requestOrder`; an
  empty record is valid under `z.record`. The conformance matrix asserts every fixture's `invalid` is
  rejected, on **all four transports**, so it would have failed for no visible reason. Mutation-checked:
  restoring `config: {}` fails `run-in-process` with "promise resolved `{reached: 'runner.saveConfig'}`
  instead of rejecting". Re-derive, never trust.
- **An integration suite that drives a command by *channel* name cannot see its registry
  implementation.** The legacy `runner:saveConfig`/`loadRunnerConfig` bodies are self-contained
  `ipcMain.handle` duplicates that never consult the registry, so `runnerStorage.integration.test.ts`
  would have passed with the engine half wrong. The conformance suite can't cover it either — its
  matrix deliberately registers `() => ({ reached: cmd })` over every command. **Zero tests in the repo
  reference any engine `register*Commands`**, so this gap applies to all ~24 commands moved in 3b-2 and
  3d, not just these two. Added a registry-level block for the runner pair; the rest is open.

## Environment incident — the whole `src/` tree vanished mid-turn

While doing the §5c slice, **all 24 files under `src/` were deleted from the working tree** between one
successful file edit and the next read (`git status` showed 23 unstaged `D` + 1 staged `D`). No git hook
is active (`ls .git/hooks/ | grep -v .sample` is empty, no husky, no `core.hooksPath`), and the only
command in between was a single `git rm src/ipc/handlers/utils.ts` — so the cause is **not** identified.
Everything else (`packages/`, `tests/`, `renderer/`, `plan/`) was untouched, and all 24 files were
tracked at `HEAD`, so the fix was:

```
git restore --source=HEAD --staged --worktree src/
```

**Consequences and lessons:**
- Uncommitted edits inside `src/` were **lost** and had to be redone. Commit early when touching `src/`.
- `git restore --source=HEAD --staged --worktree <path>` is the recovery — it restores index *and*
  worktree, which also un-stages a `git rm`. Do **not** use plain `git restore <path>` for this: with the
  deletion staged, restoring from the index keeps the file deleted.
- Always confirm the blast radius with `git status --short | grep -c "^ D\|^D "` before restoring, so a
  restore cannot mask a real, intended deletion.

## §5c slice 5 — the ten `application.*` commands (`cd7afad`)

The cleanest slice of the pass: **nothing had to travel.** Every dependency was already in
`packages/engine` (`workspaceFs`'s entity readers, `applications/processSpawner`, `commandGenerator`,
`portUtils`), so the shell file was a pure adapter — `import from the engine` + `register` + `delegate`
— and there was no shell behaviour to lose. **That is the heuristic worth keeping: a slice's difficulty
is not the command count but how much of the body is the shell's own.** Slice 5 (10 commands) was the
easiest; slice 1 (5 commands) the costliest.

`processSpawner` is a module-level **singleton** imported rather than constructed — precisely what
`tsup`'s `bundle: false` protects, since bundling would inline a private copy per entry point and a
spawned child would become unreachable with no error. `generateId` collapsed on the way in: the private
copy was **byte-identical** to `store/config.ts`'s exported one. Unlike `syncEnabledSet`, that helper is
*pure*, so this is hygiene rather than a correctness fix — **collapse a duplicated helper when it is
byte-identical and already exported; escalate only when it holds or writes state that outlives the
process.**

### Two findings, both worth more than the slice itself

**1. The ratchet is blind to the §5c defect but sharp on the §5c *move*.** §5c and §5c-i both say the
ratchet "cannot see" shell-registered commands, and that is true of the defect — a command registered at
module scope in the shell looks registered in this process. But when the first attempt at this slice
lost the `registerApplicationCommands(commandRegistry)` call site,
`tests/ipc/handlers.test.ts`'s *"implements every protocol command except the pinned list"* failed
immediately, listing all ten `application.*` commands as **missing**. So the pass has a safety net after
all, just not the one §5c assumed — the same asymmetry §5c-i noted (an explicit call site is checkable,
a module side effect is not), seen from the other side.

**2. Two `Edit` calls to the same file in one message clobber each other.** Both report success; the
second write wins and silently drops the first change. That is how the call site was lost — the import
landed and the call did not. Nothing warns you, and the failure mode is a *missing* line, so it is
invisible in a skimmed diff. **Edit one file at a time, in separate messages.** Now the first entry
under a new "Tooling" heading in `TRAPS.md`.

child-process spawns with log streaming; `handlers.test.ts` 166/166; full suite at the exact baseline
