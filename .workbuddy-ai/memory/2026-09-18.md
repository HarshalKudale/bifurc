## Two defects found by the third transport — both in the *suite*, not in `ws`

1. **`deliver()` awaited *delivery* but not *subscription establishment*.** `subscribe()` is synchronous,
   so `in-process` and `PassThrough` make a subscription live before the next line and the suite silently
   depended on that. Over a socket a `subscribe` is only *queued* as a control frame — and because
   retention is lazy, an event emitted before anything had subscribed was **dropped, not delayed**. Nine
   `expected [] to have a length of 1` failures on the first `run-ws` run. Fixed by giving `deliver()` an
   **emit callback** so the emit runs *inside* the barrier after a command round trip; ten call sites
   rewritten, and the four pre-existing runners came out byte-identical — the regression signal.
2. **`make()` had to become async-capable** (`Transport | Promise<Transport>`, `harness()` awaits it):
   binding a port is asynchronous and `ws` cannot know its own URL until the OS assigns one.

Also fixed a real production gap found by `ws.test.ts`: `subscribe()` queued its control frame into the
`outbox` but never started the connection, so a **subscriber-only** client would sit with queued frames
forever and its subscription would succeed, never fire and never error.

### Decisions encoded in `socket.ts` rather than documented

- **Access control is the file mode, asserted.** On POSIX `createSocketServer()` does not resolve until
  `chmod 0600` reads back with `mode & 0o077 === 0`; a socket that cannot be made private is **refused**,
  not served. `auth` stays optional (same reasoning as `ws`'s loopback bind).
- **The stale-socket rule.** If the path exists: `lstat().isSocket()` → refuse if not (without this the
  engine would `unlink()` a user's file); probe with a real connect → refuse loudly if live (unlinking a
  live entry would leave the running engine unreachable while a second one took its name); else unlink.
- **`dispose()` uses `destroySoon()`, not `destroy()`** — `destroy()` discards Node's writable buffer,
  and the session's `close()` writes an `unsubscribe` goodbye frame immediately before tearing down.
  `destroySoon()` flushes then releases, and ends the stream so nothing keeps the loop alive. An
  `error` no-op listener is re-added after `removeAllListeners()`, because an `error` event with no
  listener is **thrown** — during teardown, which is the worst moment.
- **`isReady()` requires a real `connect`.** Node *would* buffer a write on a connecting socket, but
  relying on that would make correctness depend on a `net.Socket` implementation detail and would leave
  the session's outbox exercised by `ws` alone.
- **No connect timeout** (a local connect fails fast with `ENOENT`/`EACCES`/`ECONNREFUSED`), **no
  `MAX_FRAME_BYTES` override** (`ws` needed one only because WebSocket carries a *second* limit), and
  **no TCP fallback** (D3's option (a) — a TCP listener would re-open work item 5's bind guards for a
  transport whose whole value is "not network-reachable").
- **One deliberate divergence from `ws`:** a decoder-rejected frame is reported through `onFatal` *and*
  closes that connection. `ws` closes silently because its framing is inside the library and a close
  code is all it has; here the framing is ours, and `oversized_frame` is a peer asking for 4 GiB.

### The honest gap

On **Windows** a named pipe has no mode and no filesystem entry, so every permission assertion in
`socket.ts` is `!isWindows`-guarded and the 5 POSIX-only cases in `socket.test.ts` are `skipIf(win32)` —
they did **not** run here. A named pipe therefore relies on the default DACL of the creating process,
which is the same untested gap the token file has; on Windows `auth` is the only control a named pipe
actually has. Recorded in `plan/05`'s "Deliberately not done" and in `TESTING.md` §4.12.

## Lessons worth keeping (this session)

- **An outbox of already-encoded bytes must never be re-encoded.** The first `opened()` called
  `sendFrame()` on `Buffer`s, and `encodeFrame` does `JSON.stringify` — so the peer would have received
  `{"type":"Buffer","data":[…]}` and rejected it as `not_an_object`, silently losing every queued
  subscription. Caught before running. The reason it hid: the *queue* path and the *flush* path are
  covered by different tests, so neither one alone shows it.
- **`lstat().isSocket()` before `unlink()`.** A path that exists and is not a socket must be refused,
  not removed — the failure mode of the alternative is a user losing a file to an engine start.
- **A fake channel is the only way to test a channel's own contract.** `session.test.ts` encodes through
  the real `framing.ts` codec, so its assertions are about real wire bytes, but it can make a channel
  misbehave on purpose (a `write()` that throws) — which no real transport can.
- **`request()` is async, so its frame is not on the wire when the call returns.** Three of my first
  `session.test.ts` cases failed on this; the fix was a harness helper that waits for the write before
  reading the `id`, not a change to any assertion.
- **Moving a section in a 1000-line doc is not worth the mangling risk** for a marginal ordering gain —
  the socket section sits after the `ws` findings and before the general sections, which reads fine.

## P4 item 3, coalescing half — the backpressure criterion, and the decision that was blocking it

**Landed: `packages/engine/src/transport/eventPump.ts`** (`createEventPump({send, maxBatch?, batchWindowMs?,
schedule?})`), batching `event.log.entry` at **100 entries or 250 ms**. Wired per-session into `stdio`,
`ws` and `socket`; `inProcess.ts` and `auth/authenticated.ts` apply the **shape** only. `VERIFIABLE.
backpressure` flipped to `true`; `stdio`/`ws`/`socket` claim it. Item 3's acceptance criterion is now
`[x]`, taking P4 from **7/10 to 8/10**.

**The half was blocked on a decision, not on work — and the decision was the payload shape.** Coalescing
is invisible to a client *by construction*: it sees the same events whether the engine sent one frame or
a hundred. So no case written against `Transport` can distinguish a coalescing engine from a forwarding
one, and the only other option was a frame counter handed to the suite — a **testing hook in a production
contract**, which the suite's own header rules out in the same words it uses for `barrier()`. What
unblocked it: **`LogEntryBatchEventSchema` (`{entries: LogEntryEvent[]}`) has been in `@bifurc/protocol`
since P1 and never used.** It is the protocol's own statement of what a client receives for
`event.log.entry`, so delivering the batch makes the batching visible *through the interface* and
therefore assertable. A single entry is a batch of one.

**Corollary worth not re-litigating: the batch shape belongs to the protocol, not to the batching.**
`in-process` has no wire and does not coalesce, but still produces `{entries}` — two shapes for one event
name would be worse than either — and an **ungated** conformance case holds every transport to it.

**The projection stopped being cosmetic and became load-bearing.** The bus payload is `RequestLogEntry`
(capture bodies — `reqBody`, `resBody` base64, response capped at 512 KB — plus `host`/`via`/`target`,
timestamp named `ts`); the wire entry is six fields with `timestamp`. One entry is already a large frame;
**a batch of 100 unprojected would be up to ~50 MB in one frame.** Two `LogEntryEvent`-shaped schemas had
sat declared-but-unused since P1; batching is what made both real.

**Three smaller decisions, each with a reason that is easy to undo by accident:**

- **The batch's `seq` is its LAST entry's.** A client's `lastSeq` is the last envelope `seq` it saw and
  the engine replays `seq > lastSeq`; carrying the *first* entry's would put the resume point **inside**
  the batch and replay every entry after the first on every reconnect.
- **An immediate event flushes the pending batch first**, then sends itself, so wire order stays emission
  order — which is what the suite's `deliver()` sentinel barrier depends on.
- **The drop policy is structural, not a mechanism.** `server.error` is never queued (so it cannot be
  displaced) and the pending queue cannot exceed `maxBatch`, because the cap-triggered flush is
  synchronous. Asserted over a 10,000-entry flood rather than argued — and a cap-exact flood turns out to
  arm **no** timer at all, which is stronger than the property I was trying to test.

**Two defects found, both pre-existing, neither in the new code:**

1. **A batch of 100 empty log rows over `ws` and `socket`, with `stdio` green.** `ws` and `socket` compose
   a client-facing `in-process` *inside* their own server, so their pump is **downstream** of something
   that already applied the shape — it projected an already-shaped payload as if it were a raw entry and
   every field fell back to its default. `stdio` was correct throughout (its server subscribes to the bus
   directly), which is exactly why a green `stdio` run did not catch it. Fixed by making `toLogEntryBatch`
   **idempotent** — `isLogEntryBatch` is an unambiguous discriminator because `RequestLogEntry` has no
   `entries` field — rather than by adding a flag to the pump.
2. **The auth decorator synthesises its replay backlog** rather than receiving it from the inner
   transport, so a reconnecting client over `in-process + auth` got the **raw** payload while its live
   entries arrived shaped. Closed by applying `toClientEvent` in that loop.

**Verified:** `npm run typecheck` **EXIT=0**; `tests/transport/eventPump.test.ts` **24/24**; conformance
**275 — 245 passed, 30 skipped, 0 failed** (was 36 skips); conformance + transport **462 — 427 passed, 35
skipped, 0 failed**; full suite **2,325 — 2,289 passed, 1 failed, 35 skipped**, the single failure being

**Recorded rather than fixed — `event.server.error` has no production emitter at all, and its two

Every `bus.emitTyped("server.error", …)` in the repo is a test; the proxy reports bind failure on

### The recording pass, and one tooling hazard worth knowing

Docs brought in step with the code: `plan/README.md`'s P4 row (new segment + counts), `TESTING.md` §4.12
(counts, per-runner skip breakdown, the `eventPump.test.ts` row, and the capability-gating paragraph —

**Hazard: two `Edit` calls issued in the same batch against the same file can race.** A read-modify-write
race silently drops one of them — the call reports success and the change is not on disk. It happened
twice here (a paragraph and a table row in `TESTING.md` both reverted), and the giveaway is that a

### P4 item 4's audit criterion — the plan's premise was false, and the real defect was attribution

Chasing the last unblocked P4 acceptance criterion ("RPC calls appear in the audit log") turned up a
**false premise in `plan/05`**, which says *"The engine already writes an audit log; this is an
extension, not a new system."* Measured against the code:

- **The audit log is derived from git; nothing writes audit rows.** `queryLog()`
  (`packages/engine/src/store/gitStore.ts:132`) walks the commit history and **parses commit bodies** for
  `entity-id:`/`workspace-id:`/`actor:` (line 152). Every `AuditEntry` needs a `commitHash`, `entity`,
  `entityId` and `entityName`. An RPC call is not a commit and has no entity, so recording one there
  means **fabricating all four fields** — and `audit.diff` would then be offered on rows where
  `getEntityAtCommit()` cannot work.
- **`commitMutation` (gitStore.ts:73) has no production caller.** It is the only function that accepts an
  `actor`, and every reference is a test (`tests/store/gitStore.test.ts`,
  `tests/integration/{auditLog,fileOps}.integration.test.ts`, `vi.fn()`s in `tests/ipc/handlers.test.ts`
  and `tests/spike/protocolPoc.test.ts`). Real entries come from the sync path — `entityCrudFactory` →
  `syncChanges()` → `publishService`'s `g.commit(fullMessage)` — with **`actor = opts.actor ?? deviceName()`**
  (line 83).
- **So the real defect was mis-attribution:** with nothing carrying a session into `CommandContext`, **a
  mutation arriving over a transport was logged as the engine's own machine name**, indistinguishable
  from a local edit. `HelloRequestSchema` had declared `clientName`/`clientVersion` since P1 (*"Recorded
  per session so the engine can log and diagnose which build is connected"*) and **nothing recorded
  them** — a second declared-but-unused protocol field, and this time the field was the spec for the fix.

Surfaced the finding and asked rather than guessing (the criterion is stated two ways — `plan/05`'s
five-field per-call record vs `plan/12`'s "every mutating command recorded"); the user chose **session
attribution**.

**Implemented — the attribution half.** `SessionIdentity` + optional `CommandContext.session` in
`packages/engine/src/commands/registry.ts`; `onSession?: (identity) => void` on
`createAuthenticatedTransport`, the counterpart of `onAuthFailure`, firing **exactly once** and **never on
a rejected handshake**, placed **after** `scopesFor` (caller-supplied, may throw; a recorded session that
never opened is worse than a missing one). `ws.ts` and `socket.ts` now build a **per-session** context
inside the connection handler instead of closing over one template at server construction; only `ws` sets
`peer`, because a unix socket's path names the engine's *own* endpoint and putting it in a field called
`peer` would be a fiction. `in-process`/`stdio` see **no session at all** — inventing one puts a fiction
in the log.

**The trap that cost time:** the decorator learns the session id *during* the handshake, **after** the
inner transport has captured its `ctx` — so the runner must hand the **same context object** to both
halves (`createInProcessTransport(..., { ctx })` **and** `onSession` mutating that object). Build two and
the identity lands on the one nobody invokes. Documented in `run-authenticated.test.ts`'s header.

**Tests:** `auth.test.ts` 51 → 59 (a new "the session identity" describe: reports id/name/version once;
reports *nothing* for a wrong token, a major mismatch, a malformed hello, a pre-handshake command, or a

two new shared-suite cases — `handshakeIt` "tells a handler which session invoked it" and the new
**`noHandshakeIt`** inverse ("gives a handler no session, because nothing established one"), where the

**Negative control** (the repo's convention for a suite change): neutering `ws.ts`'s `onSession` to a

**Verified:** `npm run typecheck` → **EXIT=0** (build:packages → protocol → engine → root);

## P4 item 1 — the frozen-API migration: the decision, and the privilege it turned out to be

**Task.** Item 1's acceptance criterion ("the *released* companion extension still works against the new
server") had been blocked on a decision since the phase began. Reconnaissance first, because the criterion
as written looked like a compatibility chore and turned out to be a security question.

**The reconnaissance finding: `onAddConflict` is a privilege, not a detail.** `createEntityCore`'s
`onAddConflict` hook — and `entity.setEnabled`'s equivalent inline loop — **scan the config and disable
other entities matching a signature** (`method|urlPattern|capturedBody` for mocks, `useRegex|pattern` for
rules). Those are entities the **caller never named**. `entity.update` is `write` because it mutates an
entity the caller identified; this mutates ones it did not. So aliasing the companion's four frozen
actions onto `entity.create`/`folder.add`/`config.get` would have formally dropped the additive-only
guarantee: a page in the user's browser could switch off the user's mock.

**Three routes, and the one taken.** (1) alias and inherit `onAddConflict` — drops the guarantee;
(2) register the four names as their own commands — every v1 guarantee preserved by construction, at the
cost of the engine carrying a second spelling of each operation forever; (3) **alias, and gate the conflict
resolution on `admin`** — one implementation, guarantee enforced by the existing total scope table rather
than by a rule written for the extension. **The user chose route 3.**

Route 3 works because of what the two callers already *are*: `COMPANION_SCOPES` is `{read, write}` and
`SHELL_SCOPES` is all four, so "may this caller affect entities it did not name?" has a different answer
for each **without the extension being named anywhere in the code**. `admin` and not `write`, because
`write` would let the companion switch off mocks.

**The rule, stated once.** *A command may only affect entities the caller names.* Expressed as a named
predicate rather than a bare scope check at each site, because the two sites must agree:
`mayAffectUnnamedEntities(ctx)` = `callerHasScope(ctx, "admin")`.

**Where the vocabulary had to live.** `Scope` moved from `transport/auth/scopes.ts` to
`commands/registry.ts` and is **re-exported** back. It had to move: `transport/` imports `commands/` and
never the reverse (all four transports import `CommandContext` from the registry), and a handler needs the
vocabulary to read `ctx.session.scopes` — so it belongs on the lower side. Re-exporting keeps `./scopes` the
single import for both vocabulary and table. **No protocol change was needed.**

**Fail-closed, and the session-less rule.** `callerHasScope()`: no session ⇒ the engine's own caller ⇒
every scope (true); session present but `scopes` absent ⇒ **false**. The second half matters: otherwise
forgetting to report scopes would silently grant them. `in-process`, `stdio` and every legacy
`ipcMain.handle` adapter pass a session-less context, so the shell's own behaviour is unchanged.

**Files changed.** `packages/engine/src/commands/registry.ts` (`Scope`, `SessionIdentity.scopes`,
`callerHasScope`, `mayAffectUnnamedEntities`); `transport/auth/scopes.ts` (re-export);
`transport/auth/authenticated.ts` (`onSession` now reports `scopes` alongside the identity);
`src/ipc/handlers/entityCrudFactory.ts` (`createEntityCore` gained a **required** third parameter
`mayResolveConflicts`); `src/ipc/handlers/coreHandlers.ts` (`entity.setEnabled`'s handler takes `ctx`; both
inline conflict loops gained `&& mayResolveConflicts` — the toggle itself stays **unconditional**, because
gating the whole handler would stop a companion turning a mock *on*, which it is entitled to do).

**The bug the integration test found — `onAddConflict` never persisted anything.** Writing the test against
a **real** workspace and reading **real disk** through `loadConfig()` is what surfaced it. `onAddConflict`
disables siblings by mutating `cfg`, and `createEntityCore` then calls `saveConfig(cfg)` — which reads like
it persists. It does not: `writeEntity()` **strips `enabled` on the way out** (`workspaceFs.ts:125/131`),
because enabled state lives **exclusively in `enabled.json`**, and `saveConfig` never writes the enabled
set. So the disable landed on an in-memory object that was then thrown away; the sibling stayed enabled on
disk, and — because `createEntityCore` had already `unshift`ed the new entity, so it still won routing —
the only visible consequence was that **deleting the new entity silently switched the old one back on**.
`entity.setEnabled`'s equivalent loop has **always** written through `syncEnabledSet`, so the two sites
disagreed about the same rule. `tests/ipc/handlers.test.ts`'s equivalent case could not see it because it
asserts on a mocked in-memory config — precisely the shape of the bug. **Fixed** by diffing the `enabled`
flag across the `onAddConflict` call and writing the differences through `syncEnabledSet`.

This is a **shell-visible behaviour change** and is flagged as such in `plan/05`: creating a duplicate mock
now really does disable the old one, which is what `legacyCompanion.ts`'s comparison table has always
claimed. It is also what makes the gate on that path mean anything — a gate guarding a no-op is a false
assurance. `legacyCompanion.ts`'s own `handleMockAdd` is untouched: it has its own body, its own
`syncEnabledSet` for its own id, and never reaches `createEntityCore`, so the v1 endpoint is unchanged.

**Tests.** `packages/engine/tests/commands/registry.test.ts` (**10**, new) tests the predicate: engine
caller gets every scope; a session answers from its own scopes; **no hierarchy** (`admin` alone does not
imply `read`); a session with no scopes is refused. `tests/integration/entityConflictScope.integration.test.ts`
(**9**, new, three of them `it.each` rows) runs against a real workspace and real `loadConfig()`: the
incoming mock is always stored in all three contexts; the sibling is disabled for the engine's caller *and*
for a shell session; it **stays enabled for the companion** (the additive-only guarantee); the gate is
inert for a kind with no conflict rule (`mappings`); and `entity.setEnabled` disables the sibling for the
engine but not the companion. `transport/auth.test.ts` **59 → 60** — the strict `toEqual` on the session
payload became `toMatchObject` plus an explicit `expect(seen[0].scopes).toEqual(SHELL_SCOPES)`, and a new
case asserts that `onSession` reports the scopes the gate will **actually** enforce when `scopesFor`
narrows them (`COMPANION_SCOPES`).

Two things about that integration test cost real time and are worth remembering: `createEntityCore()`
**regenerates the entity id** (`{...entity, id: generateId()}`), so locate entities by `name`, never by the
id you passed; and `environments` is registered by `registerCoreHandlers()`, not `registerCrudHandlers()`,
so a flat-entity case must use `mappings`.

**Verified.** `npm run typecheck` **EXIT=0** (build:packages → protocol → engine → root). The item-1 gate
re-run green: `registry.test.ts` 10 + `auth.test.ts` 60 + `entityConflictScope` 9 = **79 passed, 0 failed**
(3 files, 1.91s). Full suite after the change: **92 files, 2,364 tests — 2,323 passed, 1 failed, 40
skipped**, the sole failure being the documented `soap.execute` dead-endpoint flake. That is exactly the
predicted +20 (auth +1, `registry.test.ts` +10, `entityConflictScope` +9) over the previous 2,344, so the
change introduced no regression anywhere.

**Negative control.** Neutering `callerHasScope()` to always return `true` failed **exactly 9** cases — all
of them authority cases — with **10 passing**, and the two that correctly still passed are the engine-caller
case and the shell-holds-`admin` case, which is the right signature: the predicate is load-bearing, and it
is load-bearing *only* where authority differs. Restored, re-run green, and confirmed by grep that the
restored body is on disk.

**What is still open, and why the criterion stays unchecked.** The four-name aliasing itself has **not**
been implemented — only the security decision and the gate that unblocks it. The criterion is gated on the
**extension's release cycle**: the published extension is v1.0.0, sends no `hello` and interpolates
`resp.error` as a string, so against the auth-wrapped server it gets `UNAUTHORIZED` and the connection
closes. The only ways to satisfy it are an extension release that speaks v2 (which makes the *released*
extension the v2 one) or a v1-compat mode on the new server, which would break item 5's "never fall back to
unauthenticated". So `legacyCompanion.ts` stays byte-compatible on 9271 until then, and **two WebSocket
servers in one process** remains a documented transitional state rather than a design. The other three
v1-vs-registry differences (two validation-message suffixes, a missing blank-folder-name guard, and a
`TypeError` vs `"Unknown folder kind: …"`) are compatibility work rather than decisions.

## P5 started — the typed RPC client, and four findings from verifying its preconditions

**Why P5 and not more P4.** P4 stands at 8/10, and both open criteria are externally gated or
decision-shaped (item 1 on the extension's release cycle; item 4's record on a granularity call).
P5's own preconditions, read from `plan/06` and then verified from code, are all met: conformance green
on all four transports, `ws` auth implemented, and `renderer/types/window.ts` present. P5 blocks P6 —
the ship milestone — so it is the critical path. P4's leftovers do not gate it.

**Finding 1 — the plan's surface numbers are stale, and the discrepancy is load-bearing.**
`plan/06` says "136 methods" (129 request/response + 7 subscription) and names the type as the
authoritative list. Measured: `src/preload.ts` exposes **144** keys; `renderer/types/window.ts` declares
**140** (139 methods + the `platform` property). So the type **under-declares the runtime by four keys**:
`isFirstLaunch`, `completeFirstLaunch`, `getZoomLevel`, `setZoomLevel` — all exposed by the preload and
implemented in `src/ipc/handlers/clientHandlers.ts`, none declared in `BifurcApi`. A client built to
satisfy *the type* would pass the type-level shape check, pass a key-diff script if that script also
used the type, and still have silently dropped four keys off the runtime surface. **The runtime is the
authority; the type is a secondary check.** (Nothing reads those four today — verified repo-wide — but
"nothing reads it today" is not "safe to drop", so they are classified rather than omitted.)

**Finding 2 — the 7 subscriptions all map to real wire events, including the one that looks like it
cannot.** Six map 1:1. `onCompanionRefresh` looked like a gap — its IPC channel is `companion:refresh`
and there is no `event.companion.*` in `EVENT_NAMES`. It is not a gap: the protocol's own comment
records the rename ("`companion:refresh` becomes `entity.changed`"), and `src/ipc/eventBridge.ts:36`
deliberately **degrades** the richer bus event back to the bare signal for the renderer. So the client
subscribes to `event.entity.changed` and **discards the payload** — a shim in disguise. Three wire
events (`entity.changed`, `process.output`, `settings.changed`) have **no** `window.api` method; the
client should still expose the ability to subscribe, but there is no named method for them.

**Finding 3 — the protocol's `retryable` is necessary but not sufficient.** `isRetryable(code)` is
code-based only (`UPSTREAM_FAILED`, `TIMEOUT`, `ENGINE_ERROR`). It cannot see *which command* failed,
and the two questions are independent: a `TIMEOUT` on `server.status` is safe to retry, a `TIMEOUT` on
`entity.create` is **not** — a timeout means *we do not know whether the mutation landed*, and the
duplicate is not hypothetical (the engine has already `unshift`ed the new entity and won routing for
it). The effective policy is `isRetryable(code) && isIdempotent(command)`, and the second half is new.
The failure mode is asymmetric, so the default for an unlisted command is **not retryable**: wrongly
retryable gives a duplicated mutation visible only to the user later; wrongly non-retryable gives a
slightly worse UX. `assertRetryPolicyIsTotal()` makes the two sets partition `COMMANDS` exactly, so a
new command forces the decision where it is added.

**Finding 4 — the P0 spike already proved the shape pattern, for 10 methods.** `spike/protocol/shape.ts`
asserts `BifurcApi` and a `ProtocolClient` are **mutually assignable** over a `Pick<>` of 10 methods, via
the same type-only import across the package boundary that P5 needs — and it is marked "SPIKE CODE —
throwaway, do not productionise". So work item 4 is the productionised version of a pattern already
validated in this repo, and the cross-boundary import is precedented. Note `src/ipc/importExportHandlers.ts:59`
records the opposite convention for `src/` ("`src/` does not import from `renderer/`") — the client
package sits with `spike/` on the type-only side of that line.

### `createClient` and the enumerable-`close` defect

`src/index.ts` implements all **144** methods as typed one-liners whose command comes from `SURFACE`
via `commandFor(key)`. The object literal is annotated `const api: BifurcClient`, so **the compiler is
the shape test**. Two TS errors found while writing it, both worth remembering:
- `Parameters<BifurcApi["onLogEntry"]>[0]` yields the **callback**, not the entry → needs the doubled
  form `Parameters<Parameters<BifurcApi["onLogEntry"]>[0]>[0]`.
- Annotating the literal `BifurcApiFull` fails with `TS2741: Property 'close' is missing` → annotate
  `BifurcClient`.

**The key-diff test found a real defect on its first run.** `close()` was enumerable, so
`Object.keys(client)` returned **145** against the preload's 144. Fix: keep `close` in the literal (so
no cast and the compiler stays the shape test), then
`Object.defineProperty(api, "close", { enumerable: false })` — passing **only** `enumerable` leaves
`value`/`writable`/`configurable` intact for an existing property, per spec. This matters because the
plan's own regression instrument *is* `Object.keys`, which enumerates **enumerable own** properties —
so the plan's choice of instrument defines the surface. The shell can still call `close()` because
`contextBridge.exposeInMainWorld` copies only enumerable own properties.

### The seven-key gap — the finding this phase was worth running for

`renderer/types/window.ts` declares **140** of the **144** runtime keys, disagreeing with

- **omits four** — `isFirstLaunch`, `completeFirstLaunch`, `getZoomLevel`, `setZoomLevel`;

Fix: `BifurcApiFull = BifurcApi & { [K in OptionalInDeclaredType]-?: NonNullable<BifurcApi[K]> } & {four added}`.
The mapped type reads the signatures **out of `BifurcApi`** so they cannot drift; `OptionalInDeclaredType`
is exported because `shape.test-d.ts` must exclude exactly that set from its direction-2 check.

### Work item 5 — the retry policy needed a **third** term

Two findings, both real:

1. **`retry.ts` was dead code.** Complete, tested, and **never imported** by `index.ts`. A policy
   nothing calls passes every test in isolation and retries nothing in production. Now every request
   goes through one `withRetry` — including the two **internal** calls that are not surface methods
   (`config.get` for the three `list*` methods, `blob.read` for artifact egress). `blob.put`/
   `blob.release` were routed through too, so the non-idempotent one is now *protected* rather than
   merely not-retried.
2. **`isSafeToRetry` alone hammers a dead transport.** All four transports reject a request on a
   **closed** transport with `ENGINE_ERROR` — `inProcess.ts`'s `assertOpen`, `stdio.ts`'s `teardown`,
   `ws.ts`'s, `socket.ts`'s — and the protocol's `RETRYABLE_CODES` **includes** `ENGINE_ERROR`. So the
   two-term policy makes three attempts over 150ms against a transport it knows is gone, contradicting
   `plan/06`'s own "connection loss: reject with a typed error; **the caller decides whether to
   retry**". Guard: a `closed` flag set by `close()` (before the await, so an in-flight retry loop
   stops racing teardown). **The real fix is a distinct non-retryable code** for a closed transport —
   a protocol change plus 7 call sites across 4 transports — which belongs with P4 item 5. Recorded,
   not done.

`withRetry` also refuses to retry anything that is not an `EngineError`. That is exact rather than a
duck-type guess: `inProcess` throws `EngineError` directly and `stdio`/`ws`/`socket` rebuild one via
`remoteErrorToEngineError`. Backoff is injectable (`retry.sleep`) so tests record instead of sleeping.

### The three-transport criterion

`tests/transports.test.ts` — one case per transport, all three running the **same** `assertTheClientWorks`
body (the failure mode guarded against is "the `ws` case asserts less and nobody notices"). Each drives
`serverStatus`, `getConfig`, `listWsdls` (two round trips — `config.get` **and** `entity.list`), and
`addMock`. Harness patterns reused from the engine's conformance runners:
`new CommandRegistry()` / `new EngineEventBus()` / `new EventLog({bus})`; `stdio` = a `PassThrough` pair
(no child process, same `framing.ts`); `ws` = `createWsServer({registry,bus,log,auth})` → `server.url`
→ `createWsTransport(url)`.

**`ws` is the only one built with `auth`, and the handshake is a plain `request("hello", …)` on the raw
transport *before* `createClient()`** — so the client never learns it is remote, which is what P6 needs.
**Negative control:** removing the handshake fails the `ws` case with `UNAUTHORIZED` while the other two
stay green — so the gate is genuinely exercised.

### The two blocking findings (recorded in `plan/07`)

Neither is visible from `plan/07`'s text; both were established by reading the code.

1. **`log.entry` / `log.chunk` / `server.error` never reach the bus.** `EngineEvents` declares all three,
   `ENGINE_EVENT_NAMES` lists them, `BUS_NAME_BY_WIRE_NAME` maps them and `assertBridgeIsTotal()` asserts
   them at import — but **nothing emits them on the bus**. They travel only through `logEmitter`, and
   `src/ipc/eventBridge.ts` (the file P6 deletes) subscribes to `logEmitter` **directly**.
   `handlers.ts:44–46` says so outright. So a transport-only P6 silently kills `onLogEntry`, `onLogChunk`
   and `onServerError` — the capture panel, the request-log panel and the server-error banner — and every
   unit test stays green because they test the *mapping*, not the *traffic*.
   The fix belongs in the engine, alongside `emitEntityStatus()`'s precedent, and **must reach
   `registerIpcHandlers()`, not just `createEngine()`** — the shell uses the module singletons and never
   calls `createEngine()`.

2. **`ipcMain.handle` → `ipcRenderer.invoke` drops `err.code`.** A rejection arrives as a plain `Error`
   with a flattened message, and `packages/client/src/retry.ts` decides whether to retry from
   `isRetryable(err.code)` — the entire three-term policy. The bridge must therefore return a
   **discriminated result** (`{ok:true,value} | {ok:false,error:RpcError}`) and let the renderer rebuild
   the error. `toRpcError` (main) and `remoteErrorToEngineError` (renderer) already exist in
   `packages/engine/src/transport/types.ts` and are exactly the two halves needed.

Two smaller ones, also written into `plan/07`:

3. **`TransportKind` has no `"ipc"` member.** Nothing switches on the union — the only read is
   `auth.test.ts:712` and `session.ts:91` merely stores it — so adding `"ipc"` is safe and is one line.
   Labelling the bridge `"in-process"` would be a lie.
4. **Work item 2 is larger than the phase's framing.** The phase reads as wiring, but spawning the engine
   binary replaces the process model. The plan's own step 2 is the correct first cut: keep the engine
   in-process, bridge over `createInProcessTransport(commandRegistry, {bus})`, prove the seam, and let the
   process split be a change of transport *behind* a proven seam. That ordering is also what keeps
   `BIFURC_ENGINE_RPC=0` meaningful.

### The e2e baseline is unreachable from the agent shell — and it is NOT the app

**46 failed, 0 passed.** Every test died in ~850 ms with
`electronApplication.firstWindow: Target page, context or browser has been closed` — i.e. the app exits
at startup, so no window is ever created.

The cause, found by launching Electron by hand with the fixture's env:

```
FATAL:content\browser\gpu\gpu_data_manager_impl_private.cc:417]
GPU process isn't usable. Goodbye.        → exit code 3
```

Electron 42 cannot start a GPU process when spawned from this agent shell, and **hard-exits**. Four
experiments, and the third is the one that settles it:

| Attempt | Result |
|---|---|
| raw `electron.exe .` from the agent shell | GPU fatal, exit 3 |
| same, `dangerouslyDisableSandbox: true` | GPU fatal, exit 3 — **the sandbox flag is not the cause** |
| **a minimal 5-line Electron app** from the agent shell | `MINI-READY` printed, then GPU fatal, exit 3 |
| `npm run dev` from the *user's* terminal | **works** |

**A minimal Electron app with zero Bifurc code fails identically**, so the app is not affected and the
machine has two healthy adapters (`AMD Radeon(TM) Graphics`, `NVIDIA GeForce RTX 4080 SUPER`, both
`Status: OK`). The distinguishing factor is the **process context of the agent shell** — turning the
sandbox off does not change the parent's desktop/session context, which is what Chromium's GPU process
actually needs.

**Consequences, and they are durable:**

- **Do not try to launch Electron (or `npm run test:e2e`) from the agent shell.** It will fail with a
  GPU fatal that looks like an app bug and is not one. The user runs it from their own terminal.
- **`npm run dev` working is the standing proof the app is fine.** `dev` is `npm run build && electron .`
  — the same binary and the same `dist/main.js` the e2e harness uses.
- **No launch flags are needed, ever, including in a packaged build.** The two switches already in
  `main.ts` (`disable-gpu-shader-disk-cache`, `disable-gpu`) predate this and are unrelated hardening.
- **`timeout <n> ./electron.exe …` is a trap for a second reason**: coreutils' `timeout` parses the
  Chromium switches as *its own* options and dies with `bad option: --no-sandbox`. Chromium switches must
  go after the app path, which is where Electron's own arg handling forwards them.
- A **shell function** wrapping the launch produced a *different* failure
  (`TypeError: Cannot read properties of undefined (reading 'commandLine')` = `require("electron")`
  returning a path string, i.e. Node mode). Same shape of command, different error — so when probing
  Electron startup, run each candidate as a **plain sequential command**, never inside a function.

**P6's e2e acceptance criterion therefore has to be run by the user**, or on a machine where the shell
can host a GUI process. The unit suite is unaffected and remains the gate for P6 step 2.

### The user found the *real* e2e blocker: the TOS gate — and the fix is not in `sampleData.ts`

I was wrong to keep pushing on the launch angle. The user ran `npm run test:e2e` in their own terminal
and the app **does** start there — it just lands on the **Terms of Service acceptance screen** on a
fresh data dir, so no test can reach the UI.

**The trap, and it is a good one:** `renderer/App.tsx:23` gates the whole shell on

```ts
const [tosAccepted, setTosAccepted] = usePersistedState<boolean>("app:tos-accepted", false);
if (!tosAccepted) return <TermsAcceptanceScreen onAccept={() => setTosAccepted(true)} />;
```

and `usePersistedState` is backed by plain **`localStorage`** (`renderer/lib/storage.ts` — `getItem`/
`setItem`, JSON-encoded). So the flag is **per-profile renderer state, not `app.json`**. The fixture's
fresh `--user-data-dir` per test means `localStorage` is always empty.

**`sampleData.ts` already writes `hasSeenWelcome: true`** (line 367) — and that is *correct but
irrelevant*: it drives `app:isFirstLaunch`, a **different** gate. So "just add it to the sample data",
which is the obvious move, would have changed nothing. Worth remembering: in this codebase
`app.json` settings and `localStorage` UI state are two separate persistence layers, and the fixture
only seeds the first.

**Fix applied — `e2e/fixtures/electronApp.ts`'s `page` fixture:**

```ts
await window.addInitScript(() => {
    try { localStorage.setItem("app:tos-accepted", "true"); } catch { /* ... */ }
});
await window.reload();
```

- The **`reload()` is load-bearing**: `addInitScript` only applies to the *next* navigation, so the key
  must be seeded before `App.tsx` reads it.
- The value is the **JSON-encoded** string `"true"`, because `readStorage` does `JSON.parse` and
  `JSON.parse("true")` is the boolean the hook wants.
- It lives in the **fixture**, not `sampleData.ts` — `plan/07` work item 5 allows harness changes and
  requires the specs to stay unmodified.
- It must **not** be solved by making the renderer read `app.json` for the TOS flag: `plan/07` forbids
  renderer edits in P1–P6, and the risks table rates "someone edits the renderer just to make it work"
  as **High** likelihood. That would have been the tempting wrong fix.

`npx tsc -p e2e/tsconfig.json --noEmit` → **TSC_EXIT=0**. The fix is **unverified at runtime** — the
agent shell cannot start Electron, so `firstWindow()` never resolves here. The user runs it.

**Also settled this session:** `dangerouslyDisableSandbox: true` on a full `npx playwright test` run gave
the **same 46 failed / EXIT=1**. The sandbox flag was never the variable — so the agent-shell Electron
limitation and the user's TOS failure are two genuinely separate problems, and only the second one was
blocking the suite.

### The TOS fix worked — and the next failure was a spec asserting a control that isn't on screen

The user confirmed the suite now runs and reaches the UI, with a handful of genuine failures. The
representative one is `app.spec.ts`'s **"can open the environments manager"**:

```ts
await page.getByRole("button", { name: /^Manage Environments/i }).first().click();
```

**There is no such button in the titlebar.** The env manager is reached through the environment
**dropdown**: `TitleBar.tsx:152–167` renders `<EnvSelector>`, and `EnvSelector.tsx` shows the toggle
(titled `strings.titleBar.switchEnvironment` = `"Switch environment"`, whose *accessible name* is the
**active environment's name**, so it changes with seeded data) and renders the
`"Manage Environments…"` item **only inside the menu that opens on click** — `EnvSelector.tsx:77–84`,
`strings.titleBar.manageEnvironments`.

The spec's *assertion* was fine, though: `EnvironmentsPanel.tsx:140–142` really does render a
`New Environment` button (`strings.environments.newEnvironment`), in the sidebar footer. Only the
**entry point** was wrong.

**Fix — a new `openEnvironmentsManager(page)` helper in `e2e/helpers/index.ts`**, used by the spec:

```ts
const toggle = page.getByTitle("Switch environment").first();
await expect(toggle).toBeVisible({ timeout: 15_000 });
await toggle.click();
const manage = page.getByRole("button", { name: /Manage Environments/i }).first();
await expect(manage).toBeVisible({ timeout: 10_000 });
await manage.click();
```

Two deliberate choices:
- **`getByTitle`, not `getByRole(..., { name })`** — the toggle's accessible name is the active
  environment's name ("Development" with the seeded data), which is data-dependent; `title` is stable.
- **It lives in the helper, not inline** — so a renamed menu item fails *there*, with a readable
  assertion, instead of surfacing as a mysterious timeout inside whichever test called it.

**The renderer is NOT edited.** The user's instinct was to add a titlebar button; that is a renderer
change, which the rule at the top of `plan/07` forbids in P1–P6, so the test was updated to match the
UI as it actually is. The button can be added once the programme finishes. The temptation to "just add
the button" is precisely the **High**-likelihood risk in `plan/07`'s table.

`npx tsc -p e2e/tsconfig.json --noEmit` → **TSC_EXIT=0**.

**Also fixed: `e2e/environments.spec.ts` was a *previous-generation* spec.** Every step was wrapped in
`if (await locator.isVisible())` — the exact anti-pattern `e2e/helpers/index.ts`'s header calls out
("a test that cannot fail is worse than no test"). Its `beforeEach` looked for `nav-environments`, which
the sidebar does not generate (the panel is reached via the dropdown, not a nav item), so it silently
skipped navigation and **all four tests passed vacuously**. Rewritten to assert, same four test titles so
the 46-test baseline is unchanged, and it now uses `openEnvironmentsManager`.

Two locator traps found while rewriting it, both worth keeping:

1. **The active environment's name is ambiguous.** `EnvSelector`'s titlebar toggle takes its accessible
   name from its **text content**, which is the active environment's name — so
   `getByRole("button", { name: /^Development$/ })` matches the titlebar toggle **and** the panel's
   sidebar item. The toggle precedes the panel in DOM order, so `.last()` is the sidebar item. (The
   dropdown's menu entries also carry env names, but `openEnvironmentsManager` closes the menu, so
   there are exactly two matches.)
2. **The panel opens on its empty state.** `selectedEnvId` defaults to `GLOBAL_ENV_ID` (`__global__`),
   which `writeSampleWorkspace` does not define, so `EnvVariableTable` is not rendered until an
   environment is clicked. Assertions therefore go through the seeded data
   (`Environment name` = "Development", first `VARIABLE_NAME` = "baseUrl") rather than through counts.

**This rewrite is unverified** — the agent shell cannot launch Electron, so it has never run. It
typechecks (`TSC_EXIT=0`) and every locator was read out of the components, but if a locator is wrong the
user will see it before I do.

### Static audit of the whole e2e suite — 11 of the 46 tests cannot fail

Since the agent shell cannot launch Electron, the suite was audited **statically** instead: every spec's

| Generation | Specs | Tests | Can it fail? |
|---|---|---|---|
| Rewritten, imports `./helpers` | `app`, `mappings`, `proxy-rules`, `mocks-rest`, `requests-rest`, `environments` | 27 | **yes** — asserts real panel anchors |

| Near-tautological | `capture-ws-webhooks` | 6 | 4 are bare `expect(body).toBeTruthy()`; the 2 real steps are guarded |

**So "some fail, the rest pass" is the wrong reading — 11 of the 46 cannot fail at all, and the four

those out — so no `NavItem`, and therefore no `data-testid`, is emitted for any of them. `NavItem` builds
its testid as `nav-${id}`; the ids that *do* render are `services, healthbar, mappings, rules, capture,
requests, mocks, sockets, webhooks`. Settings is reachable only through a bespoke bottom-pinned button
carrying `aria-label={strings.nav.settings}`.

not exist.** There is no `graphql`, `soap` or `grpc` panel id in the registry at all — those are protocol

`chooseProtocol(page, /REST Mock/i)`. So all three of its describes navigate nowhere. This needs a
decision, not a selector fix: re-point them at the real flow (open Mocks → New Mock → choose GraphQL Mock)
