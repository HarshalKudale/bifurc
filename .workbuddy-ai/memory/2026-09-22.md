## Diagnosis — three stale tests and one stale fixture, no product bugs

**1. `proxy-rules.spec.ts:15` — the fixture wrote `names.json` in the wrong shape, and that was the biggest
of the four.** The error context showed the panel *rendered*, said **"2 rules"**, and rendered `—` for every
name with no match pattern. So the data arrived and the *fields* were empty.

`e2e/fixtures/sampleData.ts` wrote `ruleNames[rule.id] = rule.name` — a **string** per id — while the engine
reads `EntityNameEntry` **objects** (`fsNamesIndex.ts:5`): `store/config.ts:133-134` does
`ruleNames[s.id]?.name` and `?.url`. A string value yields `undefined` for both → `name: ""`, `pattern: ""` →
the panel's `{r.name || "—"}` placeholder. The real writer is `upsertNameEntry(wsId, kind, id, {name, method,
url})`, so objects are canonical.

**All four names indexes the fixture writes were wrong the same way**: `rules` (`{name, url=pattern}`),
`requests` (`{name, method, url}`), `sockets` (`{name, url}`), `webhooks` (`{name, urlSuffix}`) — the field
names differ per kind and are read by name (`config.ts:133,168-170,175-176,184-185`). Fixed.

**2. `mocks-rest.spec.ts:49` — the test forgot the response body.** The error context:
`locator resolved to <button disabled …>Save Mock</button>`. `RestTab.tsx:164` gates Save on
`resMode === "none" || resBody.trim()`, and `restTabReducer.ts:130-131` starts a new mock at
`resMode: "json"`, `resBody: ""` — so Save is **disabled** until a body is typed. **The sibling test in the
same file is literally named "creates a REST mock *with a body* and status" and calls
`fillVisibleCodeEditor`**; this one was written without that step. One-line fix.

**3. `happy-path-workflows.spec.ts:330` — it kept its own copy of a bug already fixed elsewhere.**
`clickTitlebarButton(page, /^Manage Environments/i)` — a local helper in that file doing
`getByRole("button", {name}).first().click()`. But "Manage Environments…" exists **only inside the
environment dropdown**, so it matches nothing at rest. `e2e/helpers/index.ts`'s `openEnvironmentsManager`
docblock records this **verbatim** ("*which is exactly how the previous version of this test failed*") — and
the fix was applied to `app.spec.ts` but never reached this file, which imports no helpers at all. Fixed by
importing and using the shared helper.

**4. `app.spec.ts:69` — a locator for a label nothing in the tree produces.** It clicked
`getByRole("button", { name: /^REST 3$/i }).nth(1)`. A repo-wide grep for `REST 3` returns **that one line
and nothing else**, and `git log -S '"REST 3"' -- e2e/fixtures/sampleData.ts` shows it was **never** a seeded
name. Tab labels come from the entity's `name` (`useRequestsPanelState.ts`'s `tabLabel`); the fixture seeds
`Get All Users` / `Create New User` / `Update User`. The test needs a **saved** request (it asserts
`Update Request` after `Ctrl+S`), so it now opens the Requests panel and clicks the seeded `Update User`.
**This is the one fix I am least able to verify without a run** — flagged to the user.

## The guard that did not exist, and now does

**~2,600 unit and integration tests were green through all of this**, because they build their own fixtures
from `src/`. The e2e fixture's on-disk shape was exercised by **nothing but a real Electron run** — the most
expensive and least frequent thing here. So `tests/integration/e2eFixtureContract.integration.test.ts` (new,
5 cases) runs `writeSampleWorkspace()` and reads it back through the engine's own `loadConfig()`, asserting
`name` / `pattern` / `method` / `url` / `urlSuffix` survive, plus a property case: no blank `name` anywhere a
**names index** backs the kind.

**Mutation-checked:** reverting `rules/names.json` to the string shape fails exactly 2 of the 5 — the specific
proxy-rule assertion and the property. Teeth confirmed.

**Two narrowings the property needed, and the general form is the lesson.** It first reported
`mappings/map-001`, because `LocalMapping` carries **`label?` and no `name`** (`store/types.ts:3-10`) — the
test was wrong, not the fixture. Then it reported `mappings/map-003.label`, which is `""` **deliberately**
(`MappingsPanel.tsx:180` renders `m.label || "—"`, a designed empty state). So the property is scoped to the
names-index-backed kinds. **A "no blank field" property must be scoped to fields that are *required*, or it
reports designed empty states as defects.**

## Two environment traps hit while building the guard

1. **`%LOCALAPPDATA%` short-circuits the data root on win32** — `setDataRoot()` is silently ignored, so the
   first probe read the developer's real profile and found **0 entities of every kind**, "failing" for a
   reason unrelated to the bug. Fixed by pointing the env at the temp root *before* `loadConfig()`, and
   restored in `afterAll` because a leak would redirect every later integration test in that worker. This is
   the same divergence `TRAPS.md` records for the WI 6 host CLI — **third victim**.
2. **The `*/`-in-JSDoc trap bit again, and again the offending token was a glob.** My comment contained
   `packages/*/src`, which closed the block comment early and produced a wall of `TS1005`/`TS1434` in
   `app.spec.ts`. `npm run typecheck:e2e` caught it immediately (clean afterwards) — **the same sting
   `TRAPS.md` already records, including that it was a glob last time too.**

### `app.spec.ts:68` — my previous fix was wrong twice, and a third defect was hiding behind it

My `a239ab5` version clicked the seeded request by name with `getByRole("button", …)`. The error context
says `waiting for getByRole('button', { name: /^Update User$/i }).first()` — and its page snapshot shows
the panel **open** with the tree rendering `generic "Update User" [cursor=pointer]`.

1. **The tree row is not a button.** `FolderTreeItemNode.tsx:28` renders
   `<div title={item.name} onClick={…}>` — a plain div. Its role is `generic` and its accessible name comes
   from `title` (Playwright's accname falls back to `title`). I found the right *entity* and asked for the
   wrong *role*. **`getByRole` matching the right name is not evidence the role is right.**
2. **The click was wrong even had the role matched: it opens a SECOND tab**, and the test ends with
   `No requests open`, which needs the panel to finish with **zero** tabs. So the seeded click had to be
   *removed*, not re-pointed — a reminder that when a step's premise is wrong, fixing its syntax is not fixing it.
3. **`Ctrl+T` does not open the request form.** `openNewTabInFolder` (`useRequestsPanelState.ts:94`) sets
   `draftProtocols[tabId] = null`, and `RequestsPanel.tsx:167` renders `ProtocolSelectorTab mode="request"`
   while `isUnsaved && !currentProto`. So a new tab opens on the **protocol chooser**; the form exists only
   after a protocol is picked. The missing `chooseProtocol(page, /REST Request/i)` is why the following
   `fill` had nothing to fill. **The same step is present in `requests-rest.spec.ts` — the passing sibling
   had it and this test never did.**

**And one assertion could not fail:** the original asserted `getByText("New Request")`, which *also* matches
the panel's own "New request" button (`ref=e175` in the snapshot) — so it passed whether or not `Ctrl+T`
did anything. Replaced with the chooser's unique heading `Select Request Protocol`
(`ProtocolSelectorTab.tsx:93`). **Same class as the `if (await locator.isVisible())` guards this repo
already removed: a test that cannot fail is worse than no test.** Checked the replacements can fail:

- `Ctrl+T` → `Select Request Protocol` — exists nowhere else.
- `Ctrl+S` → the save label. `RestTab.tsx:271` picks `Save Request` while `draftTabId` is set and
  `Update Request` once cleared (`strings/editor.ts:95-96`), so the flip **is** the evidence of a save.
- `Ctrl+W` → the empty state, reachable only by closing the one tab the test opens.

Also: a request needs only a URL to save (`RestTab.tsx:162-163` gates on `state.url.trim()` for
`tabType === "request"`; the body rule is the mock branch) — unlike a mock.

### `screenshots.spec.ts:117` — the user's diagnosis was exactly right

*"manage environment button shows up when we open environment selector"*. `EnvSelector.tsx` renders the
titlebar toggle (`title="Switch environment"`, the "Development" button in the snapshot) and renders
"Manage Environments…" **only inside `{open && …}` at line 46**. The tour declared it `trigger: "titlebar"`
and looked for it at rest. It failed at panel 11 of 12, so panels 1–10 were fine.

Fixed by giving it its own trigger instead of pretending it is a titlebar button: `trigger: "environments"`
delegates to the shared `openEnvironmentsManager` helper — whose docblock **already recorded this exact
failure mode**, because the same bug was fixed in `app.spec.ts` and never reached the tour. **Twice now a
fix has landed in one spec and not its siblings; grep the whole `e2e/` tree for the pattern, not the file.**

`EnvironmentsPanel.tsx` is a **panel, not a modal**, so the tour continues to panel 12 with no dismissal step.
