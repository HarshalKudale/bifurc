## Diagnosis — three stale tests and one stale fixture, no product bugs

**1. `proxy-rules.spec.ts:15` — the fixture wrote `names.json` in the wrong shape, and that was the biggest
of the four.** The error context showed the panel *rendered*, said **"2 rules"**, and rendered `—` for every
name with no match pattern. So the data arrived and the *fields* were empty.

`e2e/fixtures/sampleData.ts` wrote `ruleNames[rule.id] = rule.name` — a **string** per id — while the engine

`requests` (`{name, method, url}`), `sockets` (`{name, url}`), `webhooks` (`{name, urlSuffix}`) — the field

**3. `happy-path-workflows.spec.ts:330` — it kept its own copy of a bug already fixed elsewhere.**

**4. `app.spec.ts:69` — a locator for a label nothing in the tree produces.** It clicked

## Fifth batch — WI 7's desktop half lands, and measuring it first was what made it safe

### The plan's own wording for this work item was wrong, and measuring found it

The plan says the facade should delegate "to the registered runtime **for the active workspace**". That is
the obvious shape and it would have shipped a bug. **WI 4** (`coreCommands.ts:83-101`) deliberately deleted
the `reloadConfig()` that `workspace.setActive` used to call, and annotated it *"Visible change, and the
reason this needed confirming"*: on the desktop the **active pointer and the running proxies are
independent by design** — the port is owned by the workspace, not by which one is selected. So a facade
resolving by `activeWorkspaceId` would, after a switch, look up a runtime for the *new* active id, find
none, and fall back to its lazy default — whose `isRunning()` is `false` while the real proxy is listening.
**The WI 1 bug shape, arriving through a new door.** The fix is a binding that names no workspace.

**And `proxy/server.ts`'s own header still described the pre-WI-4 world** — lines 33-38 say the
`workspaceId ?? cfg.activeWorkspaceId` fallback *"is exactly how the module facade and the desktop keep
working, because they construct one proxy and mean 'whatever the user has selected'."* After WI 4 the
desktop's proxy does **not** follow a switch. The *behaviour* is right (it is what D10 wants); the
*description* is what would have misled the implementation — `TRAPS.md`'s "the docblock that sanctions the
bug", again.

### The hazard that would have broken the acceptance criterion

`WorkspaceRuntime.start()` binds **both** servers, and `webhookPort` is a **required** option. But the
desktop has **never** started the webhook receiver at boot: `src/main.ts` starts only the proxy and the
companion, and the receiver is user-started (`renderer/panels/WebhooksPanel.tsx:100` →
`window.api.startWebhookServer()`). So the tempting `runtime.start()` line would have **opened a webhook
port the product has never had** — a new listening socket, a new `preflight` warning wherever `9101` is
taken, and a direct violation of §8's "one proxy port". `main.ts` calls `runtime.proxy.start(cfg.port)`
instead. **Neither of these was in the plan, and both were found by reading the code before writing it.**

### What landed

- `proxy/server.ts` / `proxy/webhookServer.ts`: `bindProxyInstance()` / `bindWebhookInstance()`, plus an
  `existingServer()` accessor so `isRunning()` / `getPort()` / `stopServer()` keep their pre-existing
  **no-create** property (`createEngine()`'s `waitUntilReady()` polls `isRunning()` in a loop).
  **No new import edge** — `proxy/*` does not import `runtime/`, so the acyclic graph `runtimeRegistry.ts`
  protects is untouched.
- `src/main.ts`: one runtime, registered and bound; `startServer(cfg.port)` unchanged and now delegating.
- `tests/integration/facadeBinding.integration.test.ts` (new, 6 cases).
- **Suite 108 files / 2,598 — 2,558 passed, 40 skipped, 0 failed.** Delta **+6 / +1 file**, mechanism named.

### The mutation lesson: one mutation is not enough

The coarse mutation (make both `bind*Instance` no-ops) fails **4 of 6** — and *not* the `reloadConfig` case,
because it moves the **listener** too: `startServer` then binds the facade's own instance and `reloadConfig`
reloads the same one, so the rule is served and the assertion passes for the wrong reason. The
`reloadConfig` case needs its **own** mutation (make it use an instance of its own while `startServer` still
honours the binding), which fails exactly that one with **502** — the rule lands in an instance nobody is
serving from. **A test that survives one mutation may just be aimed at a different mechanism; check what
each mutation moves.**

### And a WI 4 defect the guard work uncovered — recorded, not fixed

An earlier version of the test put the runtime on a workspace **other than** the active one, to make "which
workspace got reloaded?" observable. It failed, and the cause is not in this work item:
**`serverUtils.ts:35-44`'s `workspaceCfg()` filters dispatch by `cfg.activeWorkspaceId`**, while
`servedWorkspaceId()` reads the **instance's** workspace. So a runtime serving a non-active workspace reads
its own rules and then filters every one of them out — it serves nothing, silently. **WI 4 severed
`activeWorkspaceId` from the proxy's reads but not from its dispatch filter.**

**Why it was invisible:** `workspaceRuntime.integration.test.ts`'s "both genuinely serve" step asserts
`getHomePage(port)` — the proxy's own UI page, which is served regardless of any rule. §8's **first**
criterion is *"each serving its own rules"*; **a home page is not a rule.** So the criterion is not met as
written, and the instrument chosen for *ports* and *readiness* in that file was chosen for *convenience* for
*content*. Recorded in `plan/14` + `TRAPS.md` with a measurement, left for an owner decision: the fix
threads `servedWorkspaceId()` into `workspaceCfg()`, i.e. every proxy's dispatch path — a different change
with a different blast radius, which is the distinction `configCommands.ts`'s header draws for moving an
already-registered command. The new test deliberately does **not** depend on it.

## Sixth batch — the WI 4 defect, measured properly, and the scope was bigger than my first reading

I said the fix was "thread `servedWorkspaceId()` into `workspaceCfg()`". **That was wrong**, and the
correction is worth recording because it is a *reading* error, not a coding one.

### What a throwaway probe showed

Two workspaces, each with its own mock, mapping and rule; a runtime for **B**; only `activeWorkspaceId`
differs between the two runs:

| Request against B's port | active = **A** | active = **B** |
|---|---|---|
| `GET /api/b` — **B's own mock** | **404** | **200** `{"from":"B"}` |
| `GET http://api.test/data` — **B's own rule** | **502**, upstream hits **0** | **200** `{"from":"upstream"}`, upstream hits **1** |

The rule row is the clean comparison — a `targetType: "external"` rule needs no mapping, so nothing else
differs. **A host member whose workspace is not the active pointer serves nothing, silently.**

### The part I had wrong: it is not cross-talk, and it is not one bug

My first instinct was "B serves A's data". The probe says otherwise: **A's mock is 404 too.** The two halves
of the config come from *different workspaces* and **cancel**:

- `cfg.mocks` / `cfg.mappings` come from **A** — `loadConfig()` reads the active workspace by construction
  (`config.ts:68,80-82`).
- `enabledSets` comes from **B** — `loadEnabledSets(servedWorkspaceId())`.
- `workspaceCfg()`'s filter uses **A** (`cfg.activeWorkspaceId`).

So A's entities are filtered out by **B's** enabled set, and B's entities are absent from `cfg` entirely.
**Nothing leaks and nothing works.** A probe that only looked for the other workspace's data would have
found nothing wrong — which is a good argument for asserting on *both* directions rather than one.

entities come from an **active-workspace-only loader**. Making a host member serve its own mocks and
mappings needs a per-workspace loader in `store/config.ts` — which every panel also reads. That is a
config-layer change, not a one-id thread, and it is why it is an owner decision rather than a WI 7 tail.
Recorded in `plan/14` and `TRAPS.md`; the probe was deleted (it was never meant to be committed).

**Then P7's first real build.** The owner chose a **new package** for the browser transport, on decoupling
grounds. The measurements that made that viable:

- The browser needs **one** thing at runtime — `createClientSession`. `Transport`/`EngineEvent` are
  **type-only**, erased at build, and cost a browser bundle nothing (already how `@bifurc/client` uses them).
- `@bifurc/client` is **already** `platform: "neutral"`, commented *"the client is the half that has to run in
  a browser bundle for P7's web UI"* — so only the **transport** was ever missing.
- `@bifurc/protocol` already declares itself environment-agnostic **and enforces it** (`platform: "neutral"`,
  *"fail loudly if a future command schema accidentally pulls one in"*). The build is the instrument.

**The move:** `types.ts` + `session.ts` → `packages/protocol/src/wire/`. **`framing.ts` did NOT move** — it is
length-prefix framing for byte streams, `Buffer`-heavy, and a WebSocket needs none of it; moving it would have
been cargo-culting a "wire trio" that is really a pair plus a stream codec. Two changes were needed, both
type-level: `randomUUID` from `node:crypto` → `globalThis.crypto.randomUUID()` (verified present on Node
22.22.2), and `ClientChannel.encode`/`write` `Buffer` → `Uint8Array` (Buffer extends Uint8Array, so every
existing channel still satisfies the contract — it widens, it does not break). Engine keeps **thin
re-exports**, so ~10 importers — including the shell's `ipc/rpcBridge.ts` and `ipcTransport.ts` — are
untouched.

**`@bifurc/web-client`**: 8 cases against a **real engine server over a real socket** (a mocked `WebSocket`
would only assert that the file agrees with itself), using the platform's own `WebSocket` rather than an
injected stand-in. Its built output's only runtime import is `@bifurc/protocol` — **grepped from `dist`**, not
assumed.

**Mutation-checked, and it paid for itself.** Four mutations; three caught by a *named* case. The fourth
(`dispose()` not detaching handlers) was **not caught**, and the reason is the finding: `session.ts` sets its
`closed` flag *before* calling `dispose()`, so the detach is unobservable — while the comment claimed it was
load-bearing. **Fixed the comment, not the code.** Separately: the connect-failure path was **untested**, so
`onerror` was decoration until a case was added asserting that "could not connect" and "session dropped" stay
distinguishable (work item 2 gives them different UI, and only one is worth retrying).

**A third defect, found by accident:** `ws.ts`'s client does **not** use `createClientSession` — it still
carries its own copy of the whole state machine, the third-copy drift `session.ts` was extracted to prevent. It
was invisible until the move forced the question *"who imports this?"*, and `ws.ts` was absent from the answer.
Recorded in `TRAPS.md` as a **known open item**.

**Measured:** 113 files / 2,638 → **114 files / 2,646 tests — 2,606 passed, 40 skipped, 0 failed**. The delta
is **exactly +8**, the new browser cases and nothing else. The refactor *alone* was measured first
(2,638 — **zero delta**). Commits: `7187709` (refactor), `89d3c67` (package), `e5ec1cc` (decision record).
