## P19 WI 3 — REST lands end to end (the first protocol)

**The unit of work was one protocol, and that is §8 trap 1 rather than convenience:** *"one commit per
protocol: the engine starts and the renderer stops."* Resolving in both places, even briefly, double-resolves
a value that itself contains `{{…}}`.

### The wire — `request.replaySaved` → `request.send`

**`request.send`**, a `z.union` of `{workspaceId, id}` and `{workspaceId, request, scripts}`, body as
**text**, response base64 plus the pipeline's bookkeeping (`request`, `tests`, `testLogs`,
`preScriptError`, `postScriptError`, `durationMs`). **Command count unchanged at 93** — one name replaced by
one name. The name it replaced was **never released** (`git status` shows the 2026-09-29 family as
uncommitted), so this is a **rename**, not a migration: no fifth command, no second client method.

- **⚠ The union is not §5's rejected option C.** C put two modes on `request.replay`, whose whole value is
  being *one thing*. `request.send`'s two forms are each a complete description of a request, and
  `.strict()` on **both** members is what turns a partly-both payload (`{workspaceId, id, scripts}`) into a
  rejection rather than a silent half-read. That payload is the fixture's `invalid`.
- **Entry written first** (`plan/protocol-changes.md`, 2026-09-30), per the file's own rule, with a marker
  added to the 2026-09-29 entry pointing forward.
- The seven registration points, in order: `COMMANDS`, `COMMAND_FIXTURES`, `SCOPE_BY_COMMAND`, `retry.ts`'s
  partition, the **shell** (`src/ipc/handlers.ts`), the shell↔engine drift table in
  `workspaceHost.integration.test.ts`, and `layout.test.ts`'s reachability case.

### ⚠ The ratchet forced a PLACEMENT, not just a permission

`request.send` cannot live in `workspace/entities/savedRequestCommands.ts` with its three siblings: it calls
`pipeline/`, and `workspace/`'s §6 row is exactly `kernel/` + `utils/`, so it would be a
`workspace/ → pipeline/` edge. §5.1's remedy is to place a module in the layer it reads from, so it moved to
**`packages/engine/src/pipeline/commands.ts`**, and `pipeline`'s contract gained `kernel/`.

**`ORPHANS_ALLOWED`'s `pipeline` entry was deleted in the same change** — it existed because the pipeline
function had no caller, and its own text said to delete it when the `*.send` command arrived. It arrived the
next day. **⚠ Nothing would have failed if it had stayed**: the orphan assertion reads that map as a
permission and never as a claim. **A second staleness assertion now covers it** (layout ratchet 6 → **7**
assertions), which is what makes the deletion forced rather than voluntary.

### The renderer stopped knowing what `{{host}}` is

- `useRestActions` no longer imports `resolveVars`, `runPreScript`, `runPostScript` or `runTestScript`. It
  assembles the request **unresolved**, calls `window.api.requestSend`, and dispatches what came back.
  `handleTest` uses the same command with `scripts: {}` — it has never run scripts, and resolution must
  agree with Send, which after D23 means one implementation does both.
- **Allowlist 9 → 8** — `components/rest/useRestActions.ts#pipeline` is the **first entry this ratchet has
  ever retired**, and the staleness assertion is what forced it.
- **⚠ `hasExecutableScripts` was deleted from the gate entirely.** It was `true` for REST alone and `false`
  for the other three, so it was never a per-request question — a fact about which tabs had wired scripts
  up. REST's migration made it `false` for all four, at which point it was a constant inside a gate whose
  job is to prevent a silently wrong send. `usesVariables` stays (three tabs still resolve), and
  `savedEntitySend.test.ts` gained a case asserting the deleted term is **ignored** so it cannot come back
  unnoticed.
- The gate's end state is still `!isDraft && !hasLocalChanges`; two of the four terms have now left.

### The integration case that had to be INVERTED

The block pinned *"forwards the stored values literally — no `{{variable}}` resolution"*, because resolution
was the renderer's half. `request.send` **is** the different command that case was written to exclude, so it
now asserts the opposite: a stored `{{apiToken}}` resolves against the workspace's `__global__` environment
(written with `writeSavedEntity("environments", …)`), which is §10's acceptance criterion end to end.

**⚠ The harness registers handler groups explicitly** — the first integration run failed with
`No handler registered for command "request.send"` for exactly 7 cases, because
`protocolExecution.integration.test.ts` calls each `register*Commands()` by name and had never heard of
`registerPipelineCommands`. That is the same "a command's registration is not the whole of its dependency"
shape `registerAll.ts` warns about, one consumer over.

### Client surface

`replayRequestSaved` → **`requestSend`** (a rename, so **both pinned rows stay at 136 / 132** and the gap
stays four — which is what tells a reader this was a rename and not a drop hiding inside an addition).
`packages/gui/src/types/window.ts` declares the union and the result; `types/ipc.ts` gained the four
hand-mirrors (`RequestSendRequest`, `RequestSendScripts`, `RequestSendParams`, `RequestSendResult`), because
`packages/gui` has no `@bifurc/protocol` dependency by design.

## P19 WI 3, second protocol: GraphQL

**`graphql.executeSaved` → `graphql.send`** — a union of `{workspaceId, id}` and `{workspaceId, request}`,
where `request` is the **stored entity's shape** (`endpointUrl`, not `url`) so the two forms stay
interchangeable and the rename stays the engine's business. **No `scripts` member**: the sandbox's context is
a `{method, url, headers, body}` request and a GraphQL request is not one, so a `scripts` object nothing could
run would be a field that lies. Count stays **93**.

**It landed in `graphql/commands.ts`, not `pipeline/commands.ts`** — §5.1 rather than taste: it resolves and
dispatches, so it reads `workspace/` + `utils/` + `kernel/`, which is `graphql/`'s §6 row exactly. It does
**not** call `runRequestPipeline`: that function's `PipelineRequest` view exists for the three script steps,
and fabricating one to satisfy a signature would be inventing a shape. **The pattern for the remaining two is
therefore: their own feature module, direct resolve + dispatch.**

### ⚠ The finding: each non-REST tab resolves FEWER fields than its own gate scans

| tab | gate scan (the intent) | `handleSend` actually resolved (the practice) |
|---|---|---|
| GraphQL | `endpointUrl`, `query`, `variables`, `operationName`, `headers` | `endpointUrl`, `variables`, `headers` |
| SOAP | `endpointUrl`, `soapAction`, `body`, `headers` | `endpointUrl`, `body`, `headers` |
| gRPC | `serverAddress`, `serviceName`, `methodName`, `requestBody`, `metadata` | `serverAddress`, `requestBody`, `metadata` |

So a `{{token}}` in a GraphQL `query`, a SOAP `soapAction` or a gRPC `serviceName` has **never resolved**, in
*either* path — the gate only ever chose between two ways of sending the same unresolved field. **The gate was
written from intent and the tab from practice, and the gate is the better spec.**

**⚠ This is why the migration MUST resolve every field, not the subset the tab did.** Resolving the narrower
set would preserve the bug *and* keep `usesVariables` in the gate forever, because a token in one of those
fields would still make the stored entity differ from the screen. The engine resolves all five; a new
integration case asserts each one arrived resolved.

**The tab's `activeEnv` prop was deleted** — threaded from the panel down to `handleSend`, and `handleSend` no
longer resolves. An unused prop reads as a dependency the component still has, so removing it was part of the
change. (`RequestTabContent` still passes it to the other tabs.)

**The allowlist did not move** — `graphql`'s `resolveVars` calls were *uses*, not definitions, so the ratchet
never had an entry for them. Still 8 entries. `usesVariables` stays in the gate for SOAP and gRPC.

## P19 WI 3, third protocol: SOAP

**`soap.executeSaved` → `soap.send`** — a union of `{workspaceId, id}` and `{workspaceId, request}`, where
`request` is `{endpointUrl, soapAction, headers, body}`. **This is the one protocol where the stored shape and
the command's params are identical** — all four fields are already named the same on both sides — so unlike
GraphQL there is no rename for the engine to perform, and it is the simplest of the three unions. **No
`scripts` member**, same reason as graphql (the sandbox's context is a `{method, url, headers, body}` request).
Count stays **93**.

**Same class of fix, one field wide.** The tab resolved `endpointUrl`, `headers` and `body` but **not
`soapAction`**, while the gate's token scan treated all four as resolvable — so a `{{token}}` in a SOAPAction
never resolved in *either* path. The engine resolves all four; a new integration case asserts each arrived at
the upstream resolved.

**`SoapTab`'s `activeEnv` prop was deleted** (same as GraphQLTab), and `RequestTabContent` no longer passes it
to either tab — it still passes it to gRPC.

**`savedRequestCommands.ts` is down to ONE counterpart** (`grpc.executeSaved`), and its header now records why
the "one module, not four" argument has narrowed to one: the argument was never "these commands are similar",
it was that four **identical** bodies would be four copies of one body in four directories. Three stopped being
identical — one by growing a pipeline, two by growing resolution — for exactly the reason the argument existed.

**The allowlist is still 8** — soap's `resolveVars` calls were *uses*, not definitions.

## P19 WI 3 COMPLETE — gRPC landed, and the `*Saved` family is gone

**`grpc.executeSaved` → `grpc.send`** — union `{workspaceId, id}` | `{workspaceId, request}` where `request` is
`{serverAddress, serviceName, methodName, requestBody, metadata, protoFileId, useReflection}`. Stored shape ==
command shape (like SOAP, no rename). **`protoFileId` / `useReflection` are required, not optional** — the
editor always has both, and optionality would invite a caller to omit a decision rather than make one.
**`protoFileId` is deliberately NOT resolved**: it names a stored file rather than being template text, and the
gate never scanned it. Count stays **93**.

**⚠ The whole `savedRequestCommands.ts` module is DELETED.** Its four load-and-dispatch bodies are gone, and so
are its registrations in `registerAll.ts`, `src/ipc/handlers.ts` and both integration harnesses. Its *"one
module, not four"* argument had narrowed three times (one member grew a pipeline, two grew resolution) and then
became empty — which is the honest end of an argument, not a defeat.

**`savedEntitySend.ts` reached §7's end state:** `!isDraft && !hasLocalChanges`. **Both** domain terms deleted
rather than weakened — `hasExecutableScripts` since REST, `usesVariables` with gRPC — and
`containsVariableToken` deleted alongside them (it had exactly one consumer, the four gates). The test file
pins both departures so neither can return unnoticed.

**⚠ gRPC's resolution is NOT observable, and the gap is recorded rather than papered over.** `grpc.execute` is
a `wontfix` stub that ignores every parameter it is handed, so there is no upstream at which a resolved field
could be seen. Replacing it with an echo needs a monkey-patched registry, because `CommandRegistry.register()`
**throws on a duplicate** — a worse trade than the gap, given the resolution is the same shape as `soap.send`'s,
which *is* verified field by field. The `NOT_FOUND` case is what proves the load half. Recorded in
`grpc/commands.ts`'s header and the `grpc.send` entry.

**⚠ The allowlist did NOT reach `{}`, and the two remaining entries are not WI 3's.** `lib/resolveVars.ts` and
`lib/randomizer.ts` outlive the four tabs, because `useWebSocket.ts` resolves the url and headers (**WI 6**) and
`HealthBarPanel.tsx` resolves a service url (WI 5's remaining processing). `App.tsx:288`'s `mergeEnvVars` also
still runs, for the panes' active-env hint. **They belong to WI 6, not WI 3** — §6's table said "the last tab
stops resolving", which was wrong, and the correction is now in §6 so nobody hunts for the debt.

**WI 3's own deletion, final:** `useRestActions.ts#pipeline` — the only entry this ratchet has ever retired.
The four `pipeline` / `pipelineStep` entries wait for **WI 4**; the resolver/randomizer pair for **WI 6**.

### WI 4 — the owner settled both policies (they were *decisions*, per §8 traps 5 and 6)

**D29 — a run's lifetime is the ENGINE's.** A client disconnect and a workspace switch do **not** cancel a run;
`runner.status` lets a reconnecting client attach. **A host restart loses it** — no durable run record, and the
`.runs/` files stay what they always were (a *report* of a finished run, not live state). Persisting so a restart
could resume was rejected: resuming must decide whether to re-send what the run already sent, and that has no
safe default.

**D30 — one run per `{workspaceId, folderId}`.** A second run of the same folder is **refused** with an error
naming it; two different folders run side by side; a **finished** run does not block a new one (the snapshot must
outlive the run for `runner.status`). A workspace-wide lock was rejected as forbidding two independent
collections for no reason the UI ever had; a queue as needing ordering semantics with no use yet.

### WI 4's engine half landed

- **`runner/runCollection.ts`** — the loop, and it is **thin because WI 3 exists**: the whole per-request body is
  one `registry.invoke("request.send", {workspaceId, id})`. The renderer's version could not be that thin.
- **`runner/runRegistry.ts`** — the run state. Module-level **by design** (D29: no persistence, no teardown hook,
  and *nothing in the file can observe a disconnect*). Keyed by `{workspaceId, folderId}` (D30).
- **`tests/runner/runRegistry.test.ts` — 12 cases**, including the three that make the decisions checkable rather
  than asserted: `startRun` returns **before** the loop finishes; `cancelRun` is the **only** lever; D30 in both
  directions (same folder refused, different folders concurrent, finished ≠ blocking).
- **⚠ Two config fields stay un-honoured, deliberately:** `runner.json` carries `stopOnFailure` and `iterations`
  and the renderer read **neither** — a folder set to stop on failure ran to the end anyway. Implementing them
  here would be a behaviour change smuggled in under a move, and each is a real decision (does a failed *test*
  count, or only a failed *send*?).

**⚠ The engine half is safe to land before the renderer's, unlike WI 3's** — trap 1 exists because two resolvers
*double-apply* a value; two run loops do not interfere, and nothing routes to the renderer's loop but the UI's own
button.
