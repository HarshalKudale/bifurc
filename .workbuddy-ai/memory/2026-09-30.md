## P19 WI 3, second protocol: GraphQL

**`graphql.executeSaved` → `graphql.send`** — a union of `{workspaceId, id}` and `{workspaceId, request}`,
where `request` is the **stored entity's shape** (`endpointUrl`, not `url`) so the two forms stay
interchangeable and the rename stays the engine's business. **No `scripts` member**: the sandbox's context is
a `{method, url, headers, body}` request and a GraphQL request is not one, so a `scripts` object nothing could
run would be a field that lies. Count stays **93**.

**It landed in `graphql/commands.ts`, not `pipeline/commands.ts`** — §5.1 rather than taste: it resolves and
dispatches, so it reads `workspace/` + `utils/` + `kernel/`, which is `graphql/`'s §6 row exactly. It does
**not** call `runRequestPipeline`: that function's `PipelineRequest` view exists for the three script steps,
and fabricating one to satisfy a signature would be inventing a shape. **The pattern for the remaining two is
therefore: their own feature module, direct resolve + dispatch.**

### ⚠ The finding: each non-REST tab resolves FEWER fields than its own gate scans

| tab | gate scan (the intent) | `handleSend` actually resolved (the practice) |
|---|---|---|
| GraphQL | `endpointUrl`, `query`, `variables`, `operationName`, `headers` | `endpointUrl`, `variables`, `headers` |
| SOAP | `endpointUrl`, `soapAction`, `body`, `headers` | `endpointUrl`, `body`, `headers` |
| gRPC | `serverAddress`, `serviceName`, `methodName`, `requestBody`, `metadata` | `serverAddress`, `requestBody`, `metadata` |

So a `{{token}}` in a GraphQL `query`, a SOAP `soapAction` or a gRPC `serviceName` has **never resolved**, in
*either* path — the gate only ever chose between two ways of sending the same unresolved field. **The gate was
written from intent and the tab from practice, and the gate is the better spec.**

**⚠ This is why the migration MUST resolve every field, not the subset the tab did.** Resolving the narrower
set would preserve the bug *and* keep `usesVariables` in the gate forever, because a token in one of those
fields would still make the stored entity differ from the screen. The engine resolves all five; a new
integration case asserts each one arrived resolved.

**The tab's `activeEnv` prop was deleted** — threaded from the panel down to `handleSend`, and `handleSend` no
longer resolves. An unused prop reads as a dependency the component still has, so removing it was part of the
change. (`RequestTabContent` still passes it to the other tabs.)

**The allowlist did not move** — `graphql`'s `resolveVars` calls were *uses*, not definitions, so the ratchet
never had an entry for them. Still 8 entries. `usesVariables` stays in the gate for SOAP and gRPC.

### WI 4 — the owner settled both policies (they were *decisions*, per §8 traps 5 and 6)

**D29 — a run's lifetime is the ENGINE's.** A client disconnect and a workspace switch do **not** cancel a run;
`runner.status` lets a reconnecting client attach. **A host restart loses it** — no durable run record, and the
`.runs/` files stay what they always were (a *report* of a finished run, not live state). Persisting so a restart
could resume was rejected: resuming must decide whether to re-send what the run already sent, and that has no
safe default.

**D30 — one run per `{workspaceId, folderId}`.** A second run of the same folder is **refused** with an error
naming it; two different folders run side by side; a **finished** run does not block a new one (the snapshot must
outlive the run for `runner.status`). A workspace-wide lock was rejected as forbidding two independent
collections for no reason the UI ever had; a queue as needing ordering semantics with no use yet.

## WI 4's wire — the run is drivable from any client

**Three commands + two events**, all additive (`plan/protocol-changes.md`'s 2026-09-30 entry):

| | |
|---|---|
| `runner.start` | `{workspaceId, folderId}` → `{ok, total?, error?}` — **returns when the run is registered**, not when it finishes (D29) |
| `runner.cancel` | `{workspaceId, folderId}` → `{ok, error?}` — the only lever that stops a run |
| `runner.status` | `{workspaceId, folderId}` → the state or `null` — what a reconnecting client asks |
| `event.runner.progress` | `{workspaceId, folderId, index, total, result}` |
| `event.runner.finished` | `{workspaceId, folderId, report}` |

Protocol **93 → 96** commands, **9 → 11** events. Client surface **136 → 141** (transport 66 → 69, subscribe
7 → 9) — the second growth ever, pinned in `surface.test.ts` + `client.test.ts`.

**⚠ Two scopes, deliberately:** `start`/`cancel` are **`execute`** (they make something happen), `status` is
**`read`** — which is what lets a reconnecting client ask what happened *without* being granted the right to
start or stop anything. That split is the whole reason the status command is separate.

**⚠ `total` rides on every progress event**, not only on `runner.start`'s result, because a client that
attaches mid-run (D29) never saw the start call.

**⚠ The conformance suite widened AUTOMATICALLY.** Its every-command and every-event matrices are *derived*
from `COMMANDS` / `EVENT_NAMES`, so the three commands and two events cannot be left out of them — the wire
cost three list entries, not three hand-maintained tables. That is what `EVENT_NAMES` being "total" buys.

**⚠ The client's `retry.ts` partition needed all three**, and the answers differ: `runner.status` and
`runner.cancel` are **idempotent** (a status read; a cancel flag that is a no-op the second time), while
`runner.start` is **non-idempotent** — a retry after an unknown outcome is a run the caller did not ask for.
The partition throws at import if a command is missing, so this was a load failure rather than a silent gap.

**Next: the renderer half** — `useCollectionRunner` subscribes instead of looping, and the four allowlist
entries go (`collectionRunner.ts#pipeline`, `scriptRunner.ts#pipelineStep`, `testRunner.ts#pipelineStep`,
`runnerReport.ts#reportRenderer`).

## Read-only Q&A: engine as a sidecar in a Rust app — which transport?

Asked which transport a Rust host would use. No files changed. The answer is **`socket`**, and the
reason `stdio` is *not* the answer is the finding worth keeping:

- **⚠ `createStdioServer` has NO non-test caller.** It is conformance-tested (`run-stdio.test.ts`) and
  exported from the barrel, but **nothing boots the engine on stdin/stdout.** So "spawn the engine and
  speak frames on stdio" — the classic sidecar shape, and the one `plan/09` reserves for the CLI's
  spawn-on-demand case 4 — is **unbuilt**, and would have to be written first. A grep for the four
  server factories outside tests returns exactly **one** source file: `runtime/host.ts`.
- **The sidecar surface the repo actually ships is the workspace host** (`hostCli.js`). Its flags
  (`runtime/hostArgs.ts`) offer exactly two RPC surfaces — `--rpc-socket <path>` and `--ws-port <n>` —
  and `host.ts:692` branches on `transport.kind` between `createSocketServer` and `createWsServer`.
  **No stdio flag exists.**
- **⚠ `defaultSocketPath()` uses the ENGINE's pid** (`bifurc-${process.pid}`) — a *spawning parent*
  cannot know it, so a sidecar host must pass `--rpc-socket <its own path>` explicitly. Relying on the
  default is the trap.
- **The host wraps its socket in `createAuthenticatedTransport`, so `hello` must be the first request** —
  otherwise `UNAUTHORIZED` and the session **closes**. Version check is **major-only**
  (`checkVersionCompatibility`), so a minor mismatch connects and degrades.
  **⚠ There is no token to send** (deleted 2026-09-25) — protection is `0600`/pipe ACL + loopback-only
  ws. Do not build a token field into an external client.
- **Framing differs by transport, and this is easy to get wrong:** `socket`/`stdio` use the 4-byte
  big-endian length prefix + UTF-8 JSON (`MAX_FRAME_BYTES` 8 MiB); **`ws` does NOT** — WebSocket frames
  its own messages, so a ws client sends a bare JSON message.
- Three envelopes, both directions, discriminated by key: `{id, action, payload}` request,
  `{id, ok, data|error}` response, `{event, seq, payload}` event. Events are **pushed** — a client needs
  a reader loop separate from its request correlation.
- **⚠ This is deferred work, and there is no engine binary yet.** P10 (`plan/11`, standalone binary via
  `bun build --compile` per D2) is **de-prioritised** and P11 (Tauri) is **parked** (D1/D4/D5). A Rust
  sidecar means picking both up; today the engine ships as `node` + JS (`hostCli.js`), and the
  Dockerfile runs `node` for exactly that reason.
