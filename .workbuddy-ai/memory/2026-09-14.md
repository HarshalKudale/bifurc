## Bug: blank tray icon in AppX build (Bifurc)

**Symptom:** AppX-installed build shows a blank/invisible tray icon (tray slot exists, no image). NSIS-installed older build appeared fine.

**Root cause:** Commit `2477194` moved `icon.png` / `tray-icon.png` from the project root into `build/` (buildResources) and **removed them from `build.files`**. But `src/main.ts` loads them at runtime via
`nativeImage.createFromPath(path.join(__dirname, "..", "tray-icon.png"))`, which resolves to `<resources>/app.asar/tray-icon.png`.

Verified by reading the asar header: `app.asar` contains only `/dist/**`, `/package.json`, `/node_modules/**` — no `/tray-icon.png`, no `/icon.png`. The AppX also has no `app/tray-icon.png`.

`nativeImage.createFromPath()` on a missing path returns an **empty NativeImage** (no throw), so `new Tray(emptyImage)` registers a blank tray slot.

Note: this also broke dev mode (`__dirname/..` = project root, icons now live in `build/`) and `getAppIcon()` for the BrowserWindow icon. Not an AppX-specific Electron bug — a packaging regression; NSIS would be broken too on a fresh build.

**Fix applied:**
- `bifurc/package.json`: added `extraResources` mapping `build/tray-icon.png` -> `tray-icon.png` and `build/icon.png` -> `icon.png`.
- `bifurc/src/main.ts`: added `iconPath()` (uses `process.resourcesPath` when `app.isPackaged`, else `__dirname/../build`) and `loadIcon()` with an `isEmpty()` guard that falls back to `nativeImage.createFromPath(process.execPath)`.
- Rebuilt `dist/main.js` (`tsc && tsc-alias`), typecheck passes.

**Regression guard idea:** CI should assert the built asar contains the icon files before packaging.

## Assessment: UI / Engine decoupling effort estimate (Bifurc)

Produced `Decoupling_Assessment.md` (repo root). Goal was estimating the work to split the Electron
UI from the backend engine over JSON-RPC, for a future headless engine + webview UI + CLI + Docker.

**Baseline measurements recorded (v0.3.1):**
- Main process `src/`: ~101 files / ~11,525 LOC (`ipc/` 4,763, `proxy/` 2,567, `store/` 1,278,
  `sync/` 1,060, `applications/` 854, `companion/` 309, `main.ts` 336, `preload.ts` 197)
- Renderer: 209 files / 27,910 LOC. **Zero Node/Electron APIs** — only `window.api.*`
  (207 call sites across 43 files)
- IPC: 112 `ipcMain.handle`, 0 `ipcMain.on`, 7 main→renderer push events, 136 preload invoke wrappers
- Tests: 35 files / 9,636 LOC; e2e 11 Playwright specs via `_electron.launch`

**Key findings that shape any future work:**
1. Renderer is already browser-clean → rewriting `preload.ts` as an RPC client keeps all 207 call
   sites unchanged. Biggest cost saving in the project.
2. `src/companion/companionServer.ts` already implements `{id, action, payload}` → `{id, ok, data, error}`
   over loopback WebSocket on port 9271, consumed in production by `bifurc-extension`. Generalize it
   rather than design a new transport.
3. Engine is nearly Electron-free: only `BrowserWindow.getAllWindows()` broadcast (8 files),
   `app.getPath("userData")` (2 files), `dialog.*`/`shell.*` (5 files). `src/proxy/` has exactly one
   Electron import (`webhookServer.ts`).
4. `entityCrudFactory.ts` already generates CRUD for ~11 entity kinds → 36 handlers collapse to ~6.
5. `coreHandlers.ts:20` imports `updateTrayMenu` from `@/main` — engine→shell cycle, must invert.
6. `main.ts:255` hard-requires git and reports failure via Electron `dialog.showErrorBox` — blocks
   headless/Docker startup.
7. `mkcert` (`proxy/certManager.ts`, `proxy/tlsCert.ts`) is a native binary dep — Docker/Linux/arm64 risk.
8. MSIX/APPX is the hardest packaging target (single immutable container). Recommended approach:
   support both embedded in-process and remote transport behind one interface, so the packaging target
   chooses. Needs an empirical spike before committing.

**Estimate delivered:** ~40–45 engineer-weeks central (34.5–51 range); 3–5 months calendar with 2–3
engineers. Minimum viable decoupling (seam only, zero user-visible change) ~8–10 weeks.

**Recommendation recorded:** land `Cleanup_plan.md` *before* decoupling (not concurrently) — mixing
~110 files of cleanup with the extraction makes regressions untraceable.

## Assessment v2: headless engine + Tauri shell path

User proposed replacing Electron entirely: headless Node/Bun engine spawned as a sidecar, UI as a
Tauri app (to keep tray / always-active) or plain webview. Produced `Decoupling_Plan_v2.md`, which
supersedes §6–§8 of v1.

**New verifications (measured):**
- `renderer/types/window.ts:193` declares `platform: string` but it is **never read** anywhere in
  `renderer/`. No `navigator.userAgent` sniffing. Renderer is 100% platform-agnostic → portable to any
  webview with zero changes.
- **`oklch()` in 7 renderer files, `color-mix()` in 2** (`tokens.css`, `styles.css`,
  `lib/codemirrorTheme.ts`, `TitleBar.tsx`, etc.). Fine on WebView2/WKWebView; **WebKitGTK on older
  Linux is the risk** — the whole design system depends on it.
- `__dirname` / `process.resourcesPath` appear **only in `main.ts`** (shell). No engine module resolves
  assets from disk → **compiling the engine to a standalone binary is safe**, nothing breaks on
  missing `node_modules`.
- `zoomLevel` has **zero** references in `renderer/` — zoom is purely a shell concern.
- Tray menu (`main.ts:78`) is 3 items: Open / minimizeToTray checkbox / Quit. Trivial rewrite.
- **Correction to v1:** `mkcert@3.2.0` is **pure JS** (`node-forge` + `commander`, no bundled binary,
  no spawn). v1 wrongly flagged it as a native-binary risk. v1 doc updated.
- **New risk:** `certManager.ts:41` `installCA` shells out to `certutil` / `security
  add-trusted-cert` / `sudo update-ca-certificates`. CA trust is **host-scoped** — for a remote engine
  the CA must be trusted by the *client's* browser, not the container. Added as v1 §7.7.
- **New risk:** Tauri v2's Windows bundler emits **NSIS + MSI (WiX)** only — no `appx`/`msix` target.
  The MS Store artifact becomes hand-authored, which is *more* work than today's electron-builder.

**Estimate v2:** full end state **~45–55 engineer-weeks** (range 43–63) — about **+10 weeks over the
v1 Electron-only path**. Tiered: Tier 1 seam 10–14 w (zero user-visible change), Tier 2 headless
clients 12–17 w, Tier 3 Tauri swap 10–14 w.

**Core recommendation:** do the seam first and keep Electron as the shell for one release cycle. After
decoupling the shell is disposable, so the Tauri swap becomes an isolated, deferrable, reversible
project. The RPC client is identical for Electron and Tauri, so nothing is wasted by waiting.

**Also flagged:** performance framing — Tauri wins on install size (~10–20 MB vs ~150–250 MB) and idle
RAM, but UI runtime perf is ≈ parity on Windows (WebView2 *is* Chromium) with possible Linux regression.
Backend RAM is unchanged (engine is still Node/Bun). Frame as "smaller and lighter", not "faster".

**New prerequisite workstream (not in v1):** standalone engine binary — `bun build --compile`
(preferred, needs spike) / Node 20+ SEA / ship `node` + JS (most reliable). Plus spawn+handshake model:
ephemeral port or unix socket/named pipe, ready handshake, crash supervision with backoff (Tauri
sidecar does not auto-restart).

## Design: file & system ops mediation (engine vs client authority)

User decided the model: **engine = authority for generated artifacts; client = authority for the user's
machine.** Exports are produced on the engine and fetched by the client; imports are read on the client
and uploaded; certs are generated on the engine, fetched and installed by the client.
Produced `File_Ops_Protocol.md` (companion to v2 §5 workstream 3).

**Key verifications:**
- **`src/ipc/importExport/registry.ts` is already string-in/string-out.** `ExporterFn.run(wsId,
  filePath)` does `fs.writeFileSync(filePath, string)`; `ImporterFn` does `fs.readFileSync(filePath,
  "utf-8")` → `JSON.parse`. `filePath` is a **pure transport detail** → 32 of 34 exporter/importer files
  change in one mechanical line each.
- **Exceptions (2/34):** `workspace-zip` both directions. `archiver` pipes to `createWriteStream(path)`
  and `unzipper.Open.file(path)` **requires a real file, not a buffer** → the blob store must be a real
  staging directory, not in-memory.
- **The correct pattern already exists in-repo.** `systemHandlers.ts:232` `dialog:openFile` returns
  `{name, size, base64, mimeType}` with a 1 MB cap, and is already used by `BinaryViewer.tsx:58`,
  `MultipartEditor.tsx:67`, `ProtoExplorer.tsx:147`. The model just needs generalising to the other ~11
  channels.
- **The real blocker:** `renderer/components/modals/ImportExportModal.tsx:100-117` round-trips
  `res.filePath` through React state and back into `ImportRequest.filePath`. For a remote engine that
  path is meaningless. It also means the file is **read twice** (preflight + run) — a staged-blob model
  fixes that as a side effect.
- **8+ path leaks** in return values: `ExportResult.filePath`, `PreflightResult.filePath`,
  `ImportRequest.filePath`, `tls:generate` → `{certPath, keyPath}`, `tls:exportCert`, `tls:importCert`,
  `tls:importKey`, `runner:exportReport`, `capture:shareJson`, plus `renderer/types/window.ts:44,45,191`.
- **Behavioural leak:** `importers/environments-dotenv.ts:55` derives an entity display name from
  `filePath.split(/[/\\]/).pop()` — leaks a fragment of the user's local path and produces garbage under
  a remote engine. Must become an explicit client-supplied `filename`.

**Design delivered:** a blob layer (`blob.put/stat/read/release`) with a real staging dir on the data
volume, ~1 hr TTL sweep, inline-below-1MB optimisation, and dialog-first ordering. Egress = 5 channels,
ingress = 4, privileged = 1, split = 3, client-only = 4.

**Certificate lifecycle is the genuinely new design work** (3–5 d):
- Two halves on two machines that can **drift** — user regenerates the CA on the engine while the client
  still trusts the old one → opaque TLS errors. Mitigation: `tls.status` returns a **SHA-256
  fingerprint**; client stores what it installed and compares.
- Privilege matrix: Windows `certutil -addstore -user Root` (no elevation), macOS `security
  add-trusted-cert` (no elevation), **Linux `sudo update-ca-certificates` needs root** → prefer
  `trust anchor` (p11-kit) or `pkexec`. Verify.
- **Firefox does not use the OS trust store** (own NSS store). Installing via `certutil`/`security`
  makes Chrome/Edge/Safari work but **Firefox still fails**. Top-tier support burden for a proxy tool —
  handle deliberately in the UI.
- `tls:removeCert` becomes two-sided (engine unlink **+** client un-trust); must report partial success.

**Effort:** v1 workstream 3 revised **1–2 w → 1.5–2.5 w**. Tier 1 absorbs it: **10–15 w** (was 10–14).

### Fifth production bug found (and fixed)

**`replayRequest` could fail with a spurious 400 / "socket hang up" on a later request to the same
origin.** `src/proxy/serverReplay.ts` sent `connection: close` but did not pin an agent, so when the
upstream answered `keep-alive` (servers routinely ignore the request's close) Node returned the socket
to the **global** pool; the next request on that socket was rejected by the server with
`HPE_CLOSED_CONNECTION: Parse Error: Data after 'Connection: close'`.

- Symptom in tests: `checkUrl` returned `{statusCode: 400, body: ""}` or hung for ~6 s then
  `socket hang up`. It only reproduced in a **full-file run**, never in isolation — a classic
  cross-caller socket-pool interaction.
- **Fix:** `agent: false` on the request in `replayRequest` — each replay gets its own non-pooling
  agent, so `connection: close` is actually honoured. `serverReplay.ts` is now 100% statements.
- **Regression test:** "keeps working across repeated sends to the same origin" — 10 sequential
  replays to one origin must all be 200. It failed deterministically *before* the fix and passes after.
- Note: `healthbar:checkUrl`'s live-endpoint test now uses a **dedicated server**, because it shares
  Node's global agent with `request:replay` and is otherwise exposed to the same hazard.

**Diagnosis technique worth reusing:** Node's HTTP *server* emits a `clientError` event for malformed
requests. Adding `server.on("clientError", (err, socket) => …)` to the test server gave the exact
`err.code` (`HPE_CLOSED_CONNECTION`) and message that explained the whole failure. Do this before
guessing at flakiness.

### Three more production bugs found (and fixed) — #7, #8, #9

**#7 — `publishEntities` double-counted staged paths.** `simple-git`'s `status()` reports a

## Seventh pass — settings mutations (and a third bug class)

Closed `HAPPY_PATH_COVERAGE.md` §5 item 1: the Settings screen was the last path that mutated
**live state** with nothing behind it. New file
`bifurc/tests/integration/settingsMutations.integration.test.ts` — **30 tests**, all passing.
It registers the real `config:save` / `server:*` / `theme:*` / `zoom:*` / CRUD handlers against
the real proxy and drives them with real TCP sockets (only Electron and `@/main` mocked).

What it pins:
- changing the proxy port in Settings **moves the running server** — the old port stops
  answering, the new one serves the same mock, and the port is persisted to `app.json` and
  reported by `server:status`;
- an unchanged port does not take the server down; `server:restart` / `stop` / `start`;
  `server:start` binds the port from settings, not a default;
- toggling TLS reloads the CA (`isCALoaded()` false → true → false);
- changing the companion port moves the real WebSocket server (round trip on the new port,
  old port closed);
- theme and zoom persist to disk, round-trip, and clamp to `[-5, 9]`; `zoomLevelSetByUser` set;
- **a live config mutation reaches the running proxy with no restart** — `mock:add` /
  `mock:update` / `mock:delete` are served (or stop being served) immediately, and switching
  the active workspace re-routes the same URL.

**Bug 12 — CRUD mutations were invisible to the running proxy.** `entityCrudFactory` did
`saveConfig(cfg); reloadConfig();` and only *then* wrote the entity file and called
`syncEnabledSet()`. `reloadConfig()` snapshots the enabled-sets out of `enabled.json`, so
`workspaceCfg()` filtered the new entity straight back out of routing. Consequences: a mock you
just added was **not served**, and a mock you just **deleted kept being served**, until an
unrelated action (a settings save, a workspace switch, an app restart) happened to reload.
Fixed by moving `reloadConfig()` **after** every on-disk write in the `add` / `update` /
`delete` handlers. Invisible to the old tests because they asserted on the handler's *return
value* — the config object was always correct; the **running server** was stale.

**Also: `coreHandlers.ts` reached `restartCompanionServer` through a bare alias `require()`**
(`require("@/companion/companionServer")`). It works in the packaged app only because
`tsc-alias` rewrites `require()` in the build output — so a user-facing path depended on the
build pipeline, and it was unresolvable for the test runner (no cycle exists to justify the
laziness). Promoted to a static import; that is what makes the companion-port test possible.

**Gotchas learned:**
- `workspace:add` and `mock:add` are **async** handlers — `invoke()` returns the Promise, so
  `await invoke(...)` is required or `.id` reads `undefined`.
- The integration `proxyHarness.createWorkspace()` writes a mapping for `app.localhost`, so a
  request that matches no mock still returns **200 from the real upstream** — assert on the
  *body*, not on the status, when proving "the mock is not there yet".
- When mutation-checking, **remove** the line under test rather than adding a second copy —
  my first attempt at the delete mutation only *added* an early `reloadConfig()` and the late
  one still ran, so the mutation silently passed.
