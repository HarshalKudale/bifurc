## Two anomalies from the previous session's live run, attributed — and one of my own notes was wrong

The entrypoint itself worked last session, but two numbers did not add up. Both were **the probe, not the
product**, and both were settled by measuring rather than reasoning:

- **`GET /deep/route -> 404`.** The SPA fallback keys on the request's `Accept` naming `text/html`, and **curl's
  default `Accept` is a wildcard**. The same request with a document `Accept` returns `200`. The server was right.
- **`healthcheck exit=23`.** The script's own status is `1` (nothing listening) / `0` (listening), measured
  against a known-free port, and **`23` is not a Node exit code**. Bash propagates node exits faithfully
  (`0`→0, `23`→23, `1`→1, controlled). So `23` was a **mislabelled `$?`** from another command in that
  one-liner — which was visibly degraded anyway (a proxy-injected curl 502, and `/tmp` meaning *different
  directories* to Node (`I:\tmp`) and Git Bash).

**The correction:** I had recorded the entrypoint's `SIGTERM` exit as **`143`, "the child's `128+15`
propagated"**. That number came from **the shell**, not from the entrypoint. Measured directly — a child that
installs a `SIGTERM` handler and is then killed — a Node process **on Windows cannot catch `SIGTERM` at all**:
`process.kill(pid,"SIGTERM")` terminates unconditionally, the handler never runs, and the parent sees
`code=null signal=SIGTERM`. So the forwarding path is **not measurable on this machine** and is exercised by
`docker stop` in the container. The record now says that instead of claiming a measurement. Same class of error
as the standing rule: *an exit code from the shell is not the process's exit code.*

## The headline find: `npm ci` was broken, so the image could never have built

The `Dockerfile`'s manifest `COPY`s must be **exactly the workspace set `package-lock.json` describes**, because
`npm ci` validates that set. The committed lockfile was stale in two ways, and **neither was reachable before
because the build had never been run**:

- it still described **`apps/web`** — the GUI package at its pre-extraction path, `@bifurc/web`, with
  `node_modules/@bifurc/web` linked to a directory that **no longer exists** — and its root `workspaces` field
  still read `["packages/*","apps/*"]`;
- it did **not** describe `packages/gui` (`@bifurc/gui`), although `workspaces: ["packages/*"]` matches it.

Measured both ways: **with** `packages/gui`'s manifest copied → `EUSAGE: Missing: @bifurc/gui@0.1.0 from lock
file`; **without** it → npm follows the dead `apps/web` link and fetches `@bifurc/gui@*` from the public
registry, `404` (a private name). So `DOCKER.md`'s *"treat the Dockerfile as reviewed rather than exercised"*
was concealing a **deterministic failure**, not an untested path — and the same staleness breaks `npm ci` for a
fresh clone and for CI, independently of the image.

**Repair, measured:** `npm install` once → **one key removed, two added, zero version changes**
(`node_modules/@bifurc/web` out; `packages/gui` + `node_modules/@bifurc/gui` in; root `workspaces` →
`["packages/*"]`). Afterwards `npm ci --ignore-scripts` against the image's exact five-manifest set passes
(`added 759 packages`, exit 0). `Dockerfile` now copies five manifests, with the rule stated as a comment,
because the list is a coupling and the next workspace will re-break it silently.

## ⚠ The environment trap that cost two restores: `git rm` under `scripts/` wipes the directory

`rm` is a shell **function** here (a "safe-delete" shim: `CODEBUDDY_SAFE_DELETE_SANDBOX=1`, with `rm`, `rmdir`
