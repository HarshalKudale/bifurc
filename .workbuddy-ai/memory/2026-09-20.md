# 2026-09-20 — Bifurc

## §5c-viii — the static guard §5c needed and did not have

**What was built.** A new test in `tests/ipc/handlers.test.ts` inside the `registry coverage` describe:
*"registers nothing at module scope — the §5c guard"*. It closes the checklist item *"Extend the ratchet
so it can see shell-registered engine commands"*, which had been the open follow-up to the §5c pass.

**It asserts the architectural rule, not the historical bug:** *registration goes through
`register*Commands(registry)`, so the `commandRegistry` singleton is never registered directly.* That is
not a style preference — it is what makes the engine containerisable. A consumer that supplies its own
registry (P9's Docker engine, a test's own registry, `createInProcessTransport(registry)`) can only see
commands registered **explicitly against it**. `createEngine()` registering no commands by design is the
same statement from the other side.

**Mechanism:** `import.meta.glob("../../src/**/*.ts", { query: "?raw", import: "default" })` plus the
same for `packages/engine/src`, then require `/^\s*commandRegistry\.register\(/m` to match nothing.
`vitest.config.ts` is a real Vite config so `import.meta.glob` is available; used lazily (no `eager`)
so ~152 source files are not inlined into the test bundle. Avoided `fs` deliberately — it is automocked
at the top of that file (`vi.mock("fs")`).

### Two things measured rather than assumed

**1. It is strictly stronger than the grep the pass itself used.** The pattern matches a *statement* — a
line whose first non-whitespace content is the call — so it catches module scope at column 0 **and** a
module-scope call wrapped in a top-level `if`/`try`. Mutation-verified with a scratch
`src/ipc/__guardProbe.ts`:

| probe shape | `grep -rn '^commandRegistry.register(' src/` | the guard |
| --- | --- | --- |
| column 0 | matches | fails, names the file |
| indented inside `if (process.env.NEVER_SET)` | **exit 1, no match** | **fails, names the file** |

So every slice's verification grep would have missed the indented variant. Recorded as a `TRAPS.md`
entry. Two shapes the guard still does *not* catch, stated in the test rather than implied: a call
preceded by other code on the same line, and an indirect alias (`const r = commandRegistry; r.register`).

**2. The anti-vacuity guards are the load-bearing part.** A wrong glob returns `{}` → the joined content
is `""` → `match()` is `null` → the assertion passes. A guard that reads as coverage while covering
nothing is *worse* than none, because it gets quoted. So the test asserts, in order:

1. the reader found **>20 files** in each tree;
2. a **positive control**: `/^\s*registry\.register\(/gm` matches **>30** times in the engine — the
   parameterised form is plentiful, so the reader demonstrably sees real registration code;
3. therefore a zero for the *singleton* form means "not written that way", not "content never loaded".

**Mutation-checked both ways**: the column-0 probe fails the guard; the indented probe fails it; deleting
the probe restores 167/167 green.

**Measured:** `npm run typecheck` EXIT=0; `handlers.test.ts` **167/167** (was 166); full suite
**101 files / 2,509 tests — 2,468 passed, 40 skipped, 1 failed** — **+1 over the baseline and the +1 is
this test and nothing else**.

confirmed it rather than assuming it. `app.checkUpdate` is the one SPLIT, and the block is real:

## P6 work item 5 — the e2e fixture asserts its own data-dir isolation

**Why this and not step 3.** Step 3 (delete `registerIpcHandlers()`) is unblocked on the §5c side but still
blocked on `app.checkUpdate` (SPLIT → P12) and the dead `src/ipc/importExportHandlers.ts`, so it cannot be
finished from here. Work item 5 is self-contained and was explicitly called out in the plan as a **High**
risk with a named mitigation, so it is the highest-value thing left that can actually be completed.

**The plan's premise is only half true, and the missing half is the whole subtlety.** Work item 5 says the
engine "derives its data dir from `app.getPath("userData")`, which that override already controls". `src/main.ts:256`
does call `setDataRoot(app.getPath("userData"))` — but `store/workspaceFs.ts#dataRoot()` and
`store/appSettings.ts#settingsPath()` both **short-circuit on `%LOCALAPPDATA%` on win32 before consulting
the data root**. So the Electron path has **two** inputs, not one. Measured with the fixture's env, driving
the engine's real built resolvers:

| resolver | resolves to |
|---|---|
| `workspaceFs.dataRoot()` (entity data) | `<temp>\Bifurc\data` |
| `paths.dataDir()` (settings / `app.json`) | `<temp>\electron-userdata` |
| `workspaceFs.wsDir("default")` | `<temp>\Bifurc\data\default` |
| `paths.platformDefaultDataDir()` | `<temp>\Bifurc` |

Both roots are inside the temp dir, so isolation holds — but they are **not the same directory**. That is
the defect documented in `packages/engine/src/index.ts`'s `EngineOptions.dataDir` docblock and tracked as
`plan/03` work item 8, deliberately untouched because correcting the order would move existing Windows
users' data. It also explains why the fixture's seeded sample data is found at all:
`writeSampleWorkspace(dataRoot)` writes `<dataRoot>/<wsId>/…` and puts `app.json` in the *parent* — i.e. it
targets `dataRoot()` and `settingsPath()`, not `dataDir()`.

**What landed.** A containment assertion in the `electronApp` fixture's *setup* — not a separate opt-in
fixture, so a new spec cannot forget it. It probes the app process once via `app.evaluate` for
`app.getPath("userData")`, `process.env.LOCALAPPDATA` and `process.platform`, then requires each to be
inside the temp dir. It asserts **containment of the inputs rather than a re-derived path**, because both
consumers only `path.join` relative segments onto one of the two, so input containment implies path
containment — and a re-derivation would be a copy that can drift from the original silently. `main.ts`
consults neither `--data-dir` nor `BIFURC_DATA_DIR` (`resolveDataDir` is for the CLI/Docker entrypoints), so
those branches are not on this path and are not probed.

**Scope, stated because the guard is narrower than "the data dir is correct":** this is the **shell
wiring**. The engine's own resolution order is covered by `tests/store/paths.test.ts` (all four
`resolveDataDir` branches, `platformDefaultDataDir`, `setDataRoot`/`dataDir`) and
`tests/store/workspaceFs.test.ts`. e2e proves the wiring; the unit suites prove the order.

**Verification, since the e2e suite cannot run in this sandbox.** `npm run typecheck:e2e` → **EXIT=0**. Then
a throwaway script (written to `%TEMP%`, run, deleted — not committed) drove the engine's **real built
resolvers** under the fixture's env and confirmed all four values above land inside temp. The **negative
case** is what proves non-vacuity: with the override removed, `dataRoot()` escapes to
`C:\Users\wrath\AppData\Local\Bifurc\data` — the developer's real profile — and the predicate rejects it.
Five predicate boundary cases (root, descendant, sibling, parent, real profile) also pass. **An unset
`%LOCALAPPDATA%` on win32 is an error, not a skip**, because the engine would fall back to the real profile.

**The 11 specs are untouched** — `git status` shows only `e2e/fixtures/electronApp.ts` modified, as work
item 5 requires. The e2e *run* remains uncaptured and is still the real gate (the checklist's separate
"11 e2e specs pass, unmodified" item stays open).

## Step 3f — the last key, and the seam is complete

**The audit found the plan had recorded the disagreement but not the design space.** Three designs
satisfy the split, and they differ in what they change — a frozen protocol command, or the client's
public API:

| | Fetch runs | Engine command | `registerIpcHandlers()` |
|---|---|---|---|
| **A** | engine | added | still needs the channel |
| **B** | shell (status quo) | deleted from the protocol | still needs the channel |
| **C** | preload, no IPC | deleted | **unblocked** |

**The consequence nobody had recorded:** `src/ipc/handlers.ts:155` says `registerIpcHandlers()` "cannot
be deleted yet: `app.checkUpdate` still needs a channel". That is false for C and **irrelevant for A and
B** — because A and B keep a local channel, and a local channel needs a registration point for as long as
it exists. So resolving this split does **not** unblock step 3 under A or B, and the honest statement is
that `registerIpcHandlers()` is **reduced**, not deleted.

**Also found: a latent silent bug.** `packages/client/src/index.ts:476` was
`checkUpdate: () => call("checkUpdate", {}) as ReturnType<BifurcApi["checkUpdate"]>`. The cast is a lie —

which is falsy, so the About panel renders **"you're up to date"** with `latestVersion` undefined. A
silent wrong answer, not an error — which is exactly why the ratchet pinned it.

## D16 decided — the port rule, and two collisions it exposed

**Owner's rule:** a workspace's proxy port **defaults to 80**; if 80 is taken (by another active workspace, or by
anything else), **count up from 8080** until a bind succeeds. The user can customize the port per workspace. The
webhook port follows the same shape from `9101` *(not specified — resolved by analogy, flagged in the plan as such)*.

**Recorded in:** `plan/14` §3 (D16, full rule + resolution order), WI 1, WI 5, acceptance criteria (8 new items),
risks (4 new rows); `plan/00-decisions.md` (D16 row now decided, "nothing from this pivot is still open");
`plan/13-checklist.md` Section 7.5 (WI 1 / WI 5 rewritten, 5 new port criteria); `plan/README.md` (a "Ports (D16)"
paragraph); `plan/10-phase-9-docker.md` (3 corrections).

**Two collisions the rule exposed, both found by checking the code rather than by reasoning:**

1. **The container cannot bind 80 at all.** `plan/10` mandates `USER bifurc` (non-root) and lists "runs as
   non-root" as an acceptance criterion — and an unprivileged process cannot bind a port below 1024. So the image
   now sets **`BIFURC_PROXY_PORT=8080` explicitly** rather than leaning on the fallback, because an *explicit* port
   fails loudly if taken, which is the right behaviour for a published container. Same root cause makes the
   fallback the *normal* path on the macOS/Linux desktop, where the current default of 80 already cannot bind.
   The consequence worth keeping: **the allocator must advance on `EACCES` as well as `EADDRINUSE`**, or every
   workspace dies at startup on those platforms.
2. **`preflight()`'s port check is fatal, and the second workspace is the normal case.** `startup.ts:90-99,122`
   returns `{ok:false, code:"port-in-use"}` and `plan/10`'s entrypoint exits non-zero on any `ok:false` — so a busy
   80 would refuse to start exactly the configuration P14 exists to enable. WI 5 now makes it non-fatal for a
   *default* port and keeps it fatal only for an *explicitly configured* one. `checkPortAvailable`'s hint text
   ("Free the port, or change the configured port in settings") is wrong for the default case too.

**Third trap recorded, from reading `portUtils.ts`:** `checkPortInUse` is a **probe** (bind, close, report), so
using it to allocate is probe-then-bind — a TOCTOU race whose failure surfaces as an unexplained dead proxy.
Allocation must be driven by the real `listen()`. `checkPortInUse` stays for *reporting* and for
`application.checkPort`, which are questions rather than allocations.

**Also corrected while there:** `plan/10`'s `ENTRYPOINT` was still `engine/index.js` → now
`engine/runtime/host.js`, and its §4 port table went from 2 rows to 4 (N proxy ports, N webhook ports, one RPC
port) with a note that the recommended deployment keeps it at one proxy row per container.

**Verified after writing, per `TRAPS.md`:** grepped for *every* marker string, not just the last. Two markers
reported 0 on the first pass — both were my grep patterns being wrong (case, and a backtick between `=8080` and
`**`), not missing edits. Re-grepped correctly: all landed.

## D16 revised — per-environment base port (owner's correction)

**The owner replaced my rule.** I had written "default 80, then jump to 8080". The corrected rule is a
**per-environment base port with a contiguous increment**:

| Environment | Base | Three workspaces get |
|---|---|---|
| **Windows** | `80` | 80, 81, 82 |
| **Linux, macOS, container** | `8080` | 8080, 8081, 8082 |

Overridable per workspace (fails loudly if taken), and the *base* is overridable via **`BIFURC_PROXY_BASE_PORT`**
(so a container can pin its published port without losing the increment). Webhook base stays `9101` on every
platform — already above 1024, so no split needed.

**Why it is the better rule, and what it changed in my reasoning:** the privileged-port problem is solved by the
**base**, not by the retry loop. On Linux/macOS/Docker the default path never attempts a port below 1024, so
**advancing on `EACCES` is now defensive rather than load-bearing** — I had it as a High risk and a hard
requirement. It stays (it guards a sub-1024 *override*), but downgraded. The genuinely load-bearing new invariant
is: **the base constant is the ONLY platform-dependent value in the allocator.** If per-platform logic appears in
the scan, the override path or the UI, D16 has been mis-implemented — and the acceptance criteria now assert
*both* bases in one test so a second branch surfaces as a failure.

**Also corrected by the revision:** `BIFURC_PROXY_PORT=8080` → **`BIFURC_PROXY_BASE_PORT=8080`** (in `plan/10`'s
Dockerfile and notes). The old name read as "pin one workspace's port", which would have *disabled* the fallback;
the new one sets the base. `plan/10`'s note no longer frames it as a non-root workaround, because Linux already
derives 8080 — it now exists to *state* the published port rather than infer it.

**One interaction worth keeping:** with the webhook base at `9101` and `9102` reserved for the unimplemented gRPC
placeholder, the **second** workspace's webhook skips to `9103`. Asserted in the criteria, since it is the kind of
off-by-one that looks like a bug when it appears.

**Files touched:** `plan/14` (§3 D16 rewritten, WI 1, WI 5, acceptance criteria, risks — the EACCES row replaced by
a "platform branch leaks" row), `plan/00-decisions.md`, `plan/13-checklist.md` (WI 1, WI 5, WI 6, criteria),
