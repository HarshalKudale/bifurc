# 2026-09-20 — Bifurc

## §5c-viii — the static guard §5c needed and did not have

**What was built.** A new test in `tests/ipc/handlers.test.ts` inside the `registry coverage` describe:
*"registers nothing at module scope — the §5c guard"*. It closes the checklist item *"Extend the ratchet
so it can see shell-registered engine commands"*, which had been the open follow-up to the §5c pass.

**It asserts the architectural rule, not the historical bug:** *registration goes through
`register*Commands(registry)`, so the `commandRegistry` singleton is never registered directly.* That is
not a style preference — it is what makes the engine containerisable. A consumer that supplies its own
registry (P9's Docker engine, a test's own registry, `createInProcessTransport(registry)`) can only see
commands registered **explicitly against it**. `createEngine()` registering no commands by design is the
same statement from the other side.

**Mechanism:** `import.meta.glob("../../src/**/*.ts", { query: "?raw", import: "default" })` plus the
same for `packages/engine/src`, then require `/^\s*commandRegistry\.register\(/m` to match nothing.
`vitest.config.ts` is a real Vite config so `import.meta.glob` is available; used lazily (no `eager`)
so ~152 source files are not inlined into the test bundle. Avoided `fs` deliberately — it is automocked
at the top of that file (`vi.mock("fs")`).

### Two things measured rather than assumed

**1. It is strictly stronger than the grep the pass itself used.** The pattern matches a *statement* — a
line whose first non-whitespace content is the call — so it catches module scope at column 0 **and** a
module-scope call wrapped in a top-level `if`/`try`. Mutation-verified with a scratch
`src/ipc/__guardProbe.ts`:

| probe shape | `grep -rn '^commandRegistry.register(' src/` | the guard |
| --- | --- | --- |
| column 0 | matches | fails, names the file |
| indented inside `if (process.env.NEVER_SET)` | **exit 1, no match** | **fails, names the file** |

So every slice's verification grep would have missed the indented variant. Recorded as a `TRAPS.md`
entry. Two shapes the guard still does *not* catch, stated in the test rather than implied: a call
preceded by other code on the same line, and an indirect alias (`const r = commandRegistry; r.register`).

**2. The anti-vacuity guards are the load-bearing part.** A wrong glob returns `{}` → the joined content
is `""` → `match()` is `null` → the assertion passes. A guard that reads as coverage while covering
nothing is *worse* than none, because it gets quoted. So the test asserts, in order:

1. the reader found **>20 files** in each tree;
2. a **positive control**: `/^\s*registry\.register\(/gm` matches **>30** times in the engine — the
   parameterised form is plentiful, so the reader demonstrably sees real registration code;
3. therefore a zero for the *singleton* form means "not written that way", not "content never loaded".

**Mutation-checked both ways**: the column-0 probe fails the guard; the indented probe fails it; deleting
the probe restores 167/167 green.

**Measured:** `npm run typecheck` EXIT=0; `handlers.test.ts` **167/167** (was 166); full suite
**101 files / 2,509 tests — 2,468 passed, 40 skipped, 1 failed** — **+1 over the baseline and the +1 is
this test and nothing else**.

## Why this and not step 3

Step 3's remaining act — deleting `registerIpcHandlers()` — is **genuinely blocked**, and this turn
confirmed it rather than assuming it. `app.checkUpdate` is the one SPLIT, and the block is real:

- `AppCheckUpdateParams` is `z.object({}).strict()` — **no params**, so an engine half cannot be told the
  client's platform;
- yet the schema's `downloadUrl` / `assetName` are *platform-matched* values, and `AppCheckUpdateResult`
  also lacks the `currentVersion` / `hasUpdate` the shell's success branch returns.

So a correct engine half is unwritable against that schema: it would have to guess `process.platform`,
which in a container is the *engine's* platform and not the client's — precisely the wrongness the split
exists to avoid. Widening the schema to add a `platform` param would fight the protocol's own documented
decision that **P12 moves it fully client-side**, i.e. it would be work scheduled for deletion. Left
blocked, deliberately, with the reasoning written down.
