# 2026-09-23 — the browser could not authenticate, and that is why its connection died

## What the user reported, and what it actually was

They ran the headless host (`node packages/engine/dist/runtime/hostCli.js --data-dir ./data/ --ws-port 8080`),
opened the web GUI, and the connection died immediately. The engine's log said, once per attempt:

```
[host] rpc session refused (UNAUTHORIZED) from "unnamed": the first request must be "hello";
       refusing "config.get" on an unauthenticated session
```

And the browser console said:

```
main.tsx:38 Bifurc: no engine at ws://127.0.0.1:8080 — the first request must be "hello"; refusing "config.get"…
main.tsx:24 Bifurc: lost the engine at ws://127.0.0.1:8080 — Session closed: the engine closed the connection…
session.ts:188 Uncaught (in promise) EngineError: Cannot request(): this session ended.
```

**One root cause.** The host wraps its socket in `createAuthenticatedTransport`, which requires `hello` as
the **first** request and — per `plan/05` work item 5, *"auth failure returns `UNAUTHORIZED` and closes.
Never fall back to unauthenticated"* — **closes the session** when it is not. The browser's
`connectToEngine` went straight from `createBrowserTransport` to `createClient` and called `config.get`.

**Electron never hit this, and that is why it survived P6**: its transport is `in-process`, which has no
boundary and is therefore never wrapped. The browser is the first client that has to authenticate. I had
flagged exactly this a day earlier — *"the handshake belongs to the auth layer and is not wired into a
browser client yet (work item 2)"* — and then it was found by running the thing, which is the only way it
could have been found.

### The design was already written down, and already implemented

Two things made this a small fix rather than a design job:

- **`plan/06` names the mechanism exactly**: *"the handshake is a plain `request("hello", …)` on the raw
  transport **before `createClient()`** — so the client never learns it is remote, which is what P6 needs."*
  So the composition layer owns it, not the client.
- **`packages/client/tests/transports.test.ts` already does it** for the `ws` transport, in nine lines. The
  browser host was simply the one caller that never did.

That is the lesson worth keeping: **the fix was to copy an existing, tested call, and the search for it
should have started in the plan rather than in the failing code.** I found it by grepping `plan/` for
`hello` — after reading the engine's decorator.

## What changed

### 1. `HELLO_ACTION` moved to `@bifurc/protocol`

It was defined in `packages/engine/src/transport/auth/authenticated.ts` while its *schemas*
(`HelloRequestSchema`, `HelloResponseSchema`) lived in the protocol. So a browser wanting to send `hello`
had two options: hardcode `"hello"`, or import the engine — and importing the engine into a browser bundle
to learn a string is not an option.

Moved it beside the schemas, in `envelope.ts`. The engine imports it and **keeps its load-time guard** that
no *command* has taken the name — the guard stayed there because the *interception* is the engine's, so
"a command would be shadowed" is only a true statement where the interceptor lives.

### 2. The handshake, in `web/connect.ts`

`connectToEngine` is now **async**, and does three things in order: handshake (only when a token is given),
`createClient`, then **a probe**.

The probe is the part worth explaining. Without it, connecting with *no* token to an endpoint that requires
one **succeeds** — the handshake is skipped by design, so nothing has failed yet — and the container would
mount the entire UI before the first real request came back `UNAUTHORIZED`. That is the original bug's shape
exactly, so "connected" has to mean "the engine answered", not "the socket opened".

**Why the token is conditional, not always sent.** `HelloRequest.token` is optional *in the schema* because
`in-process` and `stdio` have no boundary and a token there would be security theatre — one schema serves
both. A token present means "this endpoint has an auth boundary"; absent means "this one does not". It also
keeps the browser usable against a plain, unwrapped `ws` server, where `hello` would be an `UNKNOWN_COMMAND`
— `hello` is deliberately not a registry command.

`ConnectError` carries a `failure` **kind** (`unreachable` / `unauthorized` / `version` / `refused`) rather
than one string, because `plan/08`'s criterion is that *"handshake failure, auth failure and version
mismatch all produce actionable UI, not generic errors"* — which needs the distinction to survive as data.
The engine's own message for a refused request describes the engine's rule rather than the user's problem,
so the classification replaces it rather than forwarding it.

### 3. `web/` is now a container

The ordering requirement has a consequence the user had already asked for independently: connect **first**,
then render. So `web/` gained:

| File | Role |
|---|---|
| `Container.tsx` | the connection form, the connected-state bar, and the `<App />` mount |
| `settings.ts` | the form's pure half — `toUrl`/`fromUrl`, load/save, defaults |
| `env.d.ts` | `__APP_VERSION__`, declared locally rather than reached for across a package boundary |
| `main.tsx` | mounts `<Container />` — now short, because the ordering lives in one place |

And `<App />` gained `AppProps { host?, connection? }` — **a prop, not a second global**, because D18's
premise is that `window.api` is the *only* thing that varies between hosts, and a UI reading a second
injected global would have two seams to keep honest. `host` drives one real thing today: `h-full` instead
of `h-screen`, because `h-screen` inside the container's flex column is 100vh regardless of the bar above
it, which pushes the bar off-screen. `connection` feeds `GlobalFooter`'s existing `rightContent` slot,
which is where `plan/08`'s risk table says connection state belongs.

**This answers D18's last open question.** It was recorded as deliberately undecided: *"how does the shared
`<App />` know which host it is in?"* — three candidates, and the answer is the third (a prop), because the
other two would either make it a **surface** decision or add a second injected global.

### 4. The console errors

- `Uncaught (in promise) EngineError: Cannot request(): this session ended` — **`loadConfig` had `try/finally`
  and no `catch`**, so a rejected `config.get` propagated out of the callback and the effect's `.then()` had
  nothing to catch it with. `refreshServices` was the same. Both now catch.
- **Catching was not enough on its own.** A caught error nobody renders is a silent failure, and the UI sat
  on "Loading workspace…" forever — *the same screen a slow engine shows*, so a user cannot tell the two
  apart. `App` now renders `loadError` where the loading message was.
- `Bifurc: no engine at ws://…` for an auth failure — gone with the classification above; the form now says
  which of the four things went wrong.

### 5. The MVP CLI, refined against the plan

The user's `--ws-host` / `--ws-port` addition was already right, and I checked the rest against the plan
rather than against taste. What the host already did: produce the token (`ensureEngineToken`), pass `auth`
to both socket and ws servers, report the *resolved* address (`rpc.url`, so `--ws-port 0` works), and hold
`ws.ts`'s bind guard — a non-loopback bind needs `tls: true` **and** TLS config, so `--ws-host 0.0.0.0`
alone is refused rather than exposing an unauthenticated surface.

**One real gap, and it is the one the user hit:** `ensureEngineToken()` returns `{token, path, source}` and
`host.ts` used only `.token` — **the path was computed and thrown away**. So the only way to find the token
was to know the filename and guess the directory, which is what the first headless run did.

Added `tokenPath?: string` to `WorkspaceHostStatus` and a `notice`, so the container log now says:

```
[host] rpc endpoint: ws://127.0.0.1:8099
[host] engine token: C:\Users\wrath\AppData\Local\Temp\bifurc-hostcheck\engine.token
```

**The path, never the value.** A log is read by more people than a `0600` file is, and a token pasted into an
issue tracker is a credential in an issue tracker. It is also absent when the token came from
`BIFURC_ENGINE_TOKEN` or `--token-file`, because then the operator already knows where it is.

## The verification, which is the part that matters

**The headless host is a plain Node process, so unlike Electron I could run it.** That turned the whole thing
from "should work" into a measurement:

| Step | Result |
|---|---|
| `config.get` with **no** handshake | `ERROR UNAUTHORIZED` — *the first request must be "hello"* — and **socket state 3 (CLOSED)** |
| `hello` with the real token | `ok, engineVersion=0.0.0 sessionId=f3c1611b-…` |
| `config.get` **after** `hello` | `ok`, with the real config — and **socket state 1 (OPEN)** |
| `hello` with a wrong token | `UNAUTHORIZED` — *the hello token is missing or does not match* |

The first row is the user's bug reproduced exactly, including the socket closing; the third is the fix. Both
against the real artifact they are running.

**And the mutation check the repo requires.** Disabling the handshake condition (`if (false && …)`) and
re-running `web/tests/connect.test.ts` failed **exactly two** cases — *"authenticates before the first real
request, so the session survives"* and *"classifies a protocol major mismatch as `version`"* — while the six
others passed untouched. That is the shape a good assertion set has: the mutation is caught by the cases that
should catch it, and nothing else moves.

## One test-side lesson

`tests/renderer/App.test.tsx` broke the moment `App` gained a `loadError` branch: the hook's `vi.mock` did
not provide the field, so it was `undefined`, and `undefined !== null` is **true** — the error screen
rendered and both cases failed looking for a title bar.

**The mock was wrong, not the guard.** A `vi.mock` factory returns an untyped object literal, so TypeScript
cannot notice that it no longer matches the hook's return shape; the only thing that notices is a consumer
reading the field. Fixed the mock and left the guard strict (`!== null`), because loosening production code
to accommodate an incomplete test double is backwards.

## The browser verification — and the assumption it retired

For two days I have written *"a real `WebSocket` in a real page is work item 6's Playwright job, and the
owner runs it"* into files, tests and records. **That was wrong, and I never checked it.**

`agent-browser` is not installed here, and a global `npm install -g` would break the runtime-isolation rule.
But the project **already has Playwright**, and Chromium was already in the cache — just at revision 1243,
while Playwright 1.60 expects 1223. One `executablePath` closes that gap:

```js
chromium.launch({ headless: true, executablePath: LOCALAPPDATA + "/ms-playwright/chromium-1243/chrome-win64/chrome.exe" })
```

**Headless Chromium runs fine from the agent shell.** So the loop is closed without the user, and the
standing rule about shell-bound commands stays intact — that rule is about Electron, a GUI and a real GPU
process, none of which a headless browser needs.

**What the check does**, against a real headless host on a real socket:

| Step | Result |
|---|---|
| the connection form renders | heading *"Connect to a workspace host"*, 3 inputs, 1 button |
| Connect succeeds | the form is **gone**; the body reads *"Connected to ws://127.0.0.1:8080 / Disconnect"* |
| the shared UI mounts | the connected bar and the footer endpoint are present |
| accept the terms → the shell | `nav` 1, `main` 1, **73 buttons**, *"Bifurc · W1 Workspace 1 · Search… Ctrl K"* |
| **console errors** | **0** |
| **uncaught page errors** | **0** — this is `session.ts:188`, gone |
| **console warnings** | **0** |

The two numbers that matter are the last three. The user's report was three console errors; two are now
structurally impossible and the third is measured absent. **A unit test cannot see any of this** — a rejected
promise inside a React effect never reaches the suite, which is exactly why the `loadConfig` gap survived.

### Two things the first run got wrong, both about the instrument

1. **One 404 remained, and my own listener could not see it.** `page.on("response")` reported **0** failed
   responses while the console reported a 404 — because Chromium requests `/favicon.ico` itself, outside the
   page's network context. Fixed by capturing `consoleMessage.location()`, which carries the URL the message
   text omits. It was the favicon; `web/index.html` declared no icon, so the browser asked for the default.
   **Now set from script in `web/main.tsx`, reusing the shared UI's `icon.png`** rather than shipping a
   second copy — `index.html` cannot reference it, because Vite resolves an `href` relative to the host's
   root and the file lives in `packages/gui`.
2. **A fixed `waitForTimeout(5000)` produced a false negative.** The second run sampled mid-load and showed
   `nav 0 / main 0 / "Loading workspace…"` — which reads as a broken shell and was purely the app being
   slower than my sleep (the first run passed only because its module graph was warm). Replaced with
   `waitForSelector("nav", { timeout: 30000 })`: **a selector either appears or it does not**, and that
   distinction is not available from a duration.

### The generalisable lesson

**"The owner runs it" is a claim, and it was never tested.** For two days it shaped what I wrote into tests
(`"What it still cannot cover is a real WebSocket in a real page"`) and it was false — the tooling was one
`executablePath` away the whole time. Before writing "this cannot be verified here" into a file, spend one
command checking whether it can. A constraint stated in a comment outlives the constraint.

## Reconnect — and the three defects the check found in code I had just written

`plan/08`'s headline criterion: *"disconnect/reconnect works; the UI never silently freezes."* Built as:
`lastSeq` tracked in the client's hub and exposed non-enumerably (the `close()` pattern, so
`Object.keys(client)` still equals `window.api` and the P5 surface test is untouched); `hello` carrying it on
a reconnect; `hello`'s `replayedFrom` / `resyncRequired` finally *kept* rather than parsed and discarded; a
backoff loop in the container; and `App` re-fetching when the session's `generation` changes.

**Then I ran it, and it found three things in code I had just written and already believed.**

### 1. The UI was unmounting during the outage, while the comment said the opposite

`UI still mounted: 0`. The container rendered a **replacement tree** while reconnecting, so `<App />`
unmounted and every open tab and draft was discarded — for an outage the user may not have noticed. And the
comment right beside that code read: *"The UI stays mounted while reconnecting, deliberately."*

**The comment described the intent; the code did the opposite, and only running it could tell me.** Fixed by
merging the connected and reconnecting branches so `<App />` is rendered in both and the banner varies above
it. `nav` is now `1` during the outage *and* after recovery.

This is the same failure as the earlier "narrative written from a working tree" trap, in a different costume:
prose next to code is not evidence about the code.

### 2. Uninstalling `window.api` under a mounted UI is a `TypeError`, not a graceful stop

Two uncaught errors: `Cannot read properties of undefined (reading 'getConfig')`. The drop uninstalled the
global, and the still-mounted UI then read `undefined.getConfig`. **A dead client is better than no client**:
left installed, the same call *rejects* with the client's own "this session ended" — a state the UI renders —
whereas `undefined` throws. Removed the uninstall; `0` uncaught errors.

### 3. `loadError` was any-load, so a refresh failure blanked the workspace

A refresh that failed mid-outage replaced the whole shell with "Could not load this workspace", *while the
banner above it said "reconnecting"*. `loadError` is now a **first-load** failure: once a load has succeeded,
a later refresh failing is not the user's to fix, and the reconnect banner is the right place for "the host is
away".

### 4. And a fourth, found by the promoted script rather than the temp one

`refreshConfig` had no `catch`, and my effect called it with `void refreshConfig()` — **`void promise` does
not catch**; it discards the promise, rejection and all. The console showed
`Uncaught (in promise) EngineError: Cannot request(): this session ended`, which is precisely the class of
error this whole line of work exists to remove. `refreshConfig` now swallows its own failure, and the
docblock says why: every caller is a background refresh, so none can act on a rejection.

**Four defects, all in code written minutes earlier, all invisible to `tsc` and to 471 passing tests.** The
browser check is not a nicety.

### The token rotation is a design constraint, not an edge case

`ensureEngineToken()` generates a token on **every** host start, so a restarted host is unreachable with the
old token — and the reconnect loop would have spun forever against one that can never work again. So the loop
now distinguishes **transient** from **terminal**: `unauthorized` and `version` return to the form with the
actionable message (which already says the token is regenerated per start), and everything else retries. Both
halves are asserted in `scripts/verify-web-reconnect.mjs`, which starts and kills the host itself.

### Verified

`npm run verify:web:reconnect` → **PASS**, exit 0: shell reached, engine version in the footer, banner on the
drop with the UI still mounted, **automatic recovery** on a same-token restart, and a rotated token stopping
the loop with the token message. **0 uncaught page errors.**

## The 105 type errors — one omitted type argument

I had described this root cause twice as "`useProtocolEditor`'s inference, lost to two `as any` casts". That
was **half right**, and the missing half is the interesting part.

`ProtocolEditorConfig` is generic over five parameters, and `tabType` was typed `string` while both
implementations narrow it (`SoapTabType`, `GraphQLTabType`). A callback whose parameter is the *narrow* union
is not assignable to one taking `string` — the hook could hand it a value it cannot handle — so **every**
type-carrying argument was rejected and every one was silenced with `as any`. With nothing left to infer
`State` from, TypeScript fell back to `unknown`: 105 errors, one per `state.x` access.

**The fix is a sixth type parameter.** `TabType extends string` makes `tabType: TabType`, so the narrow union
flows through and the casts can go.

### And then my own oversight, which cost two rounds

I added `TabType` to the interface and to the function's generic list — and **not to the parameter
annotation**:

```ts
}: ProtocolEditorConfig<State, Action, Draft, SavePayload, Entity>) {   // ← five, not six
```

So `TabType` silently took its default `string` and *nothing changed*. The error message said the target was
`(…, tabType: string) => SoapTabState` — i.e. it was telling me the generic was `string`, and I read past it
twice before grepping the hook's own declarations.

**A type parameter that appears in the declaration but not in the use site is invisible.** The default made
it silent rather than an error, which is exactly what defaults do.

### What the numbers did, and what they mean

| Change | Errors |
|---|---|
| before | 152 |
| `TabType` added, casts removed | 97 → 50 (all 105 `unknown` errors gone) |
| **removing the default** to force inference | **123** — *worse* |
| the annotation fixed, both call sites given all six | **43** |

Two things worth keeping:

- **Removing the default made it worse, not better** (123 against 50). A failed inference falls back to the
  *constraint*, so dropping the default converts a silent `string` into `string` plus a cascade. And
  TypeScript rejects a partial argument list outright — *"Expected 5-6 type arguments, but got 3"* — so at a
  call site it is **all six or none**, and "none" is what produced the casts. An explicit argument list is
  checked; a cast is not.
- **`initial` had to become optional.** Every call site's own prop is optional and therefore
  `Entity | null | undefined`, while the hook demanded `Entity | null` — enough on its own to make
  TypeScript abandon inference for the whole call and fall back to the parameter defaults. The hook already
  normalises it (`initState(initial ?? null, …)`), so accepting `undefined` states what the code does.

**Verified**: both bundles build, 475 tests pass, and `npm run verify:web` → **PASS** with 0 console errors,
0 uncaught page errors, 0 warnings. The change is type-level only — `as any`, generics and `?:` are all
erased — but the browser check is what makes that a measurement rather than a claim.

**A process note:** the first browser check failed and I nearly recorded it as a regression. The host process
had died (its task had been cleaned up), so the form never detached. **The failure was the instrument, not
the product** — and the check only became meaningful after confirming the host was listening.

## The remaining 43 were not 43 problems — and two of them were live bugs

I listed the rest as "43 heterogeneous type errors". Reading them clustered by *cause* instead of by file
showed about **eight** root causes, and two of them were defects a user could hit.

### `setOpenTabs` — a `ReferenceError` on saving a new WebSocket or Webhook

`EntityTabsResult` has no `setOpenTabs`. It has **`replaceTab(draftId, savedId)`**, documented as *"Replace a
draft tab id with the newly saved entity id."* Two panels had hand-rolled a partial copy of that function's
body and called the setter directly:

```ts
setOpenTabs((prev) => [...prev.filter((id) => id !== tabId), created.id]);
setActiveTab(created.id);
```

- In `WebSocketsPanel.tsx` the compiler said **`TS2552: Cannot find name 'setOpenTabs'. Did you mean
  'openTabs'?`** — it was never destructured, so it was a bare undefined identifier:
  `ReferenceError: setOpenTabs is not defined`.
- In `useWebhooksPanelState.ts` it was `TS2339` — destructured, but not on the type, so `undefined(...)`:
  `TypeError: setOpenTabs is not a function`.

Both panels are rendered by `panelFactory`, so **creating a new WebSocket or a new Webhook in the UI threw**.
The replacement is `replaceTab(tabId, created.id)`, which does what those two lines did *and* the `clearDraft`
and `tabRefs` cleanup they had forgotten — so the explicit `clearDraft` is gone rather than duplicated.

**The type error was the entire warning, and it was being ignored as noise.** That is the cost of a
tolerated error count: it makes a `ReferenceError` look like one more line of red.

### A type that existed nowhere: `WebhookDraft`

`WebhookEditor.tsx` referenced `WebhookDraft` in two places — `loadDraft<WebhookDraft>(tabId)` and
`satisfies WebhookDraft` — with **no definition and no import anywhere in the repository**. It was an
unresolved name, so the editor's draft was silently untyped; the `as SavedWebhook | null` casts a few lines
below are the symptom, since there was no shape to narrow. It is now defined and exported from
`WebhooksPanel` (where `WsDraft` lives, and where the drafts are written), with its fields read off the
editor's own state — the only evidence available for a type that had gone missing. `WsDraft` itself existed
but was not exported, so `WsEditor` could not see it either; both are now imported as **type-only**, which
is what keeps the panel↔editor cycle erased rather than real.

### Where this leaves it

**152 → 33.** Still to do, by cause rather than by file: the `FolderTreeItem` import style (4 files, a
default export imported as a named one), the `(oldI, newI)` vs `(fromId, toId, edge?)` drag-callback drift
(7 sites), the `Mapping` type and `MockRule.path` that no longer exist (5), `Environment | null | undefined`
against `Environment | null` (3, the same class as `initial`), the `strings.*` keys that don't exist (2), and
`.error` read on a `{ ok: boolean }` (2).

**The lesson I'd carry forward: a tolerated error count is not neutral.** Every one of these was visible in
`tsc` output for as long as the count was 152, and two of them were crashes. The count is what made them
unreadable.

## Docker — the image works, and it cannot be reached

`plan/10-phase-9-docker.md` already existed, and its Dockerfile carries a warning that it **cannot boot**:
`packages/*/dist/**` keeps *bare* requires for its runtime dependencies (`bundle: false` is load-bearing,
because `store/paths.ts` holds the data root as module-level state) and it copied only `dist/` plus the root
manifest — so the first `require` of `mkcert`, `simple-git`, `ws` or `@bifurc/protocol` throws.

**Four things in that document were stale**, all corrected in place:

1. Its `ENTRYPOINT` names `engine/runtime/host.js`, which is a **library** — `createWorkspaceHost`, and by its
   own header *"nothing imports it"* is why `hostCli.js` exists. Running it does nothing.
2. Its env vars — `BIFURC_RPC_HOST`, `BIFURC_RPC_PORT`, `BIFURC_RPC_TOKEN`, `BIFURC_RPC_TOKEN_FILE` — **are
   read by nothing.** The CLI reads `BIFURC_DATA_DIR`, `BIFURC_ENGINE_TOKEN`, `BIFURC_PROXY_BASE_PORT` and
   takes `--ws-host`/`--ws-port`/`--token-file`/`--workspace`. Those names were written before the CLI.
3. Its dependency table says "exactly four packages". It is seven plus `zod`: `@bifurc/protocol`, `archiver`,
   `js-yaml`, `mkcert`, `simple-git`, `unzipper`, `ws`.
4. **Its exposure table cannot be satisfied as written** — see below.

### The significant one: nothing the host binds is publishable

The plan says to publish the proxy port. It cannot be:

- the proxy **hardcodes** `server.listen(port, "127.0.0.1")` (`proxy/server.ts:208`), and `store/config.ts`
  has no bind-host setting;
- the RPC guard refuses a non-loopback bind, and `transport/ws.ts` says *"nothing in the programme sets
  `allowNonLoopback`"* — the opt-in exists, is enforced against TLS, and **no entry point exposes it**.

Measured, not read: `hostCli.js --ws-host 0.0.0.0` fails with *"Refusing to bind 0.0.0.0 … Pass
allowNonLoopback: true to accept the exposure."*

So `docker run -p 8080:8080` maps a host port to a container port nothing is listening on. **The image is a
same-machine deployment**, reached with `--network=host`, a sidecar or an SSH tunnel — which is what the
plan's own work item 4 recommends, so this is a coherent story rather than a broken one. But it is not
"host it on a server and connect from my laptop", and that difference is the whole of what the user asked
for.

Publishing it needs two code changes, both **product decisions** rather than wiring: a
`--ws-allow-non-loopback` flag, and a configurable proxy bind host. The engine generates TLS CAs, executes
scripts and spawns child processes, so a published RPC port is a remote code execution surface — the plan's
own words. Not something to slip into a Dockerfile.

### What was verified, and what was not

**Verified without Docker.** I could not build the image (Docker Desktop is not running, and starting it is
a desktop action), so instead I assembled the runtime stage's **exact** layout — the seven runtime packages
from the registry, the two `dist` trees, the manifests — and ran the CLI from it:

```
[host] rpc endpoint: ws://127.0.0.1:8099
hello      -> ok, engineVersion=0.0.0 sessionId=697b29b8-…
config.get -> ok, proxyPort=80 workspaces=1
```

That is the specific failure the plan predicted for its own Dockerfile, tested directly: the host runs **and
serves** with no dev dependencies, no Electron and no repository around it.

**Not verified:** `docker build` and a real container run. Treat the Dockerfile as reviewed rather than
exercised, and say so rather than implying otherwise.

**A trap I walked into:** my first probe sent `clientName: "docker-sim"` and got `BAD_REQUEST` — I read it as
a host problem for a moment. `ClientNameSchema` is a four-value enum (`electron-shell`, `web-ui`, `cli`,
`bifurc-extension`), so the schema was right and my probe was wrong. A containerised host is reached by
`cli` or `web-ui`; no new name is needed.

## The port and mapping redesign — `plan/15-unified-ports-and-mapping.md`

The request: features should differ by host kind (a remote engine cannot do localhost mapping), the port model
should split so that the host-level things share one port and the per-workspace things have their own, and the
result should be one uniform channel across all five ways to run Bifurc. **Deliverable is a plan, not code.**

### What the measurements changed about the design

Four things were not what I expected, and each one reshaped the plan:

1. **The proxy already does both jobs on one port.** `proxy/server.ts`'s dispatch is: `localhost` → a home
   page; **`*.localhost`** → the reverse proxy (with mocks); an absolute `http://` URI → the forward proxy;
   otherwise TLS interception. So the user's "separate the forward proxy" is a **split of one server into
   two**, not a new server. And the forward half is a *subtraction* — the reverse branch moves out.
2. **The reverse path is gated on `host.endsWith(".localhost")`**, not on a mapping existing. So subdomain
   routing is not a new feature: `LocalMapping` already carries `domain → target` where `target` is a
   `host:port` string, and the user's own config holds `{domain: "bifurc.localhost", target: "localhost:8080"}`.
   `target: "192.168.1.50:3000"` would flow through `proxyToUpstream` unchanged. **One gate is the whole of
   what stands between today and subdomain mapping.**
3. **The companion is the compatibility trap.** `legacyCompanion.ts` is a WebSocket bridge on
   `127.0.0.1:9271` whose stated contract is to *"keep serving port 9271"* for an **already-released**
   extension that hardcodes the port. Moving it onto the edge port breaks every installed extension, and the
   extension cannot be updated atomically. The plan recommends binding the handler on both — the edge, plus a
   deprecated 9271 listener — for one release cycle.
4. **The routing table has to become host-level, and that is the substantive work.** Today
   `cfg.mappings` is the *active* workspace's list — `server.ts` says so in its own comment. A host-level edge
   cannot work that way, so the table is keyed `domain ⇒ { workspaceId, target }` and **the request's `Host`
   selects the workspace**, which is what makes that workspace's mocks apply. Today the reverse path matches
   the *active* workspace's mocks, which is wrong the moment two workspaces both publish mappings — and that
   is true independently of subdomains.

### The model

| Tier | Port | Carries | Scope |
|---|---|---|---|
| Host | the **edge** (`80`/`443`) | the web GUI · the reverse proxy · the companion | per host, shared by all workspaces |
| Workspace | the **forward proxy** | the forward proxy · **mocks for forward-proxied traffic** | per workspace |
| Workspace | **webhook**, **socket** | the mock receivers | per workspace, user-settable |

The RPC endpoint stays separate from the edge, deliberately: it executes scripts and spawns processes, and the
edge proxies traffic. Merging them would mean the port you publish to serve a GUI is also the port that runs
code.

### Two things worth flagging before anyone starts

- **Work item 1 gates everything.** Nothing here is testable until the bind opt-in lands — today
  `hostCli.js --ws-host 0.0.0.0` fails, so a remote engine cannot be reached at all. Same finding as the
  Docker work, now on the critical path rather than a caveat.
- **`AppConfig`'s four port fields are git-tracked *preferences*; `runtime.json` holds resolved *outcomes*.**
  The UI currently shows one number and it is the resolved one. With user-settable ports it has to show both,
  or someone who sets 9101 and gets 9102 will not know which they are looking at.

**Two collisions the design must reject at write time**, because they are the only ways it can be silently
wrong: two workspaces claiming one domain, and a mapping whose domain is the engine's own hostname (which
would make the GUI unreachable).

### Revised the same day — two of my decisions were wrong, and both made it bigger

1. **The companion moves outright.** I had treated the released extension's hardcoded port 9271 as a
   compatibility constraint and proposed a deprecated second listener for a release cycle. **The extension can
   be updated**, so there is nothing to work around. The compatibility window, the second listener and the
   risk row are all gone.
2. **The edge resolves the *active workspace's* mappings, not a host-level aggregate.** I had built a
   host-wide table keyed `domain ⇒ { workspaceId, target }` and made the request's `Host` select the
   workspace. That is not the model: **the reverse proxy is host-level by *port* and active-workspace-scoped
   by *content*.** The edge is one port shared by every workspace, and it resolves exactly as the workspace
   proxy does today — same lookup, same config, on a host-level port instead of a workspace-level one.

   **What that deleted:** the host-level routing table (a whole work item), the duplicate-domain collision,
   and the risk that came with it. The edge's branch 2 is now *today's branch 2, moved* — which is a much
   better shape, because it means the reverse path is relocated rather than rewritten.

**The one thing this trades away, stated in the plan rather than buried:** switching the active workspace
switches which domains the edge serves. Workspace A's mappings resolve while A is active; B's show the
not-mapped page until B is active. That is what "the reverse proxy uses the current active workspace's
mapping" means, and it is today's behaviour — but on a *shared* port it is worth making visible, so the home
page should name the active workspace and the risk table carries it. Every other per-workspace surface is
unaffected, because each has its own port and all workspaces run at once.

**A lesson about my own first drafts:** both errors came from the same habit — treating a constraint I had
read in a header comment (`"keeps serving port 9271"`) as fixed, and reaching for a *general* mechanism
(a cross-workspace routing table) where the product wanted the *existing* one. The user's correction was
shorter than my justification for the wrong version. **When a design grows a new data structure, check first
whether the thing it replaces already does the job.**

### And a third: I kept calling a design decision a risk

I had written the active-workspace scope up as *"the one thing this design trades away"*, and put *"make it
visible"* into the risk table — the home page naming the active workspace, the footer showing it. The user's
answer: **it does not matter, the user will know, and tooltips can come later.**

**And the switch already exists.** `workspace.setActive` (`store/coreCommands.ts`) writes `activeWorkspaceId`
and returns the new config, and it deliberately does **not** call `reloadConfig()` — its own comment says why:
*"the port is owned by the workspace, not by which one is selected."* So the plan needs no new command, and
the edge needs no invalidation step: resolving `activeWorkspaceId` per request is enough.

**The same handler documents the other half as the intended D10 outcome** — *"after switching workspace in
the UI, the old workspace's proxy keeps answering on its port"* — which is exactly the user's *"everything
else has their own ports and all workspaces can run at the same time"*. So the model in P15 is not new
behaviour the plan introduces; it is the behaviour the engine already documents, moved onto a shared port.

**The pattern in all three corrections:** I was writing design prose *around* a decision the codebase had
already made, instead of reading what it said. Twice I turned an existing mechanism into a work item; once I
turned an accepted behaviour into a risk. `coreCommands.ts` and `legacyCompanion.ts`'s headers both said the
answer, and both times I wrote past them.

## P15 work item 1 — the RPC bind opt-in (built)

`plan/15` was written earlier today; this session started on it, per its own *"How to start"*. **Work item 1
landed**: the flag chain plus the fail-closed token rule, and one thing the work item did not name.

### The finding: the work item as written delivered nothing

It asks for `--ws-allow-non-loopback` through `hostArgs` → `hostCli` → `HostTransport` →
`createWsServer`'s `allowNonLoopback`, *"plus the fail-closed token requirement"*. **`ws.ts` has had two bind
guards since P4, not one** — a non-loopback bind needs the opt-in **and** `tls` — so a flag wired to
`allowNonLoopback` alone reaches the second guard and is refused. It would parse, pass through, and change no
outcome: the *accepted and ignored* shape `TRAPS.md` treats as a defect, in a work item whose stated purpose
is *"without this, nothing later is reachable"*.

**The missing half was TLS material, not the token.** Nothing in the programme generates a cert for this
endpoint. So `--ws-tls-cert`/`--ws-tls-key` went in with it. Two alternatives considered and **not** taken,
recorded as open decisions rather than oversights: auto-generating from the proxy's existing `mkcert` CA
(forces a hostname-and-trust decision that belongs to a deployment), and relaxing the TLS guard for an
explicit opt-in (trades a two-guard rule that has held for six phases for a flag).

**Lesson, and it generalises:** when a plan names a guard, **count the guards in the module**. The plan was
written from the *outside* of `ws.ts` — the same failure as this morning's, one layer down: prose written
around a decision the code had already made. This time the code had made **two**.

### Where each piece went, and the split that keeps it from drifting

- `hostArgs.ts` — `--ws-allow-non-loopback` (presence), `--ws-tls-cert`/`--ws-tls-key` (value), and the
  **coherence** rules: the trio needs WebSocket mode, the TLS pair must be complete, and the opt-in needs a
  **non-loopback** `--ws-host` so it can never be inert.
- `host.ts` — `allowNonLoopback` + `tls` on `HostTransport`, passed through unexamined; and the fail-closed
  token guard at a new **step -1**.
- `hostCli.ts` — reads the PEM files as **material**, so a bad path fails by name at startup.
- `ws.ts` — `isLoopbackHost` exported, so the guard, the parser and the host share one predicate.

**The split worth keeping: the parser checks command-line coherence, the transport owns the bind policy.**
It does *not* restate "non-loopback needs the opt-in, the opt-in needs TLS" — a second copy of that is a copy
that drifts, and `ws.ts` already reports it.

**Why the guard is step -1, not beside `ensureEngineToken()`.** It must not read `dataDir()` (which
`store/paths.ts` *throws* rather than defaulting — step 1 sets it), and a refusal landing after
`bootstrapWorkspaces()` has written into the data root is a refusal that changed something on its way out.
Asserted rather than asserted-in-prose: a refused start leaves **no** `engine.token` on disk.

### Three traps met on the way

1. **`tokenPath` is shadowed inside `createWorkspaceHost()`** — there is a local `let tokenPath` for this
   run's path, so importing the helper of the same name gives `tsc`'s `String has no call signatures`, a
   message that names neither the cause nor the file. Aliased to `engineTokenPath`, with the reason in a
   comment so nobody "tidies" the alias away.
2. **An empty `workspaces: []` does not mean "no workspace".** `bootstrapWorkspaces()` takes its *"no valid
   workspace on disk — create a fresh empty one"* branch and writes `"Workspace 1"`, so the host starts a real
   runtime and **binds a real proxy port** (`[server:81] listening`, base 80 on win32). My first version of
   the test asserted the opposite in a comment. Left as-is — it is the first-run shape of a container — but it
   means **every host in a test file must be stopped**: a rejected `start()` still leaves the runtimes it had
   already started listening, and that leaked a bound port into the next case until I added the `finally`.
3. **`registerAllEngineCommands()` is not idempotent against one registry**, and `createWorkspaceHost()`
   registers into the module singleton when no registry is passed. Three hosts in one file therefore need
   three fresh registries.

## P15 work item 2 — the proxy's bind host (built)

Continues the section above and closes its first **Left open** item. `server.listen(port, "127.0.0.1")` is no
longer a literal; the proxy takes a bind host, and a non-loopback value needs its own explicit opt-in.

### The asymmetry is the design, and it is the mirror image of work item 1's

Work item 1's finding was that `ws.ts` has **two** guards where the plan named one. This is the reverse: the
proxy's guard has **one** condition where the RPC's has two, and the missing half is deliberate.

| | RPC (`transport/ws.ts`) | Proxy (`proxy/server.ts`) |
|---|---|---|
| non-loopback, no opt-in | refused | refused |
| non-loopback **with** the opt-in, no TLS | **refused** | **allowed** |
| opt-in shared with the other | — | **no** — `--proxy-allow-non-loopback` |

`--ws-allow-non-loopback` is worthless without `--ws-tls-cert`/`--ws-tls-key` because the RPC channel can
carry TLS and should. **A forward proxy's client speaks plain HTTP to the listener** — it sends `CONNECT` for
the https it wants tunnelled — so a TLS requirement there would break the browser the port exists for. The
absence is therefore asserted **directly** in `tests/proxy/server.test.ts`: a later "make the two binds
symmetric" edit would pass every other case in that file and break the proxy.

The opt-in is separate for a different reason: the exposures are not equal. This port forwards into whatever
the machine can reach *and* performs TLS interception, so one flag for both would make accepting the smaller
exposure imply accepting the larger.

### The predicate moved, and the reason is measurable

`isLoopbackHost` was private in `transport/ws.ts`. The proxy needed the same question answered, and the two
options were not equivalent:

- importing it from `../transport/ws` works, and it drags the `ws` package, `node:http`, `node:https` and
  `assertBridgeIsTotal()`'s import-time assertion into every graph that reaches the proxy server. Measured:
  `tests/proxy/server.test.ts` mocks `http` and `https` outright, and the parser suite would have loaded a
  WebSocket server **to compare two strings**.
- a dependency-free `lib/net.ts` that both import is one definition with no edge between the layers.

`transport/ws.ts` re-exports both names, so its callers and the transport barrel are unchanged. **A second
copy was the thing to avoid** — `LOOPBACK_HOSTS.includes(host.toLowerCase())` written twice is how "the
transport thinks `::1` is remote but the proxy thinks it is loopback" happens, and the two would disagree in
the *permissive* direction, which is the direction that publishes a port.

### Three decisions

1. **`bindHost` is a host-local option, not an `AppConfig` field.** `AppConfig` is the git-tracked,
   **syncing** per-workspace config (`store/gitStore.ts`), so a bind host stored there would carry one
   machine's interface name to another and back. Same rule that keeps resolved ports in `runtime.json`.
2. **The guard throws from `createProxyServer()`, not from `start()`.** A configuration error has nothing to
   retry, and throwing early means the host never bootstraps a data root it did not need to touch. The test
   asserts the stronger half: `net.createServer` is never reached.
3. **Host-wide, not per-workspace.** A host running N workspaces publishes all N proxies or none. A
   per-workspace choice needs an override source that does not exist yet — stated at the option and at the
   flag rather than discovered later.

### Evidence

`tests/proxy/server.test.ts` — 6 new cases (102 total). `hostArgs.test.ts` — 8 new (38 total).
`tests/integration/proxyBindPolicy.integration.test.ts` — **new, 5 cases, real I/O**.

The integration file exists because the mocked unit suite **cannot** see the wiring: `host.ts` →
`workspaceRuntime.ts` → `proxy/server.ts` is three hops, and a `vi.mocked(net.createServer)` assertion passes
just as happily on a host that dropped the option. The two cases carrying the claim are a **controlled
comparison**: the default answers on `127.0.0.1`, and with the machine's LAN address named, the same probe to
`127.0.0.1` is **refused** — which no firewall can fake, because a connection to loopback is never filtered —
and the LAN address answers. `0.0.0.0` is used nowhere here: it is a bind *wildcard*, not a destination, so a
probe against it would fail for an unrelated reason. The two cases that need a LAN interface **skip and say
so** on a machine that has none.

**Four mutations, each judged by exit code, each caught by the cases that should catch it:**

| Mutation | Result |
|---|---|
| `host.ts` drops the `proxyBindHost` pass-through | **3** integration failures — the wiring, exactly as designed |
| the proxy bind guard removed | 1 file failed |
| the opt-in read as `!== undefined` instead of `!== true` | 1 file failed |
| the parser's proxy coherence check removed | **2** failures — both coherence cases |

The first row is the one that matters: it is the evidence that the integration file earns its keep rather
than restating the unit suite.

Gates: `typecheck` EXIT=0. Unit **2,261 tests / 87 files**, integration **473 tests / 33 files** — total
**2,734 / 120**, which is the previous **2,715 / 119 plus exactly the 19 cases added here** (8 + 6 + 5). The
arithmetic matching is a cross-check, not a coincidence.

**A flake, named rather than reported as a number.** Three consecutive full unit runs gave **0**, then **4**,
then **1** failures, all in `tests/store/gitStore.test.ts` (`commitMutation() > creates a git commit with the
correct subject format`) — the documented load-induced git pair, signature 95 s in isolation. Both real-git

### Two workflow notes

- **The mutation recipe that worked, and it is worth reusing.** Apply the mutation by passing the
  find/replace pair through **environment variables** to a one-line `node -e` (`FILE`/`FROM`/`TO`) rather than
  quoting it into `sed` — the strings contain `!`, `(`, `)` and `{`, and a bash-quoted `sed` invocation is
  where that goes wrong. Back up with `cp`, run the suite, restore in the **same** command so the restore
  cannot be skipped, and print a `grep -c` of the restored line as the receipt. Never `git stash` in this repo.
- **The safe-delete shim blocks `npm run build:packages` outright** — `tsup`'s `clean` step trips
  `SAFE_DELETE_BULK_CONFIRM_REQUIRED` at 50 files and the build dies *after* printing "DTS Build start". The
  fix is the documented `CODEBUDDY_SAFE_DELETE_ENABLED=0`, which `MEMORY.md` already records; what is new is
  that it applies to **this** script too, not only to the test runs.

### Left open

- **Both deployment halves are still unrun.** The plan's verification steps for items 1 and 2 each end with a
  machine that is not the engine's. What is measured here is a *local* connection to the machine's own LAN
  address: that proves the bind moved, but not that a second machine can reach it — a router or firewall
  between them is not in the test.
- **Both bind guards throw `ENGINE_ERROR`, which `packages/protocol/src/errors.ts` classifies *retryable*.**
  A refused bind is not retryable, so a client honouring that flag would retry a configuration error. Not
  changed — it is the transport's existing convention and matching it is what keeps the two guards
  consistent — but it is a taxonomy question worth settling once, for both. Recorded in `plan/15`.

# `plan/15` work item 3 — **the proxy is split** (later the same day)

**Built and verified.** One socket served two jobs; there are now two servers. The **edge router**
(`packages/engine/src/proxy/edge.ts`, new) is host-level and serves the reverse half; the **forward proxy**
keeps its job and the reverse branch is gone from it.

## The split

| | Edge router | Forward proxy |
|---|---|---|
| Tier | **host** — one listener for every workspace | **workspace**, as before |
| Port | `settings.port`, **inherited** | D16's base, **moved off** `settings.port` |
| Serves | branch 2 (mappings, mocks first) + branch 5 (the home page) | branch 3 (`matchProxyRule`, `handleProxyRouting`, `proxyWithScripts`) |
| Opt-in | `--edge-allow-non-loopback` | `--proxy-allow-non-loopback` |

**Why this is §6.2's migration with no mapping edited:** `settings.port` is *host-local* `app.json`
(`AppSettings.port`, default `80`) — the port every existing `*.localhost` mapping already points at. So the
edge inherits it and the forward proxy moves off it. Nothing in a workspace's config changes.

## Three measurements that shaped it, not three assumptions

- **An `http.Server` tolerates a handler that writes raw bytes to `req.socket` and never touches `res`.**
  Probe, node 22.22.2: two responses on one keep-alive connection, both delivered, no `error` and no
  `clientError`. This is what let the edge be an `http.Server` **and** hand branch 2 to the existing
  socket-level helpers — so no proxying code was written, only relocated.
- **Node handles `Expect: 100-continue` correctly with NO `checkContinue` listener.** A hand-written listener
  was about to be added; the probe showed the interim `100 Continue` goes out and the whole 64-byte body
  reaches the handler. The listener was deleted and replaced with the measurement in the docblock.
- **The old hand-rolled parser truncated a body split across two reads** — it took the body from the same
  `data` chunk that carried the header terminator. The edge buffers fully instead: a behaviour change,
  recorded as one, and asserted.

## The five decisions

1. **Never touch `res`** (measurement 1) — buffering instead would break SSE and large downloads.
2. **No `checkContinue` listener** (measurement 2).
3. **`resolveConfig` is a function, called per request.** That is what makes `workspace.setActive` need no
   invalidation step. `null` is a real state (a workspace skipped for a taken port override, or `--workspace`
   filtering the active one out) and gets its own **503** page — because the ordinary home page would say
   "No mappings yet" about a workspace that has plenty.
4. **A third bind opt-in, not a shared one.** The RPC endpoint executes commands, the forward proxy forwards
   into the machine's network, and the edge routes a *client-chosen* `Host`. One flag for all three would make
   accepting the smallest exposure imply accepting the largest.
5. **The edge's port is bound, not scanned.** D16's scan is for a port nobody addressed; this one *is*
   addressed — it is where the mappings point and what the home page's links are built from.

## Evidence

- `tests/proxy/edge.test.ts` — **new, 40 cases**, driving the real `http.Server` by capturing
  `http.createServer`'s handler. Includes `never writes through res` (decision 1 as an assertion) and the

- Eight suites migrated; `proxyHarness` gained the pair (`port` / `edgePort`), `forwardRequest` /
  `edgeRequest`, and `proxyRequest` **routing by request shape** (absolute → forward, relative → edge).
- `getPort() || …` instead of `loadConfig().port` in `serverCommands.ts` and `configCommands.ts` — the
  proxy's port is the **resolved** one, because `settings.port` is now the edge's.

**Eight mutations, each judged by exit code.** Caught: cache `resolveConfig` (**2**); the bind guard removed
(**2**); `null` → home page (**2**); the `try/catch` around `route()` deleted (**1**); `res.writeHead` touched

# Work item 9 — the host's own domain (`--domain`), added on the owner's instruction

`plan/15`'s "how to start" list did not contain this item. It was added because **three other work items were
each waiting on the same missing input**: §3.3's branch 3 (WI 5) has to recognise which `Host` is *this
engine's own* before it can serve a GUI there; §3.3/§8's write-time collision refusal needs to know what a
mapping must not shadow; and §4.3's mapping editor (WI 7) needs a suffix to suggest instead of a hardcoded
`.localhost`. One flag, three blockers.

## What the flag is, and the discriminator that makes it two rules rather than one

`--domain <host>`, **required** — a headless host refuses to start without it. It may be `localhost` (the engine
is on the operator's own machine, so `*.localhost` mappings are meaningful — RFC 6761 resolves them to the
*browser's* loopback, which is this engine's) or a `domain.TLD` (the engine is reached by name from somewhere
else, so `*.localhost` resolves to the *visitor's* machine and a mapping has to be `<sub>.<domain>`).

**The parser is only reached by the standalone CLI.** The Electron shell starts the engine **in-process**
(`createWorkspaceHost`) and never calls `parseHostArgs` or `hostCli.ts` — so "required in the parser, defaulted
in the option" *is* the owner's Electron-versus-standalone distinction, and it needs no `isElectron` branch
anywhere. `host.ts` defaults the option to `DEFAULT_HOST_DOMAIN`; `hostArgs.ts` requires the flag. One rule, two
entry points, and the difference between them is real rather than an inconsistency.

**A wrong default would have been worse than no default**, which is the argument that settled it: defaulting to
`localhost` would offer `*.localhost` mappings on every headless deployment — including the ones where they
resolve to the visitor's machine and quietly do not reach this engine.

## Four decisions worth not re-litigating

1. **It reaches the client, or it does nothing.** Every consumer listed above is unbuilt, so a flag stopping at
   `WorkspaceHostOptions` would be *accepted and ignored* — the shape WI 1's own record is about. It is
   therefore advertised in `hello` as `hostDomain`, the channel §4.1 already designates. **It is not
   `hostKind`:** §4.1's `local`/`remote` signal is a separate field and WI 7's, and a client that derived it
   from this string would be making the decision the *host* is supposed to make.
2. **A CLI flag, not an `AppConfig` field.** `AppConfig` is git-tracked and syncs (`store/gitStore.ts`), so a
   hostname stored there would carry one deployment's name to another machine and back. `proxyBindHost`'s
   reason, and sharper here: a bind host describes a *machine*, a domain describes a **deployment**.
3. **Shape-checked, though the two bind hosts deliberately are not.** Not a change of policy — the difference is
   what the value is *used for*. A bind host's only consumer asks "is it loopback?", which is total over any
   string. This value is **displayed** (it becomes the editor's suggested suffix) and **compared** against a
   mapping's `domain`. `http://engine.example.com/` and `engine.example.com:8080` would sail through a bind
   guard and each produce a suggestion that resolves to nothing, plus a collision check that silently never
   fires. **Intent is still not checked**: a single-label name (`bifurc`, a compose service) and an IP literal
   are **accepted**, and two cases pin that rather than leaving it to chance — refusing one would turn a
   deployment that works into a host that will not start.
4. **Canonicalised at the boundary.** `normalizeHostname` (lower-case, one trailing dot stripped) joins
   `isLoopbackHost` in the dependency-free leaf `lib/net.ts`, with `DEFAULT_HOST_DOMAIN` beside it. Two
   spellings of one name would make the collision check miss the collision it exists to catch — and the miss is
   invisible, because the check's *passing* is also silence. Applied twice on the real path (parser, then
   host); harmless because it is idempotent, which a second *validation* would not be.

# Work item 10 — the headless host's CRUD kinds, and a stale fixture

## The defect, and how it was caught

`plan/15` item 5 says a hosted Bifurc whose web UI cannot create a mapping is not hosted — so before serving
the GUI I checked the commands a headless host actually routes. After `registerAllEngineCommands()`:

| after | `entity.delete({kind:"mocks"})` |
|---|---|
| `registerAllEngineCommands(reg)` | `kind "mocks" is not routed through the CommandRegistry yet` — for **all 16 kinds** |
| …then `registerCrudKind({kind:"mocks",…})` by hand | **`{ok:true}`** |

`isRegistered("entity.delete")` was **true** throughout. So a headless host advertises a command that cannot
run, and the message blames the *kind* rather than the host.

**The control is what made this diagnosable in one step.** Populating one container by hand and re-invoking
turned "the command is broken" into "the container is empty" — and the container, not the command, was the
thing that had moved out from under the engine.

The four `entity.*` commands are engine-side, but the **options containers they read** were populated by five

commands moved engine-side, the containers they consult did not.

**Invisible to the existing drift guard by construction** — it compares *command names*, and a container is
not a command. That is the generalisable lesson, and it is in TRAPS.

call it from `registerAllEngineCommands()` **first**, before the eighteen `register*Commands()` calls. All 16
kinds now `{ok:true}`.

**The five explicit calls in `src/ipc/handlers.ts` were kept, not collapsed** — reasoning recorded in the
file. **Mutation:** commenting out `registerCrudKinds();` → **1 failed, `EXIT=1`**.

**The new guard invokes rather than enumerates**, and derives its input: it iterates `EntityKind.options`
(a schema, not a hand-written list). That matters — a hand-maintained list in a test drifts, and the drift is
invisible. `workspaceHost.integration.test.ts` went 3 → **4** cases.

# `plan/16` written — the GUI's own backend, and the single image

**A PLAN ONLY. Nothing built.** The owner asked for a written plan, from two coupled proposals: (A) one Docker
image carrying engine + GUI on different internal ports, the engine exposing the GUI on a subdomain so the GUI
port stays unpublished — *"just like our electron app"*; (B) the web UI stops talking to the engine directly
and talks to its own thin backend (`ws`/API, *"maybe next JS or something"*), and Electron's UI talks to its
own backend over a pipe — *"so it will be exactly similar apart from communication and deployment methods."*

Lives at `plan/16-gui-backend-wrapper.md`; registered in `plan/README.md`; cross-referenced from `plan/15`.

## The two things that made it a short plan rather than a long one

1. **A pipe transport already exists and is done** — `transport/socket.ts` (unix socket / named pipe, `0600`
   on POSIX, `Capability.SOCKET`, its own conformance runner). So B's *"over pipe"* is available; what does
   not exist is a **backend**.
2. **The web GUI is served by nothing.** `build:web` → `dist/web`, and `web/vite.config.ts` sets
   `base: "./"` with the comment that this is what *"makes the 'engine serves the UI' option in work item 5
   available later."* That is `plan/15` item 5, and it is **not built**.

## The plan's central constraint — and the reason it exists

**The backend may add transport, credentials and static files — and no commands.** If it starts answering its
own commands ("get the mappings"), then every engine command needs two implementations, one of them outside
`surface.ts`'s 144-key typecheck; the browser and Electron stop being the same shape, which was the whole
point; and **the divergence is quiet**, because the UI still compiles — it reads `window.api`, and only the
contents differ per host. Stated as an acceptance criterion (enumerate the backend's endpoints, expect two),
not as a paragraph.

## Four decisions recorded as recommendations, one as an open question

- **Not Next.js.** It would add a build tool, a runtime, a second bundler and an SSR boundary to a process
  that is otherwise `node` plus the engine's code — for a client-rendered app whose backend has **two** routes.
  The one real benefit (server functions holding the token) is already written twice in this repo. Stated as
  a recommendation with the case, so the owner can choose on preference rather than on a claimed need.
- **The GUI belongs at the engine's own domain**, not at `console.` — a new subdomain costs a DNS entry and a
  certificate for a page that *is* the admin surface. Override, not default. `plan/15` §3.3 already chose it.
- **The direct-connect form is demoted, not deleted** — a standalone browser against a separate engine is a
  real deployment and is how `verify-web-ui.mjs` works today.
- **`127.0.0.1`, not "unpublished", is what makes the GUI unreachable** — `EXPOSE` does not bind anything, and
  the criterion asserts it by request from outside.
- **OPEN, for the owner: who may read the admin GUI on a published port?** Neither plan answers it, and
  `plan/16` says it should be decided *before* item 5 is built.

## Left open, stated rather than implied

`plan/16` has no implementation, no test and no run behind it. Its items 0 and 6 are `plan/15`'s items 5 and 7.
Its acceptance criteria are **unmet** and should stay marked so until someone runs items 5 and 7 on a real
deployment — which is also the first place `plan/15` items 1/2/4/9/10's deployment halves *must* run.

(9271), described in its own header as *"the only thing the released extension can talk to"* until the
extension speaks v2. It is **not the RPC endpoint**, and merging them is `plan/15` WI 6 + the extension's
port change, in that order. **The deeper issue: the companion takes no token** — it is a bare
`{id, action, payload}` client with no `hello`. If it shares a port with the authenticated RPC surface, the
merged listener must either accept unauthenticated frames (a hole) or the extension must authenticate (a v2
change). **His model is the destination; it is not the current state.**

**(c) `Host` routing must be the LAST match, not the first — and this is the one that would silently shadow
mappings.** With the GUI on the bare domain, if the server is reached as `domain.tld`, then the engine's own
domain *is* a key in the same space as mapping domains. A user who maps `domain.tld` → some service **shadows
the admin GUI completely**. `plan/15` §3.3 already names this: *"a mapping whose domain is the engine's own
hostname, which would shadow the GUI and make the admin surface unreachable"* — **refused at write time, and
the refusal is unbuilt** (it needs WI 7's `hostKind`). His answer *"for everything else we use the mapping
table"* is right for everything **except** the collision.

**(d) His #5 has an unstated recursion — two, actually.** A mapping's `target` is `host:port`, and the edge
does no loopback/link-local check today. So a user mapping `svc.domain.tld` → `127.0.0.1:<webhook>` makes the
edge **reach its own host's ports**, and `---` → the edge port itself is a **loop**. Neither is refused and
neither is tested. Also: **the webhook and socket servers are per-workspace** (§3.1), so a mapping to
`localhost:<webhook>` is only meaningful for whichever workspace owns that port — his "custom subdomain
mapping" cannot express *which* workspace.
